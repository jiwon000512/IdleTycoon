# 연출·완성도 중간 점검

언제: **여러 기능이 쌓인 중간 점검 때**(사용자 결정 2026-09-18). 기능마다 지키는 원칙은 `기획/코드-규칙.md` 6장 "연출 원칙"이 따로 있다. 이 스킬은 그 원칙이 실제로 지켜졌는지 게임 전체를 훑는 절차다.

## 이 게임에 맞춘 전제 (원문 프롬프트보다 우선)

- 세로 고정 모바일(Android 우선) 방치형 타이쿤. **전투가 없다** — Hit Stop·Knockback·Damage Preview 같은 전투 항목은 "해당 없음"으로 한 줄만 적고 넘어간다. 대응하는 사건(손님 결제·화난 퇴장·재고 소진 등)이 있으면 그쪽으로 옮겨 평가한다.
- 버튼 Hover는 모바일에서 의미 없으니 제외. Press·Release·Disabled만 본다. 햅틱은 모바일 기준(짧게, 중요한 사건에만).
- 아트는 2px 격자 픽셀아트 + 진갈색 외곽선(`기획/아트-프롬프트.md` 0장). 연출 제안이 격자를 깨면(비정수 스케일·회전·블러) 그 비용을 적는다. 칸 편집 프레임·정수 이동·색 플래시가 우선.
- 사운드는 아직 없다. "사운드 없음" 자체를 한 항목으로 평가하되, 사운드 동기화 항목은 "도입 시 지킬 점"으로만 적는다.
- 반복 방치형이라 **반복 시 지루해지는 연출**을 특히 엄격히 본다. 같은 사건이 분당 수십 번 나면 효과는 짧고 작게.

## 절차

1. `기획/진행상황.md`, 설계 아티팩트(진행상황에 링크), `기획/재미-프로필.md`를 읽는다.
2. 코드에서 사건 목록을 뽑는다: Core 이벤트(`ShopSim`·`ZooState`·`Navigation` 등)와 그 이벤트를 받는 View/Presenter. 이벤트는 있는데 받는 표현이 약하거나 없는 곳이 1순위 후보다.
3. 플레이 모드에서 실제로 본다(unity-cli). 사건마다 캡처 또는 상태 조회로 "지금 무엇이 보이는가"를 확인한다. 추측으로 평가하지 않는다. `Application.runInBackground=true`, 시간 가속은 런타임 값만 바꾸고 데이터는 건드리지 않는다.
4. 아래 원문 프롬프트대로 평가하고, 결과를 **아티팩트 보고서**로 낸다(설계 문서는 아티팩트 원칙). 사건 표 + 항목별 평가 + 유지/통합/삭제 + 세 단계 정리. 각 제안에 "어느 파일/이벤트에 붙는지"를 적어 바로 설계로 옮길 수 있게 한다.
5. 보고서만 낸다. 구현은 사용자가 고른 것만, 기능 하나 = 세션 하나 절차(코드-규칙 6장)로 한다.

## 원문 프롬프트 (사용자 제공, 2026-09-18)

현재 게임을 **상용 모바일/PC 게임의 완성도 기준**으로 검토하라.
새로운 콘텐츠나 기능을 추가하기보다, *이미 존재하는 게임플레이가 충분히 전달되지 않거나 완성도를 떨어뜨리는 요소를 먼저 찾아라.*

먼저 현재 게임에서 중요한 사건과 상호작용을 파악하고, 각 사건을
*입력 → Anticipation(준비) → 행동 → 충돌/변화 → 결과 → Recovery/정착*
의 흐름으로 분석하라.

다음 요소를 각각 확인하라.

- 입력 직후의 시각 / 청각 / 햅틱 피드백
- Tween / Lerp / Easing을 활용한 움직임과 수치 변화
- Anticipation / Squash & Stretch / Follow-through / Secondary Motion
- Hit Stop / Hit Flash / Knockback / Screen Shake 등 전투 피드백
- Particle / Trail / Impact / Afterimage 등 시각 효과
- Damage Preview / Trailing Health Bar / Count-up 등 상태 변화 표현
- Camera Zoom / Camera Kick / 이동 / 추적 등 카메라 연출
- 등장 / 획득 / 레벨업 / 사망 / 퇴장 과정
- 화면 전환 / 결과 화면 / Victory / Game Over 연출
- 버튼의 Hover / Press / Release / Disabled 상태 (단, 모바일 등 해당 플랫폼에서 의미 없는 상태는 제외)
- 정보 위계와 UI 가독성
- UI 및 게임 오브젝트의 등장·퇴장 타이밍
- 사운드와 화면 효과의 동기화
- 모바일이라면 Haptic Feedback의 적절성
- 반복 플레이 시 지나치게 길거나 지루해지는 연출
- 여러 효과가 같은 정보를 중복 전달하거나 서로 시선을 방해하는 문제

각각에 대해 **현재 구현 여부 / 문제점 / 개선 효과 / 구현 난이도 / 우선순위**를 평가하라.

효과를 많이 넣는 것이 목표가 아니다. *이 게임에서 체감 효과가 큰 것만 제안하고, 불필요하거나 과한 효과는 제외하라.*

또한 현재 프로젝트에서 중복된 연출, 중복된 코드, 사용하지 않는 기능, 역할이 겹치는 UI, 스타일이 다른 요소를 찾아 *유지 / 통합 / 삭제* 중 하나를 제안하라.

더 화려하게 만드는 것이 아니라 **의도가 명확하고, 일관되고, 플레이어가 행동의 원인과 결과를 즉시 이해할 수 있는 상태**를 목표로 하라.

특히 **로직은 이미 존재하지만 표현이 부족한 사건**을 우선 찾아라.

예: 공격은 되지만 맞았다는 느낌이 약함 · 몬스터는 죽지만 죽었다는 과정이 없음 · 아이템은 얻지만 획득감을 못 느낌 · 버튼은 작동하지만 눌렀다는 반응이 없음 · 레벨업은 되지만 숫자만 바뀜 · 보스가 등장하지만 일반 몬스터와 체감 차이가 없음 · 승리는 되지만 감정적인 마침표가 없음

각 사건의 **게임플레이 중요도에 비례해 연출 강도**를 결정하라. 일반 행동 / 중요한 행동 / 클라이맥스를 구분하고, 모든 사건에 동일한 수준의 Screen Shake, Particle, Sound, Zoom 등을 적용하지 마라.

중요한 시퀀스는 개별 효과가 아니라 **연속된 경험**으로 검토하라. 예를 들어 보스의 마지막 공격부터 승리 화면까지는 *마지막 공격의 임팩트 → 보스 사망 인지 → 짧은 여운 → Victory → 보상 표시* 순서로 이어지도록 검토하되, 반복 플레이를 방해할 정도로 길어지지 않게 설계하라.

마지막에는 제안 전체를 **1. 즉시 수정하면 효과가 큰 것 2. 적은 비용으로 개선 가능한 것 3. 나중에 다듬을 디테일** 순서로 정리하라.
