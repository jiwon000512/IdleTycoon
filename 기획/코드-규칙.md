# 코드 규칙

버전 v1.16 · 2026-09-26
목표는 하나다. **규칙이 어디 있는지 항상 알 수 있고, 한 곳을 고치면 한 곳만 바뀌는 코드.** 스파게티(MonoBehaviour에 규칙이 흩어지고, 서로를 Find로 찾고, 상태를 여기저기서 바꾸는 코드)를 구조로 막는다. 사람과 AI 에이전트 모두 이 문서를 따른다. 줄 단위 표기·포맷·오류 처리·이벤트 규칙은 `프로그래밍-규약.md`. 제네릭 템플릿은 스킬 `unity-project-setup/templates/code-rules.md`.

## 2. 계층과 어셈블리

```
Game ──▶ UI ──▶ Core            (컴포지션 루트가 맨 위. Game은 Data·UI·World·Core를 전부 본다)
Game ──▶ World ──▶ Core         (2D 월드: 우리·동물 개체·카메라. UI와 서로 참조하지 않는다)
Game ──▶ Data ──▶ Core          (화살표 = 참조 가능. 역방향 참조 금지)
Game, UI ──▶ GameKit.Unity      (Manager 파사드)
Tests.EditMode ──▶ Core, Data, UI, GameKit.Core
Editor ──▶ 전부 (에디터 전용 도구)
```

**UI는 Game을 참조하지 않는다**(2026-09-14 변경). 씬 스크립트(Game)가 Presenter를 조립하려면 Game이 UI를 볼 수 있어야 하고, UI 쪽은 Core만 있으면 되기 때문이다. 따라서 UI 코드는 `GameManager`를 직접 부르지 않고, 씬 스크립트가 `GameManager`의 서비스를 Presenter 생성자에 넘긴다.

## 3. 설계 원칙 (금지와 필수)

**필수**
- 클래스 하나 = 책임 하나 = 파일 하나. 파일 이름 = 클래스 이름.
- 의존은 생성자로 받는다. 서비스는 `GameManager.Init()`, Presenter는 씬 스크립트(`MainScene`)만 `new`로 조립한다.
- 외부 경계(시간, 난수, 저장, 테이블 텍스트, 로그)는 인터페이스 뒤에 둔다. Core는 `DateTime.UtcNow`, `System.Random`을 직접 쓰지 않는다.
- 상태는 모델(`ZooState`)이 소유하고, 변경은 모델 또는 서비스의 메서드로만 한다(여러 서비스가 건드리는 값은 모델에 둔다 — 코인이 그렇다). 변경 결과는 `event`로 알린다.
- 여러 곳이 읽는 파생값은 소유자 하나가 계산해 두고 이벤트로 알린다(초당 수입 = `IncomeService.IncomePerSecond` + `IncomeChanged`). 읽는 쪽이 각자 다시 계산하지 않는다(v1.7).
- 숫자는 `ConfigTable.json` 등 테이블에서 온다(`데이터-테이블-규칙.md`). 코드 상수는 형식(포맷 자릿수 등)에만 허용.
- public 표면은 최소로. 기본은 `internal`/`private`. 다른 어셈블리가 써야 할 때만 `public`.
- 불변을 기본으로. 레코드·설정은 `readonly`/init-only. 컬렉션은 `IReadOnlyList<T>`로 노출.

**금지**
- MonoBehaviour 안의 게임 규칙(코인 계산, 확률, 비용 곡선, 레벨 판정 등). MonoBehaviour는 생명주기 훅에서 서비스를 호출만 한다.
- 게임 코드(ZooTycoon.*)의 `static` 가변 상태, 싱글턴(`Instance`), 서비스 로케이터. 예외: GameKit Manager(`UIManager`, `TableManager`, `DataManager`, `PoolManager`)와 **`GameManager`**(v1.6: 게임 상태·서비스를 씬 사이에서 유지. 게임 규칙은 넣지 않는다), **`WorldManager`**(v1.8: 월드 개체·지점 프리팹 생성·Core 이벤트 → 표시. 서비스는 `MainScene`이 `Initialize`로 넘긴다)의 `Instance` 접근은 Game 계층(Manager는 UI도, `WorldManager`는 World 안에서도)에서 허용한다. Core·Data는 어셈블리 경계로 접근 불가.
- `FindObjectOfType`, `GameObject.Find`, `GetComponentInChildren`으로 의존을 "찾는" 코드. 참조는 주입받거나 `[SerializeField]`로 인스펙터에서 연결한다.
- `Update`에서 게임 로직 폴링. 시뮬 갱신은 `GameManager.Update` 하나가 매 프레임 `Mall.Tick(dt)`를 호출한다.
- UI에서 모델 필드를 직접 대입하거나 저장을 호출하는 것. UI는 Presenter를 통해 서비스 메서드를 호출한다.
- 순환 참조(A→B→A). asmdef가 계층 간은 막지만 계층 안에서도 금지. 이벤트로 끊는다.
- 인터페이스를 위한 인터페이스. 구현이 하나뿐이고 테스트 대역도 필요 없으면 클래스를 그대로 쓴다.
- Manager에 게임 규칙을 넣는 것. Manager는 GameKit 파사드 전용이며 순수 C# 클래스를 감싸 Unity 수명주기만 더한다(`프로그래밍-규약.md` 10장).
- 200줄 이상 클래스, 5개 이상 생성자 매개변수. 넘으면 분리를 검토하고 이유를 남긴다.
- `#region`, 주석 처리된 코드, TODO 없는 임시 코드.

## 4. 계층별 규칙

**Core**
- 결정적이어야 한다. 같은 입력·같은 `IRandom` 시드면 같은 결과. 이것이 테스트 가능성의 근거다.
- 서비스는 상태를 받아 변경하고 결과 객체를 돌려준다(예: `GachaService.Pull(state) → PullResult`). 결과 객체는 `readonly struct`나 불변 클래스.
- 이벤트 이름은 과거형 명사구: `CoinsChanged`, `AnimalPulled`, `ZooLevelReached`.

**곳과 사물 (Core, 설계 13)**
- 웜뱃이 다니는 곳은 `WombatArea`를 상속한다(`BakeryArea`·`PlazaArea`). 베이스가 웜뱃 걷기·대상 고르기·auto 행동·버튼을 맡고, 곳은 사물을 조립하고 사물 사이를 잇는다. 굴은 모른다(굴 격자·파기는 빵집 부품).
- 곳 안의 사물은 `Interactable`을 상속한다(`OvenInteractable` 등). 표 행(`InteractableTable`: range·actions·upgrade) + 자기 상태 + 기준점(`DistanceTo`) + 시간 흐름(`Tick`)을 가진다. 사물의 상태는 `private set`, 바꾸는 길은 사물 메서드뿐. **사물이 자기 일을 다 갖는다(v1.14)**: 계산대(`CounterInteractable`)가 줄과 계산 타이머를, 곳은 사물 사이만 잇는다. 곳을 옮기는 사물은 `PassageInteractable` 하나(id `exit`·`door`).
- **손님은 `Visitor`를 상속한다(v1.14)**: `BakeryVisitor`(행동 트리와 잎 행동을 스스로)·`PlazaVisitor`(들를 곳 → 문·계단). 베이스가 외형·Mover·톡 뛰기를 맡고, 곳은 손님 목록과 손님들 사이의 일(비켜 걷기·서는 자리·들를 곳 자리표)만 갖는다. 손님 한 명의 사건(`BakeryVisitorPicked`·`BakeryVisitorGaveUp`·`PlazaVisitorEmoted`)은 손님이 직접 버스에 낸다(v1.15).
- **행동(v1.13)**: 사물에 하는 일은 행동 객체다. `ActionTable` 행마다 `ActionFactory`가 만들고, 행동 클래스는 `ActionFactory` 안 중첩 클래스로 sim마다 partial 파일에 둔다(공통 `Core/Area/ActionFactory.cs`, 빵집 `Core/Bakery/ActionFactory.Bakery.cs`). 새 행동 = 중첩 클래스 + 팩토리 case + 표 한 줄. 행동은 일꾼(`Worker` = 손 `Hands` + 지갑 `ZooState`)을 받고, `Accepts`(받을 수 있는 사물)·`CanDo`(지금 할 수 있나)·`Do`로, 시트 행동(`SheetAction`)은 `Options`·`TryChoose`(사는 것도, 굽기처럼 고르기만 하는 것도)로 동작한다. 값은 행동이 일꾼의 지갑에서 치른다(굴 격자·사물은 돈을 모른다). 어느 사물에서 무엇을 하는지는 `InteractableTable.actions`, 어떻게 하는지는 `ActionTable.mode`(auto·manual·sheet).
- **업그레이드는 행동 하나(v1.13)**: 데이터는 사물 행의 `UpgradeInfo`, 단계는 곳이 사물 종류별로 센다(종류 공통). 그 단계가 무슨 값인지는 사물이 `UpgradeValue(level)`로 정한다. 업그레이드 전용 표·장부는 두지 않는다.
- 행동 id는 `ActionTable.k_*`, 사물 id는 각 사물 클래스의 `k_Id`. **사건은 버스(v1.15, 설계 16)**: 선언은 `Core/Events/Events.Area·Bakery·Plaza.cs`, 발행은 일이 일어난 객체가 `Area.Bus`로(사물 `ThingChanged`·계산대 `BakeryVisitorPaid`·통로 `Passed`·곳 `TargetChanged`·`LayoutChanged`…), 구독자(Presenter·View·Mall)는 토큰을 받고 발신자의 곳으로 거른다. 사물 하나만 보는 그림(OvenView·ShelfView·WombatView)만 그 사물의 C# event `Changed`를 듣는다. 화면은 사물 종류를 타입 패턴(`case OvenInteractable oven:`)으로 가른다.
- 웜뱃은 하나(`Wombat`: Mover + `Worker`, 조이스틱 걷기 `Walk`)이고 `Mall`이 두 곳에 같이 넘긴다(`Mall.Active` = 웜뱃이 있는 곳). 곳 폴더: `Core/Area`(베이스·웜뱃·손·Mall·Mover·행동 트리·손님 베이스·통로) · `Core/Bakery` · `Core/Plaza` · `Core/Burrow`. 굴 공통 상수(칸/유닛 `BurrowShape.k_PixelsPerUnit`, 걷는 땅 `BurrowNav.k_Clearance` 등)는 굴 코드에 두고 배치 클래스가 가져다 쓴다.

**테이블 (Core) · 검증 (Data)**
- 행 클래스(`XXTable`, 파일 `XXTable.json`과 같은 이름)는 JSON 한 행이고 칸을 자료형(숫자·enum·목록)으로 가진다. GameKit `Table<TId>`(Id string·int)를 상속하고 Core에 둔다. Newtonsoft 역직렬화 때문에 `get/set`을 허용한다(이 한 곳만 불변 원칙의 예외).
- 로드·조회는 GameKit `TableSet`(`TableManager.Instance.Tables`)의 `Get<T>(id)`·`GetAll<T>()`뿐이다(테이블마다 예외 없음). 서비스는 `TableSet`을 생성자로 받는다. `TableValidator`(Data)가 `데이터-테이블-규칙.md` 7장 규칙을 검사해 실패 목록을 돌려준다. 예외를 던지지 않고 결과로 보고한다.
- 화면 문구는 `StringTable.json` → `tables.Text(id)`·`Format(id, args)`(Core `Texts`). UI 코드·프리팹에 한국어 리터럴을 두지 않는다(예외 메시지는 한국어가 규칙이므로 제외).

**Game**
- 씬에 놓는 게임 MonoBehaviour는 씬 이름 스크립트(`MainScene`) 하나다. `Awake`에서 `GameManager.Instance.Init()`을 부른 뒤 그 씬의 View·Presenter만 조립한다. `GameManager.Init()` 순서: 테이블 로드·검증 → 저장 로드 → 오프라인 수익 계산 → 서비스 생성. 틱은 `GameManager.Update`.
- 어댑터(`ITableSource`, `ISaveStorage`, `IClock`, `IRandom` 구현)는 GameKit이 제공한다. 게임 전용 어댑터가 필요할 때만 Game에 만들고 이름으로 역할을 드러낸다(`XxxSource`, `XxxStorage`).
- 코루틴은 연출(숫자 보간, 뽑기 애니메이션)에만. 규칙 흐름을 코루틴으로 쓰지 않는다.

**UI (MVP)**
- View: `[SerializeField]`로 위젯 참조, `Show(...)`/`Set...(...)` 표시 메서드, `event Action Clicked` 같은 입력 이벤트. 계산·분기·상태 보관 금지. Core를 몰라도 컴파일되게 원시 타입·DTO만 받는다.
- Presenter: 생성자로 View 인터페이스와 서비스를 받는다. 모델 이벤트 구독 → View 갱신, View 입력 → 서비스 호출. `IDisposable`로 구독 해제.
- View 하나에 Presenter 하나. 팝업도 같은 구조. Presenter끼리 직접 참조하지 않고 모델 이벤트로 동기화한다.

**Tests**
- Core 서비스·수식은 기획서 표의 숫자를 그대로 테스트 케이스로 옮긴다(예: 6.3 표의 n=10 → 311).
- 테이블 검증 테스트는 실제 JSON을 로드해 7장 규칙을 전부 검사한다.
- 테스트 이름: `대상_조건_기대` (`GachaCost_At10Pulls_Is311`).

## 5. 이름과 스타일

- 식별자 영어, 주석·문서·커밋 한국어. 주석은 "왜"를 적는다. "무엇"은 이름이 말한다.
- 표기는 `프로그래밍-규약.md` 2장(Unity 6판 가이드): `PascalCase` 타입·메서드·프로퍼티, `m_camelCase` private 필드, `s_` static, `k_` 상수, `camelCase` 지역·매개변수, 인터페이스 `I`, 이벤트 발생 `On...`, 핸들러 `Subject_EventName`.
- 접미사로 역할을 드러낸다: `...Service`(규칙 실행), `...Calculator`(순수 계산), `...Table`(테이블 조회), `...Storage`/`...Source`(IO 경계), `...View`/`...Presenter`(UI만), `...Ticker`(주기 호출). `...Manager`는 GameKit 파사드와 `GameManager`·`WorldManager`에만.
- 월드 그림 클래스는 `...View`(곳·사물·개체 그림), 개체를 만들고 지우는 것은 `...Spawner`, 소리는 `...Sound`(v1.14: `Shop...` 접두사 폐기 — 게임에 Shop 개념이 없다). Core 이름을 그대로 앞에 붙인다(`BakeryView`, `WombatView`, `VisitorView`). 프리팹 이름도 같다(`Prefabs/Bakery/Bakery·Counter·Visitor·Oven…`, `Resources/UI/ControlHudView`).
- 마리 수는 `Count`다. `Level`은 동물원 레벨과 이후 별 등급에만 쓴다(v1.7, 기획서 v0.15).
- 4칸 들여쓰기, 여는 중괄호 새 줄, `var`는 우변에서 타입이 보일 때만. 한 줄 120자.
- `public` 필드 금지. 인스펙터 노출은 `[SerializeField] private`.

## 6. 작업 절차 (2026-09-14 확정)

작업 단위(기능 묶음)마다 네 단계로 진행한다.

1. **설계**: 에이전트가 설계 **아티팩트**(2026-09-18부터. 옛 `기획/설계/NN-<이름>.md`는 읽기 전용 사본)에 ① 코드 설계(계층 / 클래스 / 책임 / 의존 / 공개 API) ② QA 계획(무엇을 어떤 방법으로 검증하는지, 통과 기준) ③ 기획서 대응 표 번호를 적는다. 사용자와 함께 검토·수정해 확정한다.
2. **구현**: 확정된 설계대로 에이전트가 한 번에 전부 구현한다. Unity CLI(unity-cli 스킬)를 최대한 써서 스크립트 작성·컴파일·씬·프리팹·플레이 모드까지 에디터를 직접 조작한다. 중간 확인을 위해 사용자를 기다리지 않는다.
3. **검증 (2026-09-14 오후 확정)**: 에이전트가 **1회 실행해 직접 검증**한다 — 컴파일 오류 0 · 콘솔 오류 0 · EditMode 테스트 통과(`run_tests`는 플레이 모드가 아닐 때만) · 플레이 모드 진입 후 캡처로 동작 확인. 이것이 개발 완성의 정의다.
4. **알림**: 짧게 보고한다. 만든 것, 검증 결과, 설계와 달라진 점. 테스트 방법 문서는 쓰지 않고 문서화는 최소한만(진행상황 갱신 + 설계 문서에 달라진 점 몇 줄). **커밋은 묻지 않는다**(v1.16): 사용자가 다음 작업을 언급하면 검증이 끝난 앞 작업을 에이전트가 알아서 커밋 + 푸시한다. "미커밋 · 피드백 대기" 상태를 세션 너머로 남기지 않는다. 피드백으로 바뀌면 다음 커밋이 고친다.

절차에 딸린 규칙(2026-09-18):

- **프리팹을 통째로 만드는 에디터 스크립트는 `Assets/Scripts/Editor`에 `[MenuItem("ZooTycoon/Bake/...")]`로 남긴다.** 재실행이 문서가 아니라 명령이어야 한다. 일회성 조립·조회·검증 스크립트만 scratchpad.
- **규칙 문서 개정은 기능 구현과 커밋을 나눈다.** 구현 중 규칙을 바꿔야 하면 그 자리에서 바꾸되, 커밋은 "규칙 개정"과 "기능"으로 분리한다.
- **기획 회차 상한**: 루프·컨셉 기획은 같은 주제로 2회차를 넘기지 않는다. 2회차 뒤에는 후보 하나를 골라 **첫 기능 = 코어 루프 수직 슬라이스**(별도 프로토타입이 아니라 실제 코드 구조 안에서, 30초 루프만)로 만들고, 판정은 문장이 아니라 플레이로 한다(2026-09-18 개정. 버리는 프로토타입은 만들지 않는다).
- **3분 플레이 판정**: 기능마다 검증 항목 마지막에 사용자가 3분 플레이하고 "끌린다 / 안 끌린다 / 이유" 한 줄을 남기는 항목을 둔다. 판정은 `재미-프로필.md`에 누적한다.
- **연출 원칙 (2026-09-18)**: 기능을 만들 때마다 지킨다. ① 사건의 게임플레이 중요도에 비례해 연출 강도를 정한다 — 일반 행동(자주, 작게·짧게) / 중요한 행동 / 클라이맥스를 구분하고, 설계에 주요 사건마다 강도 한 줄을 적는다. ② 로직(Core 이벤트)만 있고 화면·손맛 표현이 없는 사건을 남기지 않는다. ③ 같은 정보를 효과 여러 개로 중복 전달하지 않는다. ④ 반복해서 보는 연출은 짧게. ⑤ 목표는 화려함이 아니라 플레이어가 원인과 결과를 즉시 이해하는 상태.
- **연출·완성도 중간 점검**: 여러 기능이 쌓였을 때 스킬 `/polish-review`(`.claude/skills/polish-review`)로 게임 전체를 점검하고 우선순위 보고서(아티팩트)를 낸다. 기능마다 돌리지 않는다.
- `진행상황.md`는 세 절(현재 상태 · 다음에 할 것 · 도구 함정) 각 10줄 안쪽. 이력은 커밋·포트폴리오·`설계/00-구현-요약.md`가 갖는다.

규칙을 어길 수밖에 없을 때는 코드에 `// 규칙 예외: <이유>` 주석을 남기고 보고에 적는다. 예외가 반복되면 규칙을 고친다.
