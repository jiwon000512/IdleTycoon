# 코드 규칙

버전 v1.1 · 2026-09-13
목표는 하나다. **규칙이 어디 있는지 항상 알 수 있고, 한 곳을 고치면 한 곳만 바뀌는 코드.** 스파게티(MonoBehaviour에 규칙이 흩어지고, 서로를 Find로 찾고, 상태를 여기저기서 바꾸는 코드)를 구조로 막는다. 사람과 AI 에이전트 모두 이 문서를 따른다. 줄 단위 표기·포맷·오류 처리·이벤트 규칙은 `프로그래밍-규약.md`. 제네릭 템플릿은 스킬 `unity-project-setup/templates/code-rules.md`.

## 2. 계층과 어셈블리

```
UI  ──▶ Game ──▶ Data ──▶ Core ──▶ GameKit.Core   (화살표 = 참조 가능. 역방향·건너뛰기 참조 금지, 단 UI→Core, Game→Core는 허용)
Game, UI ──▶ GameKit.Unity (Manager 파사드)
Tests.EditMode ──▶ Core, Data, UI
Editor ──▶ 전부 (에디터 전용 도구)
```

| asmdef | 폴더 · 네임스페이스 | 역할 | 참조 | 엔진 참조 |
|---|---|---|---|---|
| `ZooTycoon.Core` | `Scripts/Core` · `ZooTycoon.Core` | 게임 규칙·수식·상태 모델·세이브 모델. 외부 경계는 GameKit.Core의 `IClock`, `IRandom`, `ISaveStorage`를 사용. 알림은 C# event | `GameKit.Core` | 없음 |
| `ZooTycoon.Data` | `Scripts/Data` · `ZooTycoon.Data` | JSON 테이블 레코드·검증기. 로드는 GameKit `TableManager`가 하고 파싱된 행을 생성자로 받음 | Core, `GameKit.Core`, `Newtonsoft.Json.dll` | 없음 |
| `ZooTycoon.Game` | `Scripts/Game` · `ZooTycoon.Game` | 유니티 어댑터: 컴포지션 루트(`GameBootstrap`), 틱. 테이블 소스·저장소·시계·난수는 GameKit Manager가 제공 | Core, Data, `GameKit.Core`, `GameKit.Unity`, `UnityEngine.UI`, `Unity.InputSystem` | 있음 |
| `ZooTycoon.UI` | `Scripts/UI` · `ZooTycoon.UI` | View(MonoBehaviour)와 Presenter(순수 C#). 화면 열기·닫기는 GameKit `UIManager` | Core, Game, `GameKit.Core`, `GameKit.Unity`, `UnityEngine.UI`, `Unity.TextMeshPro` | 있음 |
| `ZooTycoon.Tests.EditMode` | `Tests/EditMode` · `ZooTycoon.Tests` | 유닛 테스트 | Core, Data, UI, TestRunner | Editor 전용 |
| `ZooTycoon.Editor` | `Scripts/Editor` · `ZooTycoon.Editor` | 에디터 도구(테이블 검증 메뉴 등) | 전부 | Editor 전용 |

- 폴더 = 네임스페이스 = 어셈블리. 하위 폴더는 네임스페이스에 붙이지 않는다(`ZooTycoon.Core` 안에서 `Gacha/`, `Income/` 폴더로만 나눔).
- Core·Data가 UnityEngine을 쓰고 싶어지면 그것은 설계 오류 신호다. 필요한 것을 인터페이스로 뽑아 Game에서 구현한다(예: 로그가 필요하면 `ILogger`).
- 새 asmdef를 추가하거나 참조를 바꾸는 것은 사용자 승인 사항이다.

## 3. 설계 원칙 (금지와 필수)

**필수**
- 클래스 하나 = 책임 하나 = 파일 하나. 파일 이름 = 클래스 이름.
- 의존은 생성자로 받는다. `GameBootstrap`이 유일하게 `new`로 서비스·프레젠터를 조립하는 곳이다.
- 외부 경계(시간, 난수, 저장, 테이블 텍스트, 로그)는 인터페이스 뒤에 둔다. Core는 `DateTime.UtcNow`, `System.Random`을 직접 쓰지 않는다.
- 상태는 모델(`ZooState`)이 소유하고, 변경은 서비스의 메서드로만 한다. 변경 결과는 `event`로 알린다.
- 숫자는 `game_config.json` 등 테이블에서 온다(`데이터-테이블-규칙.md`). 코드 상수는 형식(포맷 자릿수 등)에만 허용.
- public 표면은 최소로. 기본은 `internal`/`private`. 다른 어셈블리가 써야 할 때만 `public`.
- 불변을 기본으로. 레코드·설정은 `readonly`/init-only. 컬렉션은 `IReadOnlyList<T>`로 노출.

**금지**
- MonoBehaviour 안의 게임 규칙(코인 계산, 확률, 비용 곡선, 레벨 판정 등). MonoBehaviour는 생명주기 훅에서 서비스를 호출만 한다.
- 게임 코드(ZooTycoon.*)의 `static` 가변 상태, 싱글턴(`Instance`), 서비스 로케이터. 예외: GameKit Manager(`UIManager`, `TableManager`, `DataManager`, `EventManager`, `PoolManager`)의 `Instance` 접근은 Game·UI 계층에서 허용한다. Core·Data는 어셈블리 경계로 접근 불가.
- `FindObjectOfType`, `GameObject.Find`, `GetComponentInChildren`으로 의존을 "찾는" 코드. 참조는 주입받거나 `[SerializeField]`로 인스펙터에서 연결한다.
- `Update`에서 게임 로직 폴링. 수입 갱신은 `GameTicker` 하나가 일정 간격으로 `IncomeService.Tick(dt)`를 호출한다.
- UI에서 모델 필드를 직접 대입하거나 저장을 호출하는 것. UI는 Presenter를 통해 서비스 메서드를 호출한다.
- 순환 참조(A→B→A). asmdef가 계층 간은 막지만 계층 안에서도 금지. 이벤트로 끊는다.
- 인터페이스를 위한 인터페이스. 구현이 하나뿐이고 테스트 대역도 필요 없으면 클래스를 그대로 쓴다.
- Manager에 게임 규칙을 넣는 것. Manager는 GameKit 파사드 전용이며 순수 C# 클래스를 감싸 Unity 수명주기만 더한다(`프로그래밍-규약.md` 10장).
- 200줄 이상 클래스, 5개 이상 생성자 매개변수. 넘으면 분리를 검토하고 이유를 남긴다.
- `#region`, 주석 처리된 코드, TODO 없는 임시 코드.

## 4. 계층별 규칙

**Core**
- 결정적이어야 한다. 같은 입력·같은 `IRandom` 시드면 같은 결과. 이것이 테스트 가능성의 근거다.
- 서비스는 상태를 받아 변경하고 결과 객체를 돌려준다(예: `GachaService.Pull(state) → PullResult`). 결과 객체는 `readonly struct`나 불변 클래스.
- 이벤트 이름은 과거형 명사구: `CoinsChanged`, `AnimalPulled`, `ZooLevelReached`.

**Data**
- 레코드는 JSON 필드와 1:1인 불변 클래스. 파생값(확률 등)은 별도 계산 클래스(`GachaTable`)가 만든다.
- 로드는 GameKit `TableManager`가 하고, Data 계층은 파싱된 행(`IReadOnlyList<TRow>`)을 생성자로 받는다. 검증기가 `데이터-테이블-규칙.md` 7장 규칙을 검사해 실패 목록을 돌려준다. 예외를 던지지 않고 결과로 보고한다.

**Game**
- `GameBootstrap`(컴포지션 루트)만 씬에 놓는 MonoBehaviour다. 순서: 테이블 로드·검증 → 저장 로드 → 오프라인 수익 계산 → 서비스 생성 → Presenter 생성·View 연결 → 틱 시작.
- 어댑터(`ITableSource`, `ISaveStorage`, `IClock`, `IRandom` 구현)는 GameKit이 제공한다. 게임 전용 어댑터가 필요할 때만 Game에 만들고 이름으로 역할을 드러낸다(`XxxSource`, `XxxStorage`).
- 코루틴은 연출(숫자 보간, 뽑기 애니메이션)에만. 규칙 흐름을 코루틴으로 쓰지 않는다.

**UI (MVP)**
- View: `[SerializeField]`로 위젯 참조, `Show(...)`/`Set...(...)` 표시 메서드, `event Action Clicked` 같은 입력 이벤트. 계산·분기·상태 보관 금지. Core를 몰라도 컴파일되게 원시 타입·DTO만 받는다.
- Presenter: 생성자로 View 인터페이스와 서비스를 받는다. 모델 이벤트 구독 → View 갱신, View 입력 → 서비스 호출. `IDisposable`로 구독 해제.
- View 하나에 Presenter 하나. 팝업도 같은 구조. Presenter끼리 직접 참조하지 않고 모델 이벤트로 동기화한다.

**Tests**
- Core 서비스·수식은 기획서 표의 숫자를 그대로 테스트 케이스로 옮긴다(예: 6.3 표의 n=10 → 311).
- 테이블 검증 테스트는 실제 JSON을 로드해 7장 규칙을 전부 검사한다.
- 테스트 이름: `대상_조건_기대` (`GachaCost_At10Pulls_Is311`).

## 5. 이름과 스타일

- 식별자 영어, 주석·문서·커밋 한국어. 주석은 "왜"를 적는다. "무엇"은 이름이 말한다.
- 표기는 `프로그래밍-규약.md` 2장(Unity 6판 가이드): `PascalCase` 타입·메서드·프로퍼티, `m_camelCase` private 필드, `s_` static, `k_` 상수, `camelCase` 지역·매개변수, 인터페이스 `I`, 이벤트 발생 `On...`, 핸들러 `Subject_EventName`.
- 접미사로 역할을 드러낸다: `...Service`(규칙 실행), `...Calculator`(순수 계산), `...Table`(테이블 조회), `...Storage`/`...Source`(IO 경계), `...View`/`...Presenter`, `...Ticker`(주기 호출). `...Manager`는 GameKit 파사드에만.
- 4칸 들여쓰기, 여는 중괄호 새 줄, `var`는 우변에서 타입이 보일 때만. 한 줄 120자.
- `public` 필드 금지. 인스펙터 노출은 `[SerializeField] private`.

## 6. 에이전트 작업 절차

1. **설계 목록 먼저**: 기능을 만들기 전에 "계층 / 클래스 이름 / 책임 한 줄 / 의존" 표를 답변에 적는다. 사용자가 이 표만 보고 구조를 승인·수정한다. 기존 클래스 변경도 같은 표에 적는다.
2. Core·Data부터 쓰고 테스트를 먼저 통과시킨다. 그다음 Game 어댑터, 마지막에 UI.
3. 완료 기준(모두 CLI로 확인): 컴파일 오류 0 · 콘솔 오류 0 · `run_tests` 통과 · 플레이 모드 캡처로 화면 확인(UI 작업 시).
4. 보고에는 만든 파일 목록, 테스트 결과, 규칙과 어긋난 부분(있다면 이유)을 적는다.
5. 규칙을 어길 수밖에 없을 때는 코드에 `// 규칙 예외: <이유>` 주석을 남기고 보고에 적는다. 예외가 반복되면 규칙을 고친다.

## 7. 리뷰 체크리스트 (스파게티 징후)

- [ ] MonoBehaviour에 `if`가 두 단계 이상 중첩된 게임 규칙이 있다
- [ ] `static` 필드, `Instance`, `Find...`가 보인다
- [ ] 한 클래스가 계산·표시·저장 중 둘 이상을 한다
- [ ] 같은 숫자가 두 파일에 있다
- [ ] UI 코드가 모델 프로퍼티에 대입한다
- [ ] 이벤트 구독을 해제하지 않는다
- [ ] 클래스가 200줄, 메서드가 40줄을 넘는다
- [ ] 게임 코드 이름이 `Manager`, `Helper`, `Util`, `Common`이다(책임이 불명확하다는 신호. GameKit 파사드는 예외)
