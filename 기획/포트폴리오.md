# 동물원 타이쿤 — 포트폴리오 (AI 활용 · 기술 중심)

목적: 매출과 무관하게 "AI 에이전트와 1인 개발로 모바일 게임을 어떻게 만들었나"를 보여 주는 문서. **기능 하나를 완성할 때마다 4장에 한 절을 추가**한다. 기획 내용은 `동물원-타이쿤-기획서.md`, 절차·규칙은 `코드-규칙.md`가 원본이고 여기는 요약·성과만 둔다.

## 1. 한 줄 요약

Unity 6 · URP · 세로 모바일 방치형 타이쿤. 기획서 작성부터 코드·씬·프리팹·더미 리소스·테스트까지 **Claude Code 에이전트가 Unity 에디터를 CLI로 직접 조작**해 구현하고, 사람은 결정과 확인만 한다.

## 3. AI 활용 방식

### 3.1 작업 절차 (기능 하나 = 세션 하나)

1. **설계**: 에이전트가 `기획/설계/NN-*.md`에 클래스·책임·의존·검증 항목을 쓰고, 결정이 필요한 것은 객관식으로 묻는다. 사람이 확정.
2. **구현**: 에이전트가 한 번에 전부 구현. 스크립트뿐 아니라 **씬·프리팹·게임오브젝트·더미 스프라이트까지 Unity CLI(`run_script`, `recompile`, `capture_game_view`)로 에디터 안에서 생성**한다.
3. **검증**: 에이전트가 1회 실행 — 컴파일 0·콘솔 0·EditMode 테스트·플레이 모드 캡처.
4. **보고**: 만든 것·검증 결과·달라진 점을 짧게. 진행상황·포트폴리오 갱신.

### 3.2 에이전트가 맡은 것 / 사람이 맡은 것

| 에이전트 | 사람 |
|---|---|
| 기획서 초안·버전 관리, 레퍼런스 조사, 수치 초안(비용 곡선·확률·레벨 표) | 장르·루프·시점 같은 방향 결정, 객관식 답변 |
| 설계 문서, 전 코드, 테스트, JSON, 씬·프리팹 조립, 더미 리소스 생성 | 플레이 감각 확인("작동은 잘돼", "원근감이 안 나타나"), 스크린샷으로 문제 제보 |
| 규칙 문서 유지(코드 규칙·데이터 규칙·규약), 세션 인수인계 문서 | 절차 자체를 바꾸는 결정 |
| 커밋 메시지 | 커밋 시점 결정 |

### 3.3 재현 가능하게 만든 장치

- **규칙 문서가 코드보다 먼저**: 표기·계층·오류 처리·이벤트·테스트 규칙을 문서로 두고 에이전트가 grep으로 스스로 검사(`UnityEngine` in Core, `Find`, 한국어 리터럴 0건).
- **UI 문구 전부 `strings.json`**: 코드·프리팹에 한국어 리터럴 금지 → 다국어 대비.
- **더미 리소스 우선**: 에이전트가 단색 스프라이트·프리팹을 먼저 만들고, 사람이 같은 경로에 실제 아트를 덮어쓰면 코드 수정 없이 교체.
- **세션 인수인계 문서(`진행상황.md`)**: 다음 세션이 알아야 할 것만 — Unity CLI에서 겪은 함정(플레이 모드 중 `run_tests` 금지 등)을 포함.

## 4. 기능별 기록

### 4.1 기반 세팅 + GameKit (2026-09-13)

- 기술: asmdef 계층, `.editorconfig`, JSON 테이블 규칙, 세로 고정, 불필요 패키지 제거. 공통 기반을 별도 UPM 패키지(GameKit v0.1)로 분리해 `file:` 참조.
- AI: 초기 세팅 절차를 Claude 스킬(`unity-project-setup`)로 만들어 다음 프로젝트에서 재사용. 규칙 문서 3종을 에이전트가 초안 → 사람이 다듬음.

### 4.2 기능 01 — 부트스트랩과 상단 바 (2026-09-14)

- 기술: 테이블 로드 → 검증 → 상태 생성 → Presenter 조립의 컴포지션 루트. `TableValidator`가 데이터 규칙 7장을 코드로. EditMode 테스트 47개.
- AI: 한글 TMP 폰트가 없어 `초당`이 □로 나오는 것을 캡처로 발견하고 SDF 폰트 에셋까지 스스로 생성. 의존 방향(`UI → Game`)을 구현 중 `Game → UI`로 뒤집고 규칙 문서에 이유를 남김.

### 4.3 기능 02·03 — 가차와 월드 슬라이스 (2026-09-14)

- 기술:
  - 가차: 등급 가중치 × 종 가중치를 누적 표 하나로 만들어 난수 1회(`GachaTable`), 비용 `100 × 1.12^n` 반올림, `IRandom` 경계로 결정적 테스트(`SequenceRandom`). 테스트 케이스 78개.
  - 월드: 처음엔 uGUI 3×3 격자 → 기획 전환으로 **2D 월드 맵**. 동물은 우리 안을 랜덤 목적지로 걷는 개체, 중복 뽑기 = 마리 수 증가(`Level` = 마리 수, 수식 유지).
  - 시점: 쿼터뷰(방향별 스프라이트 부담) 기각 → "우리 단위 원근"(사다리꼴·축소) 구현 → **세로로 쌓으면 소실점이 모순**되는 것을 사용자 스크린샷으로 확인 → **원근 카메라 + 빌보드 카드**로 전환. 깊이 정렬·축소 코드가 사라지고 World가 더 단순해짐.
- AI:
  - 프리팹 4개·씬 오브젝트·더미 스프라이트 15개를 전부 `run_script`(에디터 C#)로 생성. 플레이 모드 없이 `capture_game_view --source camera`로 카메라 프레이밍을 세 번 반복 조정.
  - 기획 방향이 세션 중간에 바뀌었을 때(격자 → 월드), 살릴 코드(Core·버튼·카드)와 버릴 코드(격자 View·대기실)를 분리해 기획서 v0.9·로드맵을 다시 씀.
  - 문제 특정: 스크린샷 한 장에서 "우리마다 소실점이 따로라 인접 원근이 모순"이라는 구조적 원인을 짚고 선택지 3개(원근 카메라 / 원근 포기 / 소실점 공유)와 비용을 제시.

### 4.4 기능 04 — 수입 틱과 GameManager (2026-09-14)

- 기술:
  - `IncomeService.Tick(dt)` 5줄: 초당 수입 × 경과 초 적립 후 레벨 판정. `GameManager.Update`가 `game_config.income.tickSeconds`(1초)마다 호출. 표시 보간 없음.
  - 버튼 남은 시간 = ⌈(비용 − 코인) ÷ 초당 수입⌉, 수식은 `GachaService`에, 문구는 `strings.json`. 갱신은 기존 `CoinsChanged` 구독으로 끝(틱마다 발생).
  - 구조 변경: 컴포지션 루트 `GameBootstrap` → **`GameManager`(MonoSingleton) + 씬 스크립트 `MainScene`**. 씬이 늘어도 상태는 한 곳. `.meta`만 이름을 바꿔 씬 참조를 살렸다.
- AI:
  - 구현 직전 전 스크립트를 과잉 설계 관점으로 리뷰해 12건 -105줄 정리(미사용 API·수동 코루틴 핸들·설정 아닌 설정값 `costBasis` 삭제) 후 기능을 얹음.
  - 설계 단계에서 "매 프레임 틱, 보간 없음"을 제안 → 사용자가 "1초 틱"으로 확정. 틱 간격은 기획 숫자로 보고 JSON(version 4)에 둠.
  - 검증 중 에디터 창이 뒤에 있으면 프레임이 멈추는 것을 `Time.frameCount` 조회로 잡아 `editor_focus`로 해결, 인수인계 문서에 기록.

### 4.5 기능 05 — 동물 데이터와 상태, 웜뱃 (2026-09-14)

- 기술:
  - 동물의 스탯·연출값 7개(시트 경로·프레임 속도·크기·이동 속도·대기 시간)를 `animals.json` version 2로. 프리팹·코드에 종별 숫자 0개.
  - `AnimalActor`는 `AnimalState { Idle, Move }` + `switch`의 명시적 FSM. `SpriteAnimator`(20줄)가 프레임 배열을 순환. Unity Animator 에셋 없이 JSON만으로 새 종이 붙는다.
  - 등급 확률을 "동물이 있는 등급만 정규화"로 바꿔 종이 1개일 때도 표시·수식이 거짓이 아니다.
- AI:
  - 실제 아트 3장(정지·idle 시트·move 시트)을 받아 Unity 자동 슬라이스가 맞닿은 프레임을 합쳐 놓은 것을 meta에서 발견, `ISpriteEditorDataProvider`로 6×1 격자 슬라이스·피벗·PPU를 CLI 스크립트로 설정. 다운스케일된 크기로 자른 첫 시도의 오차(341 vs 362)를 원본 크기 조회로 바로잡음.
  - 더미 8종 삭제로 깨지는 테스트 6개 파일을 웜뱃 숫자로 다시 씀. 프레임 경계 비침은 아트 문제로 분리해 기록.

### 4.6 기능 06 — 관광객 (2026-09-14)

- 기술:
  - 관광객 수를 홍보 단계가 아니라 **초당 수입의 로그**(`min(12, 1 + ⌊log₂(1 + 수입)⌋)`)로 계산하는 순수 함수 `VisitorCalculator`(Core, 테스트 6케이스). 어떤 성장 축이든 수입을 올리면 길에 사람이 늘어 세 축 공통의 시각 피드백이 된다.
  - 길은 우리마다 앞에 깔린 **길 타일의 경계**(`CageView.PathBounds`)가 곧 걷는 영역. 웨이포인트·길찾기 없이 X 방향 직진 + Enter·View·Leave 3상태 FSM. 우리가 늘어도 데이터가 늘지 않는다.
  - 관광객 종류는 `visitors.json`(가중치 선택), 연출 숫자는 프리팹 인스펙터, 게임 규칙 숫자는 `game_config.visitors`. 세 종류의 숫자가 각각 제자리에 있다.
- AI:
  - 인터넷 레퍼런스 14건(Idle Miner Tycoon GDC, 고양이와 스프, Merge Town, AdVenture Capitalist 수학 등)을 조사해 "환생 없음 + 성장 축 3개 + 지점 유지형 2호점"을 근거와 함께 제안, 사용자가 확정(기획서 v0.13).
  - 설계 06의 관광객 수 제안(기본 3 + 단계)이 사용자 답변("수는 획득 가능한 코인에 따라")과 달라 로그 수식으로 다시 설계하고 구현. 더미 실루엣·길·코인 PNG 4장, 프리팹 2개, 씬 연결을 CLI 에디터 스크립트 2개로 생성. Unity 가짜 null(`?? AddComponent`) 실패를 `TryGetComponent`로 수정.
  - 플레이 검증은 리플렉션으로 FSM 상태를 14회 폴링해 View 상태와 0.7초짜리 코인 팝업을 실제로 잡았다(캡처만으로는 놓친다).
- 문제와 해결: 사용자가 "난간이 관광객을 가린다"고 지적. 플레이를 일시정지해 관광객 좌표를 읽고 그 지점을 4배 확대 크롭해 비교하는 방법으로 원인을 특정했다. 카메라 거리 정렬은 9.6유닛짜리 난간의 정렬점이 가운데 하나뿐이라 옆으로 간 관광객을 뒤로 보낸다. 정렬점 Pivot만으로는 가운데만 해결돼, URP 2D 렌더러를 Custom Axis(Z) 정렬로 바꿔 해결. 렌더러 에셋을 텍스트로 고친 뒤 강제 재임포트가 필요하다는 것도 이때 알았다.

### 4.7 구조 정리 06-1 — 리뷰 8건 (2026-09-14)

- 기술:
  - 월드 개체를 `Unit`(공통 몸체) → `Animal`·`Visitor`로 재구성하고, `switch` FSM을 **상태 객체**(`UnitState` → `WalkState`·`WaitState`)로 바꿨다. 두 개체가 "걷기"와 "기다리기" 두 상태를 공유하므로 상태 클래스는 2개뿐이고, 개체는 전이 순서만 적는다. 상태 인스턴스는 초기화 때 한 번 만들어 재사용.
  - 초당 수입의 소유자를 `IncomeService` 하나로(`IncomePerSecond` + `IncomeChanged`). 세 곳이 각자 재계산하던 것을 없애 다음 기능(홍보)의 구독 지점이 한 곳이 됐다.
  - "레벨"이라 부르던 마리 수를 코드·JSON·문구 키까지 `Count`로 통일해 다음 성장 축(별)과의 이름 충돌을 미리 제거. 데이터 변경 절차(기획서 → JSON version 6 → 검증 테스트)를 그대로 밟았다.
  - `FrameCache`(경로당 1회 로드, 번호 접미사 정렬)로 관광객이 1.5초마다 `Resources.LoadAll`을 부르던 비용과 11프레임 이상 시트의 정렬 버그를 함께 제거.
- AI:
  - 코드 3,000줄 전체를 읽고 규칙 문서와 대조해 8건을 순위와 근거로 보고 → 사용자가 "전부 + Unit 상속·State 패턴" 지시 → 코드 20파일·테스트 4파일·JSON 2개·기획 문서 4개를 한 번에 수정. 스크립트·프리팹 이름 변경은 `.meta`를 같이 옮겨 GUID를 유지(씬·프리팹 참조 무손실).
  - 검증은 플레이 모드에서 버튼 3회 호출 후 상태 조회(마리 수·스프라이트 프레임·관광객 수·결과 카드 활성)로 확인. 캡처만으로는 프레임 전환을 못 본다.
- 문제와 해결: 팝업 View를 Presenter에 주입하려면 GameKit `UIManager`에 "열지 않고 얻기"가 없었다. `GetView<T>`를 public으로 여는 한 줄 변경(패키지 저장소).

### 4.8 기능 07 — 우리 꾸미기, 시설 (2026-09-15)

- 기획 전환: 설계 시작 시점에 "우리 해금·맵 확장"이던 07을 사용자가 **"우리는 지점당 하나, 그 우리를 꾸미는 구조"**로 바꿨다. 에이전트가 객관식 5문(꾸미기의 본체·배치 방식·수입 효과·해금 조건·첫 범위)으로 결정을 받아 기획서 v0.16·데이터-테이블-규칙 v1.10·설계 07을 같은 세션에 반영하고 구현했다.

### 4.9 기능 07-1 — 시점 전환, 원근에서 직교 쿼터뷰로 (2026-09-16)

### 4.10 기능 07-2 — 순수 2D 쿼터뷰로 전환 (2026-09-16)

- **AI가 한 일**: "왜 그냥 2D에 안 뿌렸나"라는 질문에 두 방식의 등가성과 차이(변환 코드 vs 방향별 아트, 픽셀 리샘플링, 장르 관행)를 표로 답하고, 레퍼런스 게임들이 순수 2D임을 근거로 추천을 바꿨다. 더미 바닥·길·울타리 PNG를 외부 라이브러리 없이 순수 python(zlib)으로 생성하고, 실제 아트용 프롬프트(눕는 텍스처는 top-down seamless → 에이전트가 평행사변형 변환, 서 있는 물체만 쿼터뷰 각도)를 `아트-프롬프트.md`에 적었다.
- **문제와 해결**: 07-1 검증 중 Unity CLI 파이프라인이 `run_tests` 뒤 멈춰 프로세스를 강제 종료·재실행. 재실행 직후 스크립트를 쓰는 중에 컴파일이 돌아 옛 오류가 콘솔에 남았고, `console_status`의 groundTruth(오류 0)로 구분했다.

### 4.11 기능 07-3 — 타일맵과 1호점 맵 (2026-09-16)

- **기술 포인트**: 눕는 바닥(잔디·흙·길)을 Unity Tilemap(Isometric Grid, 셀 1×0.5)으로 옮기고 타일 64×32 px = 논리 1유닛이 되도록 `Iso` 상수만 0.5/0.25로 바꿨다. Unity의 `CellToWorld`와 `Iso.ToScreen`이 같은 식이라 셀 (x, z) = 논리 (x, z)로 두 좌표계가 하나가 됐다(`GetCellCenterWorld(0,0) == Iso.ToScreen(0.5,0.5)`로 검증). 존은 6×8 타일 프리팹(`ZoneView`), 1호점은 존 10개 + 길 2칸을 타일맵에 미리 칠해 둔 프리팹(`BranchView`)이고 씬에는 인스턴스 하나. 서 있는 것(울타리·시설·동물)은 스프라이트 + 화면 y 정렬을 유지해 타일맵 청크와 정렬 충돌을 피했다. 코드 변경은 World 7파일, Core·테스트 0.
- **AI가 한 일**: 타일맵 채택 여부와 1호점 배치를 아티팩트 두 장(현행 vs 안 B·C 비교, 위에서 본 배치 + 쿼터뷰 렌더링 SVG)으로 그려 논의를 이끌었고, "왜 Unity Tilemap을 안 쓰나"는 오해에 바닥층은 쓰고 서 있는 것만 안 쓰는 이유(청크 정렬·런타임 생성)를 답했다. 타일 더미·울타리 더미는 Pillow로 생성(첫 시도의 폴리곤 가장자리 틈을 행 단위 스팬으로 고쳐 이음새 제거), 에디터 스크립트 한 번으로 임포트 설정·Tile 에셋·프리팹 2개·타일 칠하기·씬 교체를 끝냈다. 캡처에서 발견한 세 가지(타일 틈, 개체가 타일 대비 큼, 울타리 뒤 모서리 X자 교차)를 그 자리에서 고쳤다(정수 좌표 기둥 + 뒤 모서리 기둥 스프라이트).
- **문제와 해결**: PATH의 python이 MSYS2용이라 pip이 없고 pacman은 gcc 의존 충돌. winget으로 Windows Python 3.12를 따로 설치해 Pillow를 쓴다. 아트 생성은 사용자의 ChatGPT 구독으로 로그인된 Codex CLI의 내장 이미지 생성을 명령줄에서 호출할 수 있음을 확인(자물쇠 1장 테스트)해, 이후 리소스는 에이전트가 직접 뽑는다.

### 4.12 기능 08 — 빵집 코어 루프, 손님이 걸어서 사 가는 가게 (2026-09-18)

- **기술 포인트**: 굴(존)을 누르면 가게 화면으로 넘어가고, 손님 동물이 입구 → 좌우 진열대(원하는 빵) → 가운데 줄 → 계산대 웜뱃 → 퇴장한다. 재고가 없으면 참다가 화내며 나간다. 규칙은 Core `ShopSim` 하나가 전부 갖고 **걷는 시간까지 Core가 센다**(진열대까지 = 1.5 + 층 × 0.8초). World는 이벤트를 받아 "경로 길이 ÷ 받은 시간"으로 속도를 맞춰 걷기만 하므로, 화면과 규칙이 어긋나지 않고 오프라인 계산(11)도 같은 시뮬을 화면 없이 돌릴 수 있다. 가게는 **구역 프리팹을 위에서 아래로 쌓은 것**(입구 · 진열 층 × n · 계산대 · 오븐 줄 × m)이라, 빵을 해금해 층이 늘면 한 층을 끼우고 아래를 내린다(굴 확장 연출 + 카메라 이동). 빵 종류 추가 = `breads.json` 한 행. 카메라는 가게에 들어가면 경계만 가게 사각형으로 바꿔 기존 드래그 코드 그대로 세로 스크롤이 된다. 다 구운 빵은 오븐에서 기다리다 진열대에 자리가 나면 옮겨진다.
- **AI가 한 일**: 첫 설계(v0.2)가 줄 게이지·러시·쿵 버튼으로 돌아가는 "HUD 게임"이라는 사용자 지적을 받고, 객관식 네 문항(손님 흐름·플레이어 역할·원하는 빵·업그레이드)으로 의도를 좁혀 v0.3 → 배치 지시 반영 v0.4 → 결정 3개 확정 v0.5로 설계 아티팩트를 갱신했다. 구현은 한 번에: Core 4파일 + 테스트 12개, World 10파일, UI 팝업 공용 베이스(`ListPopupView`) + 굽기·업그레이드 팝업, 더미 스프라이트 14장(Pillow), 구역 4종·가게·손님·HUD·팝업 프리팹을 굽는 `ShopBaker` 메뉴. 플레이 모드에서 도착·줄·계산·화난 퇴장·굴 확장·스크롤 경계·오븐 탭 → 팝업 → 굽기를 상태 조회와 캡처로 확인했다.
- **문제와 해결**: 캡처에서 바닥 점·구역 경계로 초록 배경이 비쳐 보여(반투명 픽셀) 불투명 어두운 색으로 다시 그렸다. 문자열 리터럴을 상수로 바꾸는 일괄 치환이 상수 선언 자체까지 바꿔 순환 정의 컴파일 오류가 났고 선언만 되돌렸다. 도착 4초·계산 1.5초에서는 줄이 1명 넘게 쌓이지 않아, 검증할 때만 실행 중 값을 바꿔 줄 모양을 확인했다(데이터는 그대로).

### 4.13 아트 — 첫 손님 토끼, 시안부터 인게임까지 (2026-09-21)

- **기술 포인트**: 손님 외형이 이제 앞·뒷모습 × 숨쉬기·걷기 4시트다. `Unit.Face`가 화면에서 위로 걸으면 뒷모습, 아래로 걸으면 앞모습을 고르고, 옆으로만 걸을 때는 직전 방향을 유지한다. 대기와 걷기 프레임 속도를 나눠 웜뱃과 같은 2.5·8fps로 맞췄다(`visitors` version 2). 말풍선은 외형 키(스프라이트 높이)에 맞춰 머리 위에 뜬다. 숨쉬기·걷기 프레임은 AI 없이 칸 편집 스크립트가 만들고, 웜뱃 스크립트에 토끼 설정 줄만 더해 공용으로 쓴다(다시 돌려도 웜뱃 결과는 그대로).
- **AI가 한 일**: 후보 4종을 실루엣 기준으로 제안하고, Codex CLI로 시안 3장을 뽑아 격자를 강제한 뒤 실제 가게 캡처 위에 합성한 비교 아티팩트 한 장으로 논의했다. 버전 6까지 같은 URL에서 갱신하며 선택을 좁혔다(앞모습 3장 → "A에 B의 손" 칸 편집 → 손가락 선 제거 → 뒷모습 3장 → 숨쉬기 → 걷기). 숨쉬기·걷기는 페이지 안에서 게임 속도로 재생해 보여 줬다. 적용은 한 번에: 시트 묶기 스크립트, 슬라이스 메뉴(`ZooTycoon/Bake/Import Visitor Sheets`), 레코드·검증·테스트, 방향 전환, 말풍선 높이. 플레이 모드에서 진열대 앞 앞모습, 줄 서기, 계산 뒤 뒷모습 퇴장, 화난 퇴장을 캡처로 확인했다.
- **문제와 해결**: 웜뱃 걷기처럼 귀 전체를 옆으로 밀면 긴 귀가 머리와 만나는 곳에서 외곽선이 끊겨, 귀 윗부분만 미는 `tip` 값을 추가했다. 격자 자동 측정이 시안 C에서 반 주기를 잡아 얼굴이 뭉개졌고, 칸 수를 직접 줘서 다시 맞췄다. 크림색 털이 가게 바닥과 비슷해 묻힌다는 점은 비교 페이지에 적었고, 사용자는 그 점을 알고 A를 골랐다.

### 4.18 굴 격자 — 흙 화면과 좌우로 불어나는 굴 (2026-09-23)

- **AI가 한 일**: 기획서 아티팩트를 v0.1 → v0.5로 다섯 번 고쳤다(잔디 삭제 → 입구를 화면 맨 위로 → 방·통로 삭제와 실행 중 한 장 그리기 → 결정 5개 확정). 「방으로 인식해 통로를 만들지 말고 자연스럽게」라는 지적에 픽셀 모폴로지(닫기·열기)를 격자 꼭짓점 규칙으로 바꿔 O(꼭짓점 × r²)로 줄였다. 구현은 Core 3 파일 신설 + ShopSim·ShopView·스포너·카메라·시트·Baker 개정, 방 배경 4장과 파이썬 삭제, 타일 3장 생성.
- **문제와 해결**: 마스크 꼭짓점 루프가 맨 아래 줄을 빠뜨려 아래 모서리가 안 깎였다(테스트가 잡음) → 줄 상한 +1. 플레이 중 EditMode 테스트를 불러 에디터가 멈춤 → 재시작(함정 목록 규칙 재확인).
- **검증**: EditMode 70/70(BurrowGrid 5·BurrowShape 4 신설, ShopSim 4 개정), 콘솔 0, 플레이 캡처: 진입 직후 화면 전부 흙·입구가 맨 위, (−2,1) 파기 → 둥글게 불어남·ㄱ 자 메움·카메라 이동, 진열대·오븐 놓기, 웜뱃이 옆 칸 오븐까지 심부름, 오른쪽 드래그 태그 3개 표시 후 2초 뒤 사라짐.

### 4.19 손님 동선 — 4방향 A*, 행동 트리, 위치를 가진 규칙 (2026-09-23)

- **기술 포인트**: 걷기를 규칙(Core)으로 옮겼다. `ShopLayout`이 굴 마스크(굴 그림과 같은 것) 위 0.2유닛 격자에서 사물 바닥 자리를 0.3 넓혀 막은 걷는 땅을 만들고, `BurrowNav`가 4방향 A*(꺾을 때마다 벌점 0.6, 이진 힙, 탐색 배열 재사용)로 길을 찾는다. 막힌 곳(계산대 뒤 웜뱃)에서는 가장 가까운 걷는 점으로 곧장 나온다. 손님은 `Mover`가 A* 꺾임점을 walkSpeed로 따라가고, 화면(`ShopCustomer`·`ShopWombat`)은 매 프레임 Core 위치·보는 방향·상태를 읽어 그리기만 한다. 그래서 가게 시뮬을 1초 틱에서 매 프레임으로 바꿨다(행동 트리 단계마다 최대 1초 멈칫 방지). 손님은 순서·선택·반복 마디 셋과 잎 행동으로 된 행동 트리(`Bt*`, `ShopSim.Customers.cs`)로 움직인다: 구멍에서 톡 → 안 가 본 빵 중 가중치 → A*로 진열대 옆자리(예약) → 있으면 집기, 없으면 최대 2초 두리번(그사이 채워지면 바로 집기) → 다른 빵 → 인내(두리번 합계 6초)가 다 하면 「!!」. 줄은 등록기 앞에서 계산대를 감싸는 자리(가로 5 + 왼쪽 아래 3)를 걷는 땅 판정으로 만들고, 계산은 머리가 머리 자리에 선 뒤에만 시작한다.
- **AI가 한 일**: 플레이 모드에서 0.1초마다 손님 발 위치를 기록해 문제를 수치로 먼저 보였다(속도 0.6~3.0, 오븐 10명·계산대/웜뱃 9명·진열대 9명 뚫기, 줄이 입구까지, 품절 대기 겹침 211). 설계 아티팩트 v0.1(결정 6개) → 사용자 답(가로·세로 A*, 행동 트리, 옆모습 아트) → v0.2. 「도착해서 재고를 보고 판단」하려면 규칙이 도착 시각을 알아야 한다는 점에서 길 찾기를 Core로 옮기는 구조를 정했다. 옆모습은 앞모습 사본 더미로 먼저 넣고, Codex로 토끼 옆모습 시안 3장을 뽑아 선택을 받는다.
- **문제와 해결**: 웜뱃 바닥 자리와 계산대 사이 0.3 틈으로 손님 길이 났다 → 웜뱃 자리를 계산대 밑변까지. 줄을 위로 꺾으면 진열대 옆자리와 부딪혀 계산대 왼쪽 아래로 꺾게 했다. 오븐 사건이 매 프레임 나가 시트가 매 프레임 다시 그려질 뻔해, 오븐 사건은 남은 초가 바뀔 때만 내고 진행 막대는 화면이 매 프레임 읽는다.
- **검증**: EditMode 86/86(BurrowNav 6·행동 트리 5·배치 4 신설, 손님 규칙 테스트 전면 재작성). 플레이 관찰 세 가지(보통 30초·붐빔 40초·빵 바꾸기 30초) 모두 걷는 속도 중앙값 2.20, 사물 바닥 자리 안 발 0, 줄 손님이 통로·입구에 0, 같은 자리에 선 두 손님 0, 웜뱃이 계산대 안 0. 빵 바꾸기에서 두리번 9명 → 다른 빵 6명, 화난 손님 0. 콘솔 오류 0.

### 4.20 손님·웜뱃 옆모습 아트 — 턴어라운드 시트 빈칸 채우기 (2026-09-23)

### 4.34 설계 16 — 사건 버스: 선언은 한 곳, 발행은 주인, 구독은 버스 (2026-09-25)

- **기술 포인트**: 클래스마다 흩어진 C# event 21개를 `readonly struct` 사건 16개로 바꿔 `Events` 정적 partial 클래스(Area·Bakery·Plaza 파일)에 모았다. Core는 UnityEngine을 못 보므로 GameKit에 순수 C# `EventBus`를 새로 두었다(처음엔 `EventManager` 싱글턴이 감쌌으나 같은 날 "실무식 싱글턴을 둘지" 장단점을 따져 삭제 — 버스는 게임 상태와 같이 `GameManager`가 만든다). 버스는 `GameManager.Init`이 꺼내 곳·지갑·굴 격자에 생성자로 넣고, 사건은 일이 일어난 객체(계산대·손님·통로·사물)가 직접 낸다. 모든 사건은 첫 필드가 발신자라 구독자가 자기 곳으로 한 줄 거르고, 두 번째 빵집이 생겨도 사건 이름은 늘지 않는다. 곳이 손님·사물 사건을 받아 다시 내던 전달 코드와 나가기·문 콜백이 사라졌다. 사물 하나만 보는 그림(오븐·진열대·웜뱃)은 C# event `Changed`를 그대로 둬 필터가 없다.
- **AI가 한 일**: 「EventManager 하나에서 관리됐으면 한다」는 요청에 세 안(버스만 · 선언까지 한 곳 · 지금)의 장단점을 표로 비교하고, Core가 싱글턴을 못 쓰는 제약과 partial이 어셈블리를 못 넘는 제약을 먼저 짚어 "2안 절충"을 제안했다. 손님 사건을 곳마다 따로 둘지는 사용자에게 물어 결정(곳마다 도착 행동이 달라질 수 있어 따로)했다. GameKit 패키지 테스트를 게임 EditMode에 포함시키는 `testables` 설정도 함께.
- **검증**: 컴파일 0, 콘솔 0, EditMode 128/128(GameKit `EventBusTests` 4: 타입별 전달·해제·구독자 없음·핸들러 안 해제/구독, 게임 `Passed_FromForeignArea_IsIgnored`). 플레이 스크립트: 굽기 → 꺼내기 → 채우기 → 결제(+10) → 업그레이드 2종 튀기기 → 오븐 설치 → 파기 → 광장 오가기, 효과음 3종 재생 시각 확인.

### 4.33 코드 리뷰 R2 — 사용자의 리뷰 기준을 배워 에이전트가 전부 스스로 리팩토링 (2026-09-24)

- **기술 포인트**: R1에서 사용자가 파일마다 준 기준(책임은 주인 객체에 · 개념은 뜻으로 · 무엇을 할 수 있나는 표에 · 파일·개념 줄이기 · 이름 규칙)을 메모리에 정리하고, 그 기준으로 84개 파일과 11개 표를 전부 다시 봤다. 20개 결정(설계 15): 계산대가 줄과 계산 타이머를 갖고(`CounterInteractable.Queue`·`Tick`·`Serve`), 손님은 `Visitor` 베이스(외형·Mover·톡 뛰기) 위에 `BakeryVisitor`(행동 트리와 잎 행동을 스스로)·`PlazaVisitor`(들를 곳 → 문·계단)로 나뉘어 곳에는 손님들 사이의 일만 남았다. 나가기·문 두 클래스 + 인터페이스를 `PassageInteractable` 하나로, `WombatWalker`를 `Wombat.Walk`로, 손 사건에 "어느 사물에서"를 실어 화면의 마지막 오븐 추적 꼼수를 없앴다. 값은 행동이 지갑에서 치르고(굴 격자는 돈을 모른다), 굴 공통 상수는 굴 코드로, 읽지 않던 데이터 칸 7개와 `TotalCoinsEarned`를 지웠다. 게임에 없는 "Shop" 이름을 World·UI·Editor·프리팹에서 뺐다(`BakeryView`·`WombatView`·`VisitorView`·`ControlHudView`, 파일과 .meta를 함께 옮겨 프리팹 참조 유지).
- **AI가 한 일**: 사용자 요청 「저장한 내용과 리뷰 특징대로 스스로 리팩토링」에 따라 질문 → 대안 → 최선을 스스로 정하고 한 번에 구현했다. 큰 이름 바꾸기는 정규식 치환 스크립트로 테스트까지 한 번에 옮기고, 컴파일 오류 3건(손 사건 인자)만 손으로 고쳤다. 코드 지도 아티팩트를 기능별 소통 다이어그램(기능 안의 화살표 + 다른 기능과 이어지는 곳을 모서리에 요약)으로 다시 만들었다.
- **검증**: 컴파일 0, 콘솔 0, EditMode 123/123(파기 값은 행동이 치름·carryCapacity 정수 검증 추가, 굴 격자·지갑 테스트를 새 책임에 맞게 고침). 플레이에서 굽기 → 자동 꺼내기(손 6) → 채우기 → 손님 결제(코인 +10) → 업그레이드 2종 → 오븐 설치 300 → 파기 150 → 광장 나가기·들어오기를 스크립트로 확인, 캡처에서 빵집·광장 그림 정상.

### 4.32 코드 리뷰 R1 — 업그레이드를 행동 하나로, 행동은 팩토리 중첩 클래스 (2026-09-24)

- **기술 포인트**: 사물의 `CanDo`/`Do`와 따로 놀던 업그레이드 장부(`Upgrades`)·`ShopUpgradeTable`·시트 전용 분기를 모두 지우고, 사물에 하는 일을 행동 객체 하나로 모았다. `ActionTable` 행마다 `ActionFactory`가 행동을 만들고, 행동 클래스는 팩토리 안 중첩 클래스로 sim마다 partial 파일(공통 3 · 빵집 7)에 둬 행동이 늘어도 파일이 늘지 않는다. 어느 사물에서 무엇을 하는지는 `InteractableTable.actions`, 어떻게 하는지는 `ActionTable.mode`(auto·manual·sheet)라 버튼·자동·시트 줄이 같은 틀이다. 업그레이드는 `upgrade` 행동 하나 + 사물 행 안의 `UpgradeInfo`, 단계는 곳이 종류별로 세고 그 값의 뜻은 사물이 `UpgradeValue`로 정한다. - **AI가 한 일**: 「상하좌우만 이동」 실험을 UI 한 줄로 넣어 바로 만져 보게 하고, 레퍼런스(같은 장르 My Perfect Hotel·Burger Please, 픽셀 탑다운 Stardew Valley·Zelda LttP, 4/8방향 설계 논의)를 조사해 "자유 이동 + 4방향 그림이 표준"이라 보고하자 사용자가 되돌리기로 했다. 손님 행동은 아트방 세션에 규격(64×72, PPU 80, 시트 허용)을 메시지로 넘겨 시안 3장 → 사용자 선택(점 셋, 더 작고 가로로 넓게 52×36) → 임포트를 병렬로 받는 동안 코드·소리 삭제·테스트를 먼저 끝냈다. 사용자가 중간에 「돌아갈 때 사운드 삭제」를 덧붙여 같은 회차에 넣었다.
- **검증**: 컴파일 0, 콘솔 0, EditMode 128/128(SoundTable 버전·필수 행 테스트를 give_up → pay로). 플레이에서 손님 상태를 0.5초 간격으로 읽어 Looking 동안 말풍선 켜짐·보는 방향 고정·프레임 0→1→2, 나갈 때 꺼짐을 확인하고 캡처로 자리(머리 위)를 봤다.

### 4.26 굴 환경 A2 — 파 내려간 방으로 읽히는 굴 (2026-09-24)

- **기술 포인트**: 방 윗변 안쪽에 지층 띠(40칸)를 세워 평평한 흙 오림이 파 내려간 방으로 보이게 했다. 걷는 바닥 윗변은 그대로 두고 방 윤곽만 띠만큼 올렸기 때문에, 손님 동선·사물 자리·길 찾기는 한 줄도 바뀌지 않았다. 대신 굴 마스크에 띠 행(`WallRow`)을 더하고 길 찾기는 `IsFloor`(방 안이면서 띠가 아님)만 본다. 모서리 둥글리기를 칸 꼭짓점 대신 픽셀 격자점마다 보게 바꿔서, 옆으로 판 칸의 띠가 이웃 바닥과 만나는 안쪽 모서리까지 같은 코드가 처리한다. 지층은 격자 줄 기준으로 샘플해 둥근 모서리에서도 휘지 않고 윤곽에 잘린다. 방 둘레는 8방향 거리 6겹 턱(선·턱 4·선)이다.

- **검증**: 컴파일 0, 콘솔 0, EditMode 91/91(굴 모양 테스트 4개를 띠 규칙으로 다시 씀). 플레이 중 칸을 파서 옆 칸 띠·안쪽 모서리·턱을 캡처. 굽기 부산물인 폰트 에셋을 되돌린 뒤 글자가 빠지는 것을 찾아, 폰트 재임포트 + 스크립트 리로드로 해결했다.

### 4.23 기능 10 — 연출 2순위: 오븐 상태 표시·빵 나르기·효과음 (2026-09-23)

- **기술 포인트**: 이미 있는 Core 사건을 화면이 읽기만 해서 연출을 붙였다. Core에 늘린 것은 업그레이드 하나를 샀다는 이벤트 `Upgraded(id)` 하나다. 오븐 타이머 자리에 빈 오븐 = 오르내리는 화살표(웜뱃이 그 오븐 앞이면 끔), 다 구움 = 빈 원판 + 식빵과 개수. 꺼내면 빵 하나가 오븐 → 머리로 포물선을 그리고 도착해야 층이 늘며, 채우면 머리 → 진열대로 날아간다. 업그레이드는 `shop_upgrades.target`으로 월드 대상(진열대 전부·오븐 전부·계산대)을 튀기고, 새로 놓인 진열대·오븐도 한 번 튄다. 공용 `PressScale`(누르는 동안 0.95배)을 굽기 스크립트가 모든 버튼에 붙인다. 효과음은 새 테이블 `sounds.json`(결제·완료·화남)으로, 소리마다 AudioSource를 따로 두어 결제 연속음만 피치를 올린다(0.1초 안 중복은 건너뜀).
- **AI가 한 일**: 5일 전 점검표의 2순위를 지금 조작(조이스틱)에 맞춰 다시 골랐다 — 탭 거절 흔들기·지상 전환은 빼고, 업그레이드 줄 번쩍·빨간 비용은 이미 있음을 확인. 결정 2개(빈 오븐 표시·사운드 범위)를 객관식으로 받고, 작업 중 아트방이 넘긴 오븐 표시 2장(사용자 선택)으로 빈 오븐 표시를 바꿨다. 더미 효과음 3개는 이미지 도구 없이 Python 표준 라이브러리로 합성(사인 두 번 짤랑·배음 감쇠 종·내려가는 사각파 콧소리).
- **검증**: 컴파일 0, 콘솔 0, EditMode 89/89(효과음 표 검증·파일 존재 6개 추가). 플레이에서 `Time.timeScale` 0.1로 늦춰 날아가는 빵과 튀기기를 캡처·스케일 조회, 채널별 마지막 재생 시각으로 세 소리가 난 것을 확인. 날아가는 빵이 쌓인 층(0.6배)보다 크게 보이는 것을 캡처에서 찾아 그 자리에서 맞췄다.
- **든 물건은 손에**: 사용자 지적(「대부분의 동물은 손이 있다」)으로 든 빵을 머리 위 대신 앞발에서 위로 쌓게 바꿨다. 그림에서 앞발 높이를 재어(웜뱃 발끝 위 0.21유닛, 손님은 키의 약 1/3) 앞모습은 몸 앞, 옆모습은 보는 쪽으로 내밀고, 뒷모습은 몸 뒤에 그린다. 날개를 벌린 펭귄만 머리 위 — 「다른 물건을 들 수도 있으니 데이터로」라는 요청에 `visitors.carryAt`(hand/head) 칼럼을 두었다. EditMode 91/91.
- **다른 세션과 나눠 하기**: 같은 시간 아트방 세션이 정면 식빵·발바닥 코인·오븐 표시를 만들어 임포트하면, 이 세션이 플레이에서 확인해 결과(확대 캡처 경로)를 메시지로 돌려줬다. 새 코인 확인 중 결제 코인이 오븐 뒤로 가려지는(그리는 순서 0) 옛 문제를 찾아 순서와 금액 글자 높이를 고쳤다.

### 4.32 설계 17 — 빈 진열대는 아무 빵, 해금은 오븐 시트로 (2026-09-26)

- **기술 포인트**: 진열대가 생성 시점의 빵 한 종에 묶여 있어(해금 = 그 빵 진열대를 빈 자리에 사기) 「아무 진열대에나 놓기」가 안 됐다. 사용자 요청은 "여러 빵 섞어 진열"이었지만, 결정 축 5개(담는 것·해금·손님 순서·채우기 우선순위·그림)와 후보 3안을 실제 스프라이트 합성으로 비교한 뒤 사용자가 가장 작은 안 1을 골랐다. 진열대 `Bread`를 null 가능으로 바꾸고 첫 `Put`이 정하고 다 팔리면 풀리게 했을 뿐인데, 그 한 줄이 해금 구조를 갈랐다: 빵 해금은 오븐 굽기 시트의 다음 빵 칩(값 = `unlockCost`, 사면 빈 오븐이면 바로 굽기), 진열대는 빈 자리에서 오븐과 같은 가격 곡선으로. `Unlock` 행동·`Locked` 상태는 삭제, `ShelfOf(id)`는 `ShelfFor(bread, from)`(재고 있는 가장 가까운 곳, 없으면 가장 가까운 곳)와 `StockOf`로. 웜뱃은 같은 빵 진열대에 자리가 남았으면 빈 진열대를 안 쓰고(모든 진열대가 식빵이 되는 것 방지), 손님은 기다리는 사이 다른 빵으로 채워진 진열대에서는 집지 않는다. Core가 규칙을 다 가져 World는 `Icon(null)` 한 줄, UI는 문구 셋만 바뀌었다.
- **AI가 한 일**: 「트레이 안에 레이어를 잘 세팅하면 되나」라는 질문에 스프라이트 행별 밝기를 재서 층 바닥면이 7~8px뿐이라 50px 빵이 들어갈 틈이 없음을 숫자로 보이고, 레이어 규약(조각 3개 + anchor)은 되지만 그림이 먼저라고 답했다. 남은 결정 3개(해금 위치·가격 곡선·채우기 우선순위)는 객관식으로 한 번에 묻고 설계 17 문서를 확정받은 뒤 Core 6·UI 2·World 2·JSON 5·테스트 2 파일을 한 번에 고쳤다. 사용자가 플레이 중이라 재컴파일을 멈추고 허락을 받은 뒤 진행했다.

### 4.33 굴 이동 자동화 — 버튼 대신 닿으면 넘어가기 (2026-09-26)

- **기술 포인트**: 빵집 구멍·광장 문은 상호작용 버튼(exit·enter manual)이었다. 표 한 칸(`mode: auto`)으로 바꾸면 끝일 것 같지만, 곳을 옮기면 웜뱃이 상대편 통로 위에 서므로 그 프레임에 바로 되돌아오는 핑퐁이 난다. 통로에 `Armed`를 두고 곳에 들어올 때 끄는 것으로 막았다. 첫 판은 "range 밖으로 한 번 나가야 다시 켜짐"이었는데 사용자가 「굴에 다시 안 들어가진다」— 자연스러운 조작(손을 뗐다 다시 위로 밀기)은 1유닛을 물러서지 않는다. 방향·막힘 조건을 더해 봤지만 사용자의 답은 「동굴과의 거리로만」. 최종은 조건 하나: 통로 앞 띠(바닥선에서 0.25 위, 가로 ±0.75 = 아치 절반)에 들어오면 넘어간다. 들어온 웜뱃은 바닥선(띠 바로 밑)에 서고 누르고 있던 조이스틱을 놓을 때까지 걷지 않으므로(`Wombat.WaitRelease`) `Armed` 같은 상태 없이도 되돌아가지 않고, 굴을 등진 채 선다. 검증기의 "곳 옮기기는 manual만" 규칙과 아이콘 2장은 삭제.
- **AI가 한 일**: 한 프레임 안에서 빵집 틱 → 통로 → Mall 전환 → 광장 진입 → 광장 틱 순서를 따라가 핑퐁이 어디서 나는지 코드를 고치기 전에 짚었다. 재진입 버그는 사용자 동선(위로 민 채 도착 → 놓고 → 다시 위로)을 플레이에서 스크립트로 재현해 range 하나짜리 재켜짐 조건이 원인임을 확인하고 고쳤다.
- **검증**: 컴파일 0, 콘솔 0, EditMode 128/128(왕복 2회 · 바닥선까지는 안 넘어가고 0.25 위에서 넘어감 · 도착 직후 위로 밀어도 제자리에서 아래를 봄 · 놓았다 조금만 밀어도 넘어감). 플레이에서 같은 동선 재현.

### 4.34 설계 18 — 자유 배치와 편집 모드 (2026-09-26)

- **기술 포인트**: 「진열대 한 줄·계산대 한 줄·오븐 한 줄」이 단조롭다는 사용자 판단에서 출발했다. 레퍼런스 9종(Eatventure 고정 슬롯 ~ Kairosoft 인접 콤보 ~ Two Point 프레스티지 ~ Bakery Story 자유 격자)을 조사해 후보 3안을 냈고, 사용자는 자유 배치를 고르고 점수는 막바지로 미뤘다. 구현의 핵심은 「칸 → 자리」 층을 통째로 걷어 내고 사물을 좌표 + 바닥 사각형(`IPlaced`)으로 바꾼 것. 배치 규칙은 `WombatArea.Placement` 한 곳(바닥 안 · 겹침 없음 · 입구 안 덮음 · 작업 자리가 걷는 땅이고 입구에서 길이 닿음)에 두고, 검증마다 후보 사물을 넣은 임시 `BurrowNav`를 만들어 실제 길 찾기로 확인한다. 곳(빵집·광장)은 무엇을 파는지·목록·만들고 없애는 법만 다르다. 바닥 크기·손님 자리·웜뱃 자리·줄 머리·가격은 전부 사물 표(`halfWidth`·`depth`·`spots(role)`·`price`)로 옮겨 `BakeryLayout`의 상수를 지웠고, 줄은 계산대마다 만들어 계산대 여러 대가 됐다. 화면은 놓기·옮기기·치우기를 사건 하나(`LayoutChanged`)로 받고 목록을 객체 키로 동기화한다. 편집 UI는 Presenter가 손가락(카드 끌기·사물 끌기·패널에 놓기·빈 곳 끌기·흙 탭)을 곳 호출로만 바꾸고, 그림자·카메라 팬은 `MainScene`이 월드에 잇는다.

- **사용자 플레이 뒤**: 「계산대가 안 옮겨진다·동물이 못 움직인다」 — 라이브 상태를 스크립트로 조회해 콘솔 예외 0·CanMove 전부 Ok·ThingAt 정상임을 확인한 뒤, 계산대 프리팹 원점이 옛 「계산대 줄 윗변」이라 그림이 논리 위치보다 1.55 아래에 그려진 것을 찾았다(보이는 계산대를 잡으면 빈 곳 → 카메라 팬, 손님 줄·웜뱃 자리도 그림과 어긋남). 원점을 밑변으로 바꿔 다시 굽고, 진열대를 전부 보관했을 때 손님이 null 진열대로 가던 경로도 막았다.

### 4.35 설계 19 — 계산은 자리에 붙어서, 웜뱃 시스템 이동 (2026-09-26)

- **기술 포인트**: 「계산 시작 때 계산대에 붙어 있지 않으면 중앙에 붙기. 미션 가이드도 웜뱃을 움직일 것이니 시스템으로」라는 요구를 손님이 이미 쓰는 `Mover.WalkTo`(A* 길 따라 걷기) 재사용으로 풀었다. 새 코드는 `Wombat.Guide` 한 메서드와 `Walk`의 분기 하나(조이스틱을 놓고 있으면 길을 따라 걷고, 건드리면 길을 지운다)뿐이고, 계산대는 자리 판정(`WombatAtSpot`)을 더해 자리에 있을 때만 타이머를 돌리며 자리 밖·대상·조이스틱 놓음일 때 `Guide`를 부른다. 계산대가 여럿이면 대상(가장 가까운) 계산대에만 붙어 두 대 사이를 오가지 않는다.
- **AI가 한 일**: 설계 문서 없이 코드·테스트·플레이 검증까지 한 번에. 첫 테스트가 실패했는데 원인은 코드가 아니라 단정이었다(`Serving`은 「타이머가 시작됐다」이고 손님이 줄 머리에 선 순간 웜뱃이 아직 자리에 있어 이미 켜져 있었다) → 코인 불변으로 바꿨다. 플레이 검증은 CLI 왕복(0.4초)보다 걷기(0.3초)가 빨라 중간을 못 잡아, 스크립트 안에서 틱을 직접 돌려 경로(위로 한 칸 → 왼쪽 → 아래, 도착 뒤 앞모습)를 확인했다.
- **검증**: 컴파일 0, 콘솔 0, EditMode 137/137(range 안·자리 밖에서 조이스틱을 쥐면 붙지도 계산하지도 않음 → 놓으면 걸어 붙고 걷기 + 계산 시간 뒤 결제, 도착 방향 Down · 시스템 이동 중 조이스틱을 밀면 그 자리에서 그만둠). 플레이: 줄 머리가 선 뒤 웜뱃을 (0.8, 0.3) 옆에 두면 자리로 돌아와 계산 진행.

### 4.36 설계 20 — 상점 카드는 탭, 편집 패널 가독성 (2026-09-26)

- **기술 포인트**: 「배치 UI 가독성 나쁨 · 계산대 아이콘 위치 · 배치 안 됨」 세 줄 피드백. 「배치 안 됨」은 실제 UI 이벤트 경로(EventSystem 레이캐스트·`ExecuteEvents` 끌기)를 스크립트로 재현하던 중 사용자가 「드래그였네, 탭하면 화면 가운데에 생기고 끌어 옮기자」로 정리해 흐름을 바꿨다. 카드는 `IPointerClickHandler` 하나, View는 패널 위 영역의 화면 가운데를 월드 점으로 넘기고, 곳(Core)의 `TryFindSpot`이 배치 격자 고리를 넓혀 가며 가장 가까운 놓을 수 있는 자리를 준다(격자 번호로 계산해 `Snap`과 비트까지 같게 — 더한 좌표는 1ulp 어긋나 모서리 맞닿음 판정이 뒤집혔다). 계산대 아이콘이 위로 붙던 원인은 `Image.preserveAspect`가 RectTransform 피벗 쪽으로 정렬하는 것(피벗 위 → 위로 붙음) → 피벗 가운데. 글자는 9 → 11 굵게, 값은 코인 HUD와 같은 그림자 위 금색.
- **AI가 한 일**: 레이캐스트 진단 스크립트로 카드 중심에서 맨 위 히트를 확인하고, 끌기 시뮬레이션이 실제 `TryBuy`까지 닿는 것을 본 뒤 사용자 결정에 맞춰 카드 끌기 코드(View 이벤트 3개·Presenter 분기)를 지웠다. 새 테스트 첫 실행 실패 두 번은 단정 오류(놓을 수 없는 점을 놓을 수 있다고 가정)와 부동소수 1ulp 문제였고 후자는 Core를 고쳤다.
- **검증**: 컴파일 0, 콘솔 0, EditMode 138/138(TryFindSpot: 겹치는 자리 → 가장 가까운 빈 자리, 빈 자리는 그대로, 굴 밖은 false). 플레이: 편집 진입 세로 캡처(글자·값·아이콘 정렬), 진열대 카드 탭 → 코인 350→200·사물 +1(화면 가운데 근처), 코인 부족한 오븐·계산대는 변화 없음.

### 4.37 설계 21 — 점원: 손님 뼈대를 쓴 일꾼, 월급 협상 타이밍 바 (2026-09-26)

- **기술 포인트**: 기획은 객관식 6회(범위 → 월급 방식 → 종류 → 빵 선택 → 고용 UI → 팝업 구조)로 좁힌 뒤 시안 아티팩트에서 사용자가 흐름을 세 번 뒤집었다(뽑기 → 후보 선택 + 월급 협상, 3명 카드 → 5명 세로 줄 + 고용할까 창, 능률 % → 일머리 1~100에 높을수록 드묾). 코드는 새 개체 없이 `Clerk : Visitor` — 외형(VisitorTable `role` clerk)·걷기·톡 뛰기·화면(`VisitorView`)을 손님과 공유하고, 할 일만 행동 트리 두 그루(일·퇴장). 오븐 점원은 웜뱃 행동 클래스(`TakeOut`·`Fill`)를 `WombatArea.TryDo`로 그대로 부르고, 계산은 계산대가 `clerk.Working`을 보고 돌린다. 협상은 순수 C# `Negotiation`(표시 왕복 → 멈춘 색 → 가중치 난수 → 금액 난수)이라 EditMode에서 구간·확률·시간 초과·속도를 전부 고정 난수로 검증. 점원 외형은 팔레트 교체 스크립트(털 5색만, 외곽선·눈 유지)로 시트를 뽑고 표에 행 하나 더하면 늘어나는 구조.
- **AI가 한 일**: 실제 남부 털코웜뱃 색을 검색해 팔레트 D·E를 더하고 빵집 캡처 위 합성으로 비교. 첫 테스트 실패 3건(0.9² 암산 오류, 오른쪽 이동이 계산대 바닥과 겹침, 서 있는 점원이 옮겨진 자리를 따라가지 않음)을 원인별로 고쳤고 마지막 것은 Core `Clerk.Repath`를 「걷는 중이거나 자리 목표면」으로 넓혔다. 사용자 플레이 첫 버그(점원이 일하다 사라져 구멍에서 다시 나옴)는 `BtRepeat`이 자식 성공을 그대로 돌려 「들어오기 → 반복」 순서 전체가 끝나고 다시 시작한 것 — 들어오기를 순서 밖으로 빼고 바퀴 하나를 계속 틱하게 바꾸고, 1분 동안 톡 뛰기·구멍 위치가 다시 없음을 단정하는 테스트를 더했다. 둘째 버그(오븐 점원 좌우 떨림)는 진열대가 가득 찰 때 바퀴가 매 프레임 되돌아 자리로 다시 걷기를 부른 것 + A*가 격자 밖 자리에서 격자 점을 거쳐 돌아오는 한 걸음 — `Mover.WalkTo`의 「이미 그 자리면 길 없음」과 점원의 「진열대 자리가 날 때까지 서서 기다리기」로 고치고 5초 동안 위치가 1e-4 안에 머무는 테스트를 더했다. 플레이 검증은 버튼 `onClick.Invoke`로 흐름을 밟는 스크립트(열기 → 고용 → 선택 → 협상 → 탭 → 해고)로 세로 캡처 10장. 협상 장면의 후보가 작게 보인 원인(시트 칸 여백 + preserveAspect)은 두 그림을 스프라이트 픽셀 ×2 고정으로.

### 4.38 설계 22 — 점원 깨우기, 공통 대화·말풍선 부품 (2026-09-26)

- **기술 포인트**: 「놀고 있는 점원에게 가서 상호작용하면 정신 차리기 + 대화 시스템 + 새 이모지 말풍선」 요청을 기획 초안 아티팩트(흐름·범위·결정 5개)로 정리하고 객관식으로 확정한 뒤 설계로 바꿨다. 말풍선은 Core 상태 하나(`BubbleState`: 표 행·경과·남은 초)를 손님·점원·웜뱃이 같이 갖고 화면은 읽기만 하는 구조라, 기존의 세 가지 표현(점 셋 시트·♥ 글자·!! 글자)이 표 한 장으로 합쳐졌다(손님 화남 「!!」는 옮기다 되살아난 것을 사용자가 잡아 다시 뺐다). 딴짓 중인 점원은 `ClerkInteractable`로 사물 목록에 들어가 기존 상호작용 틀(대상·range·manual 행동·버튼 아이콘)을 그대로 타고, 대화는 순수 C# `Dialogue`가 표의 줄을 시간 간격으로 사건으로 내어 화면이 말하는 이의 머리 위에 띄운다(조작을 막지 않음). 수다는 「딴짓 중인 다른 점원 옆으로 가서 마주 봄」 한 규칙으로 끝냈다.
- **AI가 한 일**: 이모지 시트·깨우기 아이콘은 아트방 전에 스크립트 더미(기존 말풍선 틀 위 2px 글리프)로 만들어 파이프라인(시트 임포트 52px·BubbleTable 칸 번호)을 먼저 굳혔다. 테스트에서 난수 순서(후보 5명 + 고용 뒤 채움 + 손님 빵 고르기)가 섞여 산책/멍이 뒤바뀌는 것을 보고, 순서에 기대는 대신 표 값(산책 확률 0)으로 결정성을 만들었다.
- **피드백 반영**: 「딴짓은 일머리에 영향, 1분도 넘을 수 있다」「딴짓 중 광장에 나가 놀 수도 있다」 두 줄에 외출 딴짓을 더했다. 빵집 점원은 구멍 안(보이지 않음)에 남고 광장이 같은 외형의 손님 그림을 세워 점원의 말풍선 상태를 공유하므로, 광장에서도 같은 상호작용(「?」·깨우기·대화)이 코드 추가 없이 돈다. 돌아옴·해고 신호는 사건 세 개(나감·돌아오라·들어왔다)로 빵집과 광장이 서로를 모른 채 주고받는다.
- **UI 폰트(같은 날)**: 「점원 글씨가 얇다」 → 정자체는 갈무리 9·11·14 모두 1px 획이라 한 굵기로 통일했더니 「다 똑같아졌다」 반려. 2px로 굵히니 「굵은체와 너무 비슷하다」, 아틀라스에 1px 반투명 그림자를 심으니 「혼자만 그림자라 어울리지 않는다」. 세 시도 뒤 정자체는 원래 1px로 두고, 얇아 보이는 원인이 글자가 아니라 「·」로 이어 붙인 긴 보조 글이라는 쪽으로 옮겨 점원 UI 폴리싱(칸 나누기)으로 이어졌다. 굽기 단계 아틀라스 가공(`Embolden`·`Shadow`)은 코드에서 지웠다.
- **점원 UI 폴리싱(같은 날)**: 사용자 원칙 「한 글에 정보 하나, 「·」로 잇지 않는다」를 받아 아트방 절차로 진행했다. Codex에 지금 팝업 캡처를 참조로 주고 레이아웃 시안 3장(두 줄 카드·칸 표·명찰 카드)을 뽑아 비교 페이지로 검수 → 사용자가 셋의 장점(명찰 틀·붉은 일머리 게이지·표)을 골라 2차 3장 → D1 확정 + 버튼 비율 지시. 굽기는 목업을 베끼지 않고 UI 규칙 숫자(1 UI px = 4px, 팔레트, 부품 크기)로 `UIBaker`에 조립했고, 두 칸 표는 `ClerkStatView` 부품 하나를 자리 줄·후보 줄·고용할까 창이 같이 쓴다. 첫 굽기 캡처에서 배지 글이 표에 가려 두 글자(근무·딴짓·외출·비었음)로 줄였다.
- **시안 그대로 굽기(같은 날)**: 조합으로 고른 D1 시안을 9-slice 부품으로 흉내 내 구웠더니 「시안이랑 다름, 퀄리티가 안 좋음」 반려. 「웜뱃 사진·폰트 빼고 100% 같아야 한다」를 받아 시안 그림 자체를 원본으로 삼았다: FFT로 픽셀 격자(4.45px)를 재서 211×375칸으로 줄이고, 칸 단위 색 구간 스캔으로 부품 좌표를 잰 뒤 16조각(패널·카드·초상 틀·배지 선/채움·표·게이지·버튼 3상태 등)을 칸 좌표 그대로 잘라 `make_clerk_ui.py`로 굽는다(글자 칸은 비우고, 둥근 모서리 밖 크림은 가장자리 flood fill로 투명). 배치도 시안 칸 수(한 칸 = 캔버스 5px)라 위치·크기가 시안과 같다. 이어 받은 다듬기 요청(초상 180px + 틀 마스크, 흰 찌꺼기, 이름 간격, 버튼 두께·가운데, 빈 틀 탭 = 고용)을 같은 흐름에서 고쳤다.
- **버그(같은 날)**: 「노는 점원을 깨웠더니 돌아가면서 다시 노는 상태」 → 광장에서 깨운 점원이 빵집에 닿을 때까지 딴짓으로 남아 광장이 매 프레임 「?」·「♪」를 다시 그리고 깨우기 버튼도 남던 것. `Idling` = 딴짓 && !돌아오는 중으로 정의를 좁히고, 구멍에 뛰어드는 중 깨우면 광장에 가지 않고 바로 나오게 했다. 재현 테스트 2개(돌아가는 30프레임 동안 딴짓·말풍선·버튼 없음, 뛰어드는 중 깨우기) 추가.
- **검증**: 컴파일 0, 콘솔 0, EditMode 171/171(OutingTests 6: 일머리 1이면 1분 넘게, 외출 → 광장 그림·사물 → 시간 뒤 복귀, 광장에서 「?」·wake 버튼·대화 줄 → 복귀, 외출 중 해고. ### 4.40 UI 공용 조각 정리 — 한 역할 한 조각, 규칙 문서화 (2026-09-27~28)

### 4.52 숨쉬기 · 딴짓 — 머리만 까딱이던 서 있기를 몸 전체와 종마다 다른 버릇으로 (2026-09-29)

### 4.53 빵집 소품 C — 시안 세 벌을 게임에 끼워 고르고, 시점은 칸 무늬로 지키다 (2026-09-29)

Codex는 말로 평행 투영을 시켜도 판을 사다리꼴로, 기둥을 벌어지게 그려서, 계산대 통나무는 칸 무늬 스크립트로 직접 그리고(윗면 깊이는 숫자 하나) 진열대는 윗면 · 앞면만 보이는 회색 블록아웃 그림을 시점 참조로 줘서 뽑았다. 그림에 갇힌 흰 바탕(판 사이 틈)은 둘레가 어두운 흰 덩어리로 가려 투명하게 한다. 오븐 불빛은 새 몸통의 아궁이 칸에서 다시 계산하고, 진열대 빵은 밑이 아랫판에 앉도록 빵 키에 맞춰 높이를 정한다.

### 4.54 웜뱃 똥 — 걷는 땅은 그대로 두고 손님 길찾기에만 원을 건다 (2026-09-29)

- **문제**: 사용자 원안 「웜뱃은 작은 네모 똥을 싸고, 청소해야 하며, 똥으로 길이 막히면 손님은 돌아간다」. 아케이드 방치형의 「치우기」 축(손으로 하던 잡일 → 나중에 직원에게)을 빵집에 얹되, 걷는 땅 격자 · 줄 자리 · 서는 자리를 흔들지 않아야 했다.
- **기술 포인트**: 똥은 딴짓 점원처럼 곳이 목록을 맞추는 사물(`PoopInteractable`)이라 대상 고르기 · 버튼 아이콘 · 튀기기는 기존 코드가 그대로 해 준다. 손님 쪽은 웜뱃 비켜 가기가 쓰던 「피할 원 하나」를 A* 탐색의 원 목록으로 넓혀 손님 땅(`BakeryLayout.Nav`)에만 건다 — 점원 · 웜뱃은 다른 땅이라 밟고 지나간다. 탐색마다 시작점 기준 둘레(지금 거리 − 0.01까지)를 다시 재 이미 둘레 안에 선 손님도 걸어 나온다. `Mover.WalkTo`는 둘레 때문에만 길이 없을 때를 가려(둘레를 무시하면 닿는다) 멈추고 false를 돌려주고, 손님은 걷던 행동 트리 잎을 실패시켜 기존 「빵을 못 찾음」 가지로 넘어간다(🤢, 줄에서 빠지고 든 빵은 버림). 나가는 손님은 둘레를 무시한 길로 지나가 가게가 멈추지 않는다. 똥은 걸은 거리 10유닛마다 25%로 떨어지고(순간 이동은 세지 않음), 숫자는 전부 `BakeryConfigTable`.
- **AI가 한 일**: 원안에서 갈리는 네 가지(막힘 규칙 · 치우는 법 · 누가 싸나 · 자동화 범위)를 객관식으로 묻고, 시작 배치 좌표로 「계산대 옆 통로 걷는 폭 1.8 = 둘레 지름 1.0 두 개면 막힘」을 그려 설계 페이지로 확인받았다. 다른 세션이 Unity와 같은 파일을 쓰는 동안은 git worktree에서 코드를 쓰고 패치로 옮겼다. EditMode 16개(한쪽 통로가 막히면 반대쪽으로, 둘 다 막히면 🤢 포기, 나가는 손님은 지나감 등)와 플레이에서 통로를 막아 여우가 빵을 버리고 돌아가는 장면, 치우기 버튼으로 범위 안 똥만 사라지는 것을 캡처로 확인하고, 포기한 손님이 빵을 계속 든 채로 보이던 뷰 버그를 그 자리에서 고쳤다.

### 4.55 밀 농사 — 곳 둘을 가정한 코드를 곳 N개로, 빵은 레시피로 (2026-09-29)

- **문제**: 사용자 원안 「광장에서 이어지는 빵집 같은 굴에서 밀을 기르고, 그 재료를 조합해 빵을 굽는다(빵마다 조합이 다르다)」. 필요한 것은 ① 광장의 두 번째 문과 굴 ② 인벤토리 ③ 밀 농사 ④ 굽기를 아이템 조합으로. 그런데 `Mall`·`WorldManager`·배경음악·편집 그림자는 모두 「빵집 아니면 광장」 두 곳을 가정하고 있었다.
- **기술 포인트**: 곳에 id(`WombatArea.Id`)를 주고 통로 사물이 가는 곳 id를 갖게 해 `Mall`은 id로 곳을 찾는다. 들어서는 자리는 온 곳이 정한다(`EntranceFrom` — 광장은 농장에서 오면 농장 문 앞), 편집 배치가 막으면 안 되는 문은 곳마다 여럿(`Doors`). 월드는 곳 화면 공통 계약(`IAreaView`)을 두어 `WorldManager`의 두 갈래 분기 다섯 곳을 곳 → 화면 사전 하나로 바꿨다. 농장은 파지 않는 방(`BurrowShape.Room`, 광장과 공용)에 밭(`PlotInteractable`, 기존 배치 규칙 그대로 사고 옮김)을 놓고, 심기는 버튼 행동 · 거두기는 auto 행동이라 대상 고르기 · 버튼 아이콘 · 자동 실행은 기존 곳 코드가 그대로 한다. 거둔 밀은 들지 않고 창고(`ZooState` 재료 사전)로 가고, 오븐은 굽기를 시작할 때 레시피(`BreadTable.ingredients`)만큼 한 번에 꺼낸다(모자라면 아무것도 빼지 않음). 모자라면 굽기 칩이 새 상태(`Lacking`)로 잠기고 오븐 점원은 빈 오븐 앞에서 「…」를 띄운 채 재료가 들어올 때까지 다시 굽는다. 숫자(밀 20초 · 3개, 레시피 2·3·4, 밭 100 · ×2 · 최대 6)는 전부 표.
- **AI가 한 일**: 원안에서 갈리는 네 가지(레시피 방식 · 농사 조작 · 창고 표시 · 농장 여는 때)를 객관식으로 묻고 나머지는 기본값(들고 다니지 않음 · 재료 매매 없음 · 밭은 편집 모드에서 구입)으로 진행해 보고에 적었다. 테스트가 재료 때문에 멈추지 않게 테스트 표는 시작 재료를 넉넉히 두고, 농장 테스트 7개(문 오가기 · 심기 → 자람 → 지나가며 거두기 · 밭 사기 · 광장 장식이 농장 문을 막지 못함 · 레시피 부족 · 창고 전부 아니면 없음)와 점원 「…」 대기 테스트를 더했다. 플레이에서 광장 농장 문 → 농장 → 새싹 · 줄기 · 금빛 밀 → 「+3」 팝업과 상단 바 10 → 13, 굽기 칩 레시피와 밀 0일 때 잠긴 칩, 밭 구입(350 → 250, 카드 200)을 캡처로 확인하고, 빈 밭 화살표가 너무 높이 뜬 것을 그 자리에서 낮췄다.

### 4.56 창고 화면 — 늘어날 재료를 상단 바가 아니라 칸 격자로 (2026-09-29)

- **문제**: 설계 25에서 재료를 상단 바 코인 옆 알약으로 보였으나, 사용자 판단은 「재료가 늘어날 것이라 상단 바에 더하는 방식은 맞지 않다. 점원 버튼 아래 인벤토리 버튼과 화면이 필요하다」. 화면은 칸 격자이고, 처음에는 아무것도 고르지 않은 채 칸을 누르면 별도 정보 창에 그 재료의 정보 · 획득처 · 사용처가 나와야 했다.
- **기술 포인트**: 새 표 없이 있는 표로 답한다 — 칸은 `ItemTable` 행 순서, 획득처는 그 재료를 거두는 `CropTable` 행(밭 · 자라는 초 · 한 번에 몇 개), 사용처는 레시피에 그 재료가 든 `BreadTable` 행. 재료 설명만 `ItemTable.desc` 한 칸을 더했다. 프리팹은 버튼 · 딤 · 제목 · 닫기를 점원 팝업에서, 칸은 사물 시트 칩에서, 획득처 · 사용처 묶음 틀은 사물 시트 줄에서 복사해 조립해 공용 조각이 한 벌로 남는다. 정보 창은 점원 팝업의 「고용할까」 창처럼 창고 패널 위 딤 + 틀이고, 두 틀 모두 내용에 맞춰 늘어난다(세로 레이아웃 + 크기 맞춤). 월드 그림은 한 칸 = 정수 배로 얹는다. 열린 동안 재료가 들어오면(`ItemsChanged`) 칸과 정보 창의 개수가 바로 바뀌고, 편집 모드에서는 점원 버튼처럼 숨는다.
- **AI가 한 일**: 질문 창 답이 전달되지 않은 채 「ㅇㅇ」만 받아 권장안(장식 · 연출까지)으로 진행하다가, 사용자가 「농사는 장식이 아니라 방식의 문제」라고 바로잡아 장식 공용화 · 농장 소품 작업을 커밋 전에 모두 되돌리고 창고만 남겼다. 처음 만든 판은 첫 칸을 고른 채 격자 아래에 설명을 붙였는데, 사용자가 「기본값이 선택되는 구조가 아니고 별도 정보 UI가 있는 구조」라고 해 정보 창으로 나눴다. 플레이 캡처로 격자 · 정보 창과 열린 채 밀이 들어올 때 개수가 바뀌는 것(10 → 13개), 정보 창을 닫으면 격자로 돌아오는 것을 확인했다.

### 4.57 칸 밭 — 빵집 전용이던 굴 파기를 굴 공용으로 빼고, 밭을 사물이 아니라 판 칸으로 (2026-09-30)

- **문제**: 농사 기획 3회차(뼈대)에서 「밭은 놓는 사물이 아니라 땅 하나(칸)를 농사 토지로 만드는 방식」과 「농장은 문 하나 아래로 층을 파 내려가는 구조(C)」가 정해졌다. 설계 25의 밭은 편집 모드에서 사서 놓는 사물이었고, 굴 파기(격자 · 파기 사물 · 시트 행동 · 값 표식 · 흙덩이 연출)는 전부 빵집 클래스에 박혀 있었다.
- **기술 포인트**: 파기를 굴 공용으로 뺐다 — `BurrowGrid`는 시작 칸 · 비용 곡선 · 층 범위(`CellBounds`)를 곳에서 받고, 칸 ↔ 좌표 계산은 `CellMetrics` 하나를 빵집 · 농장 배치가 같이 든다. 파기 사물은 격자만 알고(`DigInteractable.Grid`), 프론티어에 맞춰 두는 묶음(`DigSet`)과 값 표식 · 연출(`DigView`)을 두 곳 화면이 같이 써서 빵집에 남은 파기 코드는 「무엇을 파나」뿐이다. 편집 모드의 흙 탭은 곳 공통 `DigAt`, 굴 파기 시트는 대상의 곳(`Interactable.Area`)에서 연다. 농장은 판 칸(입구 줄 제외)마다 밭 사물 하나가 흙 → 갈기(버튼, 고정 값) → 밭 → 심기 → 익음 상태를 가지며, 거리가 칸 사각형까지(안이면 0)라 칸에 서면 대상이 되고 익은 밭은 발이 들면 거둔다. 밭은 걷는 바닥이라 막는 사각형이 없고, 층이 다 차면 파기 대상이 없다(계단은 설계 32). 앞으로 올 굴(낚시터 · 목장 · 농장 2층)도 같은 조각을 든다.
- **AI가 한 일**: 설계 페이지에 코드 설계 · 데이터 · 테스트 · 검증 항목 · 결정 3개(흙 → 밭은 한 사물 · 갈기 값 고정 · 시작 2×2 + 밭 2)를 적어 확인받은 뒤 한 번에 구현했다. 테스트는 격자 층 범위 1개와 농장 6개(시작 상태 · 파기 → 갈기 → 심기 버튼 순서와 코인 부족 · 밟고 거두기와 옆 칸에서는 안 거둠 · 밭이 길을 막지 않음 · 편집 카드 없음과 흙 탭 · 층 상한)로 바꿨다(220 → 225). 플레이는 검증 스크립트로 상태 값(코인 350 → 250 → 200, 밀 10 → 13, 판 칸 4 → 5)과 캡처(시작 밭 2칸 · 갈기 값 표식 · 익은 밀 · 편집 모드 표식과 안내 · 빵집 편집 회귀)를 확인하고, 갈기 표식이 그 칸에 선 웜뱃에 가리는 것을 칸 윗변 · 모든 그림 위로 옮겼다.
- **QA(같은 날, 상용 기준 · 연출 집중)**: 사용자가 QA 테스터 역할을 시켜 농장을 캡처 열두 장으로 훑었다. 누가 봐도 고칠 것 여덟은 바로 고쳤다 — 굴 파기 시트가 농장에서는 걸어가도 안 닫히고 갱신도 안 되던 빵집 전용 필터(대상의 곳 기준으로), 코인이 모자라도 켜지던 갈기 버튼(편집 카드 · 시트 줄처럼 꺼짐), 갈기 · 심기에 연출이 없던 것(파기와 같은 흙덩이 · 톡 튀기), 익은 밭 표시 없음(오븐 다 구움 표시 재사용), 빈 밭 화살표가 칸 경계에 뜨던 것(칸 가운데), 타이머 · 표식이 웜뱃 얼굴을 덮던 것(세계 깊이로 정렬), 거두기 「+3」이 얼굴 위에서 시작하던 것(머리 위). 방향이 갈리는 것(밭 위에서 삽 버튼이 안 뜸 · 판 흙 칸이 바닥과 같음 · 빈 편집 패널 · 카메라 프레이밍)과 아트 시안(흙판 · 작물 · BGM)은 선택지로 보고했다.

### 4.58 농장 그림 · BGM · 창고 다듬기 — 시안을 사람 없이 고르고, 캡처로 다시 훑다 (2026-09-30)

- **문제**: 칸 밭은 그림 · 소리가 더미였고 창고 칸은 아이콘이 작고 개수 글자가 떠 있어 「조잡한 느낌」이었다. 사용자는 「시안도 네가 고른 것으로 농장을 완성한 뒤 전체 느낌을 보고 리소스 하나씩 피드백하겠다」며 자리를 비웠다.
- **기술 포인트**: 흙판은 Codex 시안 셋 중 이랑이 칸 이음새 없이 이어지는 soil_b를 골라 칸 단위(270×192)로 줄였고, 밀은 한 줄 그림(120칸 폭) 하나를 반쪽 둘로 잘라 칸의 이랑 셋에 번갈아 얹어(`_단계_반쪽`, 13 · 21 · 26칸) 발끝 기준 깊이 정렬로 웜뱃이 사이를 지나게 했다(`make_farm_art.py`, 팔레트 임계 · 흰 잡티 제거). BGM은 들을 수 없으니 `metrics.py`로 수치(튀는 음 99퍼센타일 · 스펙트럼 무게중심 · 3kHz 위 비율)를 재서 farm_c(6.3dB · 310Hz)를 고르고 루프 후보 넷(8 · 12 · 16 · 20마디)을 남겼다. 창고 칸은 아이콘 5배(한 칸 = 캔버스 10px), 개수는 `CoinPill`과 같은 틀의 진갈색 알약 배지(글자 폭에 맞춰 늘어남, 빈 칸 숨김), 열린 채 개수가 바뀐 칸은 `UiFx.Pulse`로 한 번 부푼다.
- **AI가 한 일**: 연출 QA 2차로 농장 · 광장 · 빵집을 캡처 스무 장으로 다시 훑었다(진입 · 갈기 · 심기 · 자람 · 익음 · 밟고 거두기 · 편집 · 파기 · 시트 3종 · 점원 팝업). 고친 것은 편집 패널의 안내 글 · 완료 줄이 9-slice 윗 테두리(8칸)에 붙어 있던 것 하나(빵집 · 농장 둘 다, 농장 한 줄 패널은 카드 줄만 뺀 높이). 흙덩이가 첫 몇 프레임 한 덩어리로 보이는 것은 앞선 시각으로 놓는 수정을 시도했다가 효과가 작아 되돌렸고, 점원 팝업 아래 절반이 비는 것 · 새싹 초록이 팔레트보다 선명한 것은 선택지로 남겼다. 리소스마다 시안 셋 · 고른 것 · 게임 캡처 · BGM 후보를 한 페이지에 모아 사용자가 하나씩 판단하게 했다.

### 4.59 농장 피드백 2차 — 밭을 칸 안쪽 몸통으로, 표시 · 소리 · 두 팝업을 지적대로 (2026-09-30)

- **문제**: 사용자가 리뷰 페이지를 보고 여덟 가지를 짚었다 — 흙판 가장자리가 네모라 땅과 구분이 없다, 싹 자리가 이상하다, 농장에 들어가자마자 거둬져 무슨 일인지 모른다, 완료 표시가 작물에 가려지고 빵 모양이다, 걸음 소리가 없다, 빵집 소리가 농장에서도 들린다, 창고 사용처 셋째 줄이 어긋난다, 점원 팝업 요약이 목록 사이에 있고 아래가 빈다. 밀 아이콘은 옛 리소스 같다고 했다.
- **기술 포인트**: 「들어가자마자 거둠」은 밭을 줄여 여러 개 두자는 사용자 고민에 세 안(칸 안쪽 몸통 + 연출 · 한 칸에 작은 밭 4개 · 버튼 거두기)을 내고 첫 안으로 갔다: `FarmConfigTable.fieldInset`(0.25유닛)만큼 칸 둘레를 여백으로 두고 `PlotInteractable.IsUnderfoot`로 거두기 auto 행동을 몸통 안에서만 허락한다(대상 고르기는 칸 그대로라 심기 버튼은 그대로). 흙판은 시안을 줄이던 것을 그만두고 같은 팔레트로 직접 그린다 — 여백은 투명, 테두리 2칸, 작물 줄 셋의 밑변 자리에 고랑 띠. 작물 줄 그림은 잉크가 적은 끝을 잘라 104칸으로 몸통에 맞추고 새싹 · 줄기는 HSV로 채도 · 밝기를 눌렀다. 표시는 오븐 원판을 바탕으로 초록 부채꼴 16장과 밀 이삭 원판을 만들어 칸 윗변 위 · 모든 그림 위에 둔다. 소리는 `WorldSound`가 `Mall.Active`로 곳에 매인 사건을 거르고(오븐 · 진열대 상태 사전은 곳 밖에서도 따라가 돌아왔을 때 헛소리가 없다), 발소리는 걷기 프레임 가운데 몸이 내려앉는 두 칸(`m_walkBob` −1)에 낸다. 창고 사용처는 격자를 세로 목록 + `ScrollRect`(세 줄 창)로, 점원 팝업은 요약 줄을 목록 밖 바닥에 고정하고 패널 높이를 보이는 줄 수(최대 3)로 계산한다.
- **AI가 한 일**: 기획 결정 하나(밭 크기)만 객관식으로 묻고 나머지 열둘은 답 그대로 구현 · 굽기 · 캡처(진입 · 심기 · 자람 · 익음 · 여백에서 안 거둠 · 몸통에서 거둠 · 창고 · 점원 팝업 두 상태)로 확인했다. 발소리는 `SoundManager` 큐의 마지막 재생 시각으로 확인했다(듣지 못하므로). 테스트는 여백 거두기 1개 + 검증 1개(226 → 227).

### 4.60 농장 피드백 3차 — 시안 셋씩 끼워 보이고, 고른 것만 적용 (2026-09-30)

- **문제**: 2차 결과를 본 사용자가 다섯을 더 짚었다 — 밀 아이콘이 밭의 밀과 다르다, 이랑 비율이 이상하고 싹이 진한 줄에 심긴다, 걸음 소리가 흙 밟는 소리가 아니다, 버튼 안에 선이 든 행동 아이콘들, 창고 버튼이 농사처럼 보인다 — 그리고 「리소스는 시안을 뽑아 보여 주고 내가 고른 뒤 적용」으로 절차를 되돌렸다.
- **기술 포인트**: 시안은 에셋을 건드리지 않고 플레이 중 런타임 스프라이트(`Texture2D.LoadImage` + `Sprite.Create`)를 실제 부품(창고 칸 `Image` · 밭 `PlotView` 몸통과 작물 줄 자리)에 끼워 캡처했고, 버튼 아이콘은 `btn_act` 위에 합성했다. 밀 아이콘은 「밭에 심긴 것과 같게」 — 줄 그림의 포기들은 잎이 서로 닿아 연결 성분으로도 못 가르고 이삭만 오려 붙인 것은 「너무 다르다」고 반려돼, 사용자 지시대로 밭 밀 줄을 참조로 Codex에 한 포기만 그리게 해(시안 셋) 고른 것을 밭 밀 팔레트 7색으로 13×24칸에 줄였다(창고 칸 2배 = 밭과 같은 결). 그림이 상자보다 커지자 `InventoryView.SetIcon`이 프리팹 상자 높이에 드는 정수 배로 줄인다(폭은 줄이 받는다 — 폭까지 재면 크루아상이 1배로 떨어졌다). 흙판은 같은 높이 이랑 셋 + 가는 선, 작물 밑변은 이랑 아래 6칸. 걸음 소리는 고른 시안에서 「귀를 때리는」 대역을 낮췄다(900~4000 → 700~2600Hz).
- **AI가 한 일**: 시안 페이지(밀 3 · 흙판 3 · 소리 3 · 행동 아이콘 3×3 · 가방 3)를 만들어 멈췄고, 답(1 밭과 같게 · 2-A · 3-a 누름 · 4 B/B/A · 5-B)대로 원본 스크립트에 옮겨 굽고 캡처로 확인했다. 테스트 227/227.

### 4.61 똥 거름 · 덤 — 치울 이유를 다른 굴의 이득으로 (2026-09-30)

- **문제**: 웜뱃 똥(4.54)은 손님 길을 막는 벌칙뿐이라 치우는 일이 귀찮음으로만 남았고, 농장은 밀만 내는 한 줄짜리 루프였다. 농사 뼈대(3회차)가 이 단계에 건 판정 질문은 「똥을 치울 이유가 생겼나」.

### 4.62 창고 다듬기 · 값 표식 — 다른 세션의 시안을 프리팹으로 옮기다 (2026-09-30)

QA 스크립트가 닫힌 팝업의 닫기 버튼을 눌러 난 콘솔 오류 둘은 실제로는 누를 수 없는 경로임을 스택으로 확인하고 지웠다. 테스트 228/228(글꼴 둘이 줄어 에셋 검사 −2, 규칙 검사 +1).

### 4.64 획득 팝업 쌓기 · 작물 「무럭무럭」 — 겹침은 한 곳에서, 연출은 시안 값 그대로 (2026-09-30)

- **문제**: 거둘 때 반짝돌 팝업이 밀 팝업과 겹쳤다. 덤을 0.25초 늦게 0.5 위에 띄웠는데, 그사이 밀 팝업이 떠올라 두 그림이 포개졌다. 사용자는 「획득 이펙트는 서로 겹치지 않게」를 규칙으로 걸었다. 같은 날 아트방에서 작물 자라는 연출 C(단계 5개 · 늘어남 · 바람 · 반짝임)와 새싹 원판 게이지를 골랐다.

### 4.65 웜뱃 석상 — 능력 세 줄을 굴리고 잠그는 가게 공통 강화 (2026-09-30)

- **문제**: 설계 28의 반짝돌은 창고에 쌓이기만 했다. 농사 뼈대는 이것을 광장의 웜뱃 석상에 바쳐 「능력 세 줄을 굴리고, 마음에 드는 줄은 잠그고 나머지만 다시」로 가게 전부를 세게 하는 자리로 잡았다. 판정 질문은 「굴리는 맛, 가게가 세지나」.
- **기술 포인트**: 석상 줄은 저장할 플레이어 상태라 `ZooState.Statue`에 두었다 — 오븐 · 계산대 · 밭 · 웜뱃 · 광장이 이미 지갑을 들고 있어 새 전달 경로 없이 `Statue.Boost(능력)` 한 줄씩으로 속도 · 값 · 간격 · 확률에 걸린다. 능력 일곱은 표 행(`StatueTable`: 등급 셋 값 · 비중), 굴리기 값 · 잠금 · 등급 비중은 광장 설정이다. 광장 석상은 `Interactable`이면서 `IPlaced`라 길을 막고 겹침 검사 · 손님 들를 곳에 그대로 들지만, 값이 없는 종류는 편집에서 집지 않는다는 규칙 하나로 고정했다(`ThingAt`). 사용자 결정대로 분수 자리를 석상이 대신하면서 광장 들를 곳 목록이 바뀌어, 「첫 손님이 먼저 빵집에 들어간다」를 가정하던 테스트가 깨졌다 — 첫 손님을 따라가 보니 먼 구석부터 들를 뿐이라 테스트를 「빵집에 들어간 그 손님」으로 고쳤다. 팝업은 창고와 같은 조각 · 글자 규칙으로 스크립트가 프리팹을 만들었고, 굴리면 굴린 줄만 능력 이름을 넘기다 위부터 한 박자씩 멈춘다. UI에는 입자를 넣지 않는 규칙이라 전설은 금빛 줄 틀 · 부풂 · 소리로, 반짝 알갱이는 월드의 석상 쪽에서 튄다.
- **AI가 한 일**: 설계 페이지에서 넷(비용 · 자리 · 능력 풀 · 연출)을 물었고 자리는 권장과 달리 「분수 자리를 대신」이 골라졌다. 테스트 11개(굴리기 · 잠금 · 모자람 · 능력 다섯 · 광장 석상 · 표 검증)를 더했고(228 → 239), 플레이에서 굴리기(반짝돌 30 → 27) · 잠금(값 3 → 5) · 걸음 능력(속도 3.0 → 3.3) · 느린 시간의 도는 줄 · 전설 멈춤을 상태 값과 캡처로 확인했다. 석상 그림은 웜뱃 앞모습을 돌 색으로 바꾼 더미다.

### 4.66 석상 축복 — 돌리기를 지우고 무료 시간제 축복으로 (2026-09-30)

- **기술 포인트**: 수레를 「행상 둘레」가 아니라 「행상이 걷는 길 위」에 둔다. 올 때는 View가 행상 발자취를 기록해 길 위 거리만큼 뒤(끌기), 갈 때는 Core `Mover`가 연 남은 꺾임점을 따라 앞(밀기). 거리는 수레가 놓인 길 방향(옆 그림 1.4 · 끝면 0.5, 손잡이가 앞발에 닿게)을 따르고 바뀔 때도 길 위에서만 미끄러진다. 손잡이는 펼친 좌판 그림처럼 늘 오른쪽이 되게 동선을 짰다: 좌판 왼쪽 위에서 곧게 내려와 오른쪽으로 끌고 들어가 손잡이 자리에 서면 수레가 좌판 자리에 멈추고(오차 0.08), 펼치는 동안 행상이 앞을 돌아 왼쪽 앞에 선다. 떠날 때는 접고 손잡이 자리로 가 수레를 왼쪽으로 밀어내며 계단으로(수레가 먼저 모퉁이를 돌고 먼저 계단에 든다). 점을 여럿 거쳐 걷는 `Mover.WalkThrough`, 단계 「잡으러 감」(Hitching) 하나를 더했다. 계단 안쪽에서는 수레가 흐려졌다 나타난다.
- **AI가 한 일**: 문제 캡처와 안 셋(길 따라 끌고 밀기 · 멈춰서 돌리기 · 등에 지기) 비교 → 사용자 A. 느린 화면 캡처와 수레 좌표 기록으로 고치며 확인: 처음엔 행상이 손잡이 자리를 지나쳤다 되돌아오며 수레를 뚫고 지났고, 마지막 한 걸음에 간격이 줄어 수레가 0.37 덜 갔고, 세워 둔 수레가 지나가는 행상 쪽으로 뒤집혔다 — 위에서 곧게 내려오는 점 · 수레 쪽 길 방향 간격 · 손잡이 오른쪽 고정 동선으로 셋 다 고쳤다. 같은 날 아트방 그림(유물 아이콘 아홉 · 유물 버튼 · 버튼 틀 돌 테 · 볼록 단추)을 붙이고 가게에 걸린 자리를 캡처로 맞췄다.
- **떨림 고침(같은 날, 사용자 「짧게 방향을 바꾸면 수레가 떨림」)**: 프레임마다 수레 그림을 기록해 보니 모퉁이에서 옆 ↔ 끝면이 몇 프레임마다 번갈아 바뀌었다 — 간격(옆 1.4 · 위아래 0.5)을 수레가 놓인 길 방향으로 고르니, 간격이 바뀌면 수레가 모퉁이 너머로 밀리고 방향이 다시 바뀌는 고리였다. 수레 자리를 「행상 발에서 그 방향의 타원 거리에 처음 닿는 길 위의 점」으로 바꿔 간격이 이어지게 했고(곧은 길에서는 정확히 그 거리라 좌판에 그대로 멈춘다), 그림은 기울기가 1.3배를 넘어설 때만 바꾼다. 중간에 시험한 「끌려오는 줄」 방식은 떨림은 없었지만 모퉁이를 크게 질러 좌판에 1칸 비껴 닿아 버렸다. 또 웜뱃을 비켜 길을 다시 찾을 때 경유점이 지워져 행상이 손잡이 자리로 곧장 내려오던 것을, 경유점을 행상이 들고 한 구간씩 걷게 고쳤다. 이어서 사용자가 「옆을 보며 아래로 움직인다」고 해 보니 그림을 「행상에서 본 수레 방향」으로 골라, 모퉁이를 돌아 내려가는 수레가 옆에 선 행상 때문에 옆모습이었다 — 그림은 수레가 실제로 굴러간 방향(0.12유닛마다 잼)으로 고르게 바꿨고, 구간마다 그림과 실제 이동을 비교하는 기록에서 어긋남이 16/293 → 7/301(모두 꺾은 바로 그 구간)로 줄었다.

### 4.71 행상과 대화로 뽑기 — 수레를 버리다 (2026-10-01)

- **문제**: 수레를 길 따라 끌고 밀게 고쳐도(4.70) 모퉁이에서 옆모습으로 아래로 가는 등 어색함이 남았다. 사용자 「그냥 수레를 버리고 너구리랑 대화해서 뽑는걸로 하자」.
- **기술 포인트**: 수레 사물 · 수레 그림 · 펼침/접음/잡으러 감 단계 · 경유점 걷기를 모두 지웠다. 행상은 오는 중 → 서 있음 → 가는 중 → 없음 네 단계로, 계단에서 좌판 자리(`merchantX · Y`, 옛 수레 자리)까지 걸어와 서고, 사물 `MerchantInteractable`은 행상이 서 있는 동안만 행상 발까지의 거리로 닿는다. 버튼(행동 `talk`)을 누르면 행상이 웜뱃 쪽을 보고 인사 한 줄(`DialogueTable merchant_hello`, 셋 중 하나)을 말하고, 말풍선이 반쯤 지났을 때 뽑기 팝업이 뜬다(사건 `MerchantTalked` 하나를 말풍선과 팝업이 같이 받는다). `Mover` · `PlazaVisitor`는 수레 전(302608c)으로 되돌렸다.
- **AI가 한 일**: 테스트에서 웜뱃이 좌판 자리 0.7 앞에 서 있으면 행상이 1칸 앞에서 영영 멈추는 것을 찾았다 — 갈 곳이 웜뱃 둘레(0.8) 안이면 손님은 웜뱃이 비킬 때까지 서는데, 행상 자리는 통로처럼 기다렸다 지나가게 하고, 갈 곳이 둘레 안일 때는 소용없는 돌아가기를 하지 않게 고쳤다(돌아가기와 기다림이 번갈아 제자리 떨림). 플레이 확인에서 유물 메뉴 버튼이 모든 팝업 위에 그려져 좌판 팝업 닫기 버튼을 가리던 것을, 메뉴 버튼 줄 바로 다음으로 열어 고쳤다. 아트방 그림(너구리 얼굴 아이콘 · 말풍선 행동 아이콘)을 붙이고 유물 아이콘을 26칸의 4배(104)로 맞췄다. 테스트 257 → 256(수레 길막이 · 비켜 서기 시험이 빠지고 대화 시험으로). 같은 날 아트방 모형에서 사용자가 고른 둘을 붙였다: 행상이 없을 때 상단 알약은 회색 얼굴 + 시간만(「다음 행상」 글자 삭제), 메뉴 버튼 아이콘 54 → 72px, 유물 버튼은 옛 항아리.

### 4.72 작물 · 밭 시트 — 빵 해금을 본떠 작물을 늘리고, 첫 레시피 벽 (2026-10-01)

- **문제**: 심기 버튼이 늘 표의 첫 행(밀)만 심어, 작물을 늘릴 자리도 「무엇을 심을까」라는 선택도 없었다. 농사 뼈대(3회차)의 다음 단계는 작물 확장 + 밭 시트 + 상점에 없는 둘째 작물이 고급 메뉴의 관문이 되는 것.
- **기술 포인트**: 오븐 굽기 시트를 그대로 본떴다. 빈 밭의 버튼(`open_plant`)은 시트를 열기만 하고, 시트 행동 `plant`가 연 작물마다 칩 + 다음 작물 해금 칩(`CropTable.unlockCost`)을 내놓는다 — `FarmArea`의 `UnlockedCrops` · `NextCrop` · `UnlockCrop`은 `BakeryArea`의 빵 해금과 같은 세 줄이고, 새 파일 · 새 UI 조각은 없다. 사면 열리고 그 밭에 바로 심는다(오븐의 다음 빵 칩과 같은 규칙). 둘째 작물 딸기(60초 · 2개 · 1,000)가 케이크 레시피(밀 2 · 딸기 2)에 들어가 첫 레시피 벽이 된다. 거두기 사건이 재료 id 대신 작물을 실어, 이삭 바구니 덤 판정이 농장 첫 작물이 아니라 그 밭 작물의 개수와 비교한다. 칩의 레시피 자리에는 한 번에 거두는 개수 「+3」을 둬 빵 칩과 같은 틀에서 산출을 보인다.
- **AI가 한 일**: 설계 페이지에서 심는 조작 두 안(버튼 → 시트 → 칩 / 한 번에 마지막 작물)을 비교해 권장안(시트, 다음 설계의 농장 점원이 반복 조작을 넘겨받음)으로 확정받았다. 프로그래밍방은 그림을 만들지 않으므로 딸기 아이콘 · 작물 5단계를 아트방에 넘기고 그동안 케이크 · 밀 그림을 임시로 가리켰다(같은 날 아트방 시안으로 바꿈: 아이콘 C 「딸기 한 알 + 흰 딸기꽃」, 작물 5단계 A 「잎 덤불 → 꽃 · 풋딸기 → 빨간 딸기」). 플레이에서 밭 시트 → 딸기 해금(코인 −1,000) → 60초 뒤 밟아 거둠(딸기 +2) → 케이크 칩 레시피 → 굽기(딸기 −2, 레시피 숫자가 부족 색) → 창고 정보 창(획득처 농장 60초 ×2 · 사용처 케이크 ×2)을 캡처와 상태 값으로 확인했다. 테스트 256 → 257.
- **칩 정보 다듬기(같은 날, 사용자 「아이콘이 두개이고 획득 갯수가 나오고 밑에 그냥 텍스트로만」)**: 아트방이 실제 화면 모형 시안 셋을 만들고 사용자가 A 「배지 + 시계 줄」을 골랐다. 새 조각 없이 있는 조각만으로, 개수는 칩 오른쪽 위 배지(창고 칸 배지 결, 0이면 강조색), 아래 줄은 시계 + 초, 해금 칩은 자물쇠 + 코인 값. 작은 같은 아이콘과 「+3」은 뺐다. `SheetChip`의 글 두 칸(Sub · SubRight)을 Count · Seconds · Cost로 나눠 오븐 칩과 작물 칩이 같은 틀을 쓴다. 캡처를 시안과 픽셀로 견줘 둘을 고쳤다: 배지 85%가 선형 색 공간에서 시안보다 밝게 섞여 95%로, 레시피 줄이 없는 작물 칩은 고정 거리로 내리면 키 큰 딸기가 이름에 겹쳐 아이콘 가운데를 칩 윗변에서 100px(4px 격자)에 둔다.

### 4.73 유물은 UI에만 — 가게에 거는 그림을 지우다 (2026-10-01)

- **문제**: 끼운 유물이 가게에 그림으로 걸려(풀무는 오븐 옆, 종 · 주판 · 동전은 계산대 위, 풍경은 광장 계단, 물뿌리개 · 바구니는 농장 문) 효과가 날 때 톡 튀었다. 사용자 「유물을 장착하면 게임에 등장하는것같은데, 그냥 UI상으로 가지고 있게만 해」.
- **기술 포인트**: 월드 쪽은 `RelicProps` 한 클래스였고 빵집 · 광장 · 농장 화면이 하나씩 들고 사건(굽기 · 계산 · 손님 도착 · 거두기 · 똥 치우기 · 점원 깨움)마다 `Pop`을 불렀다. 그 클래스와 걸 자리 계산, 튀기만 하던 구독을 지웠고, 사건 자체는 소리 · 손님 팝업 · 테스트가 쓰므로 그대로 뒀다. `RelicTable`에서 걸 자리 칸(anchor · dx · dy)과 그 검증 · 시험 사례를 지웠다(version 2). 유물 효과는 Core에 있어 바뀌지 않는다.
- **AI가 한 일**: 플레이에서 유물 셋을 끼워 효과 값(풀무 0.2 · 바구니 0.3 · 시계 30)이 걸린 채 월드의 유물 그림이 0개인 것을 확인했다. 같은 날 다음 작업으로 넘어가며 앞 작업(설계 35)을 기능 · 아트방 · 규칙 · 문서 네 커밋으로 나눠 올렸다.

### 4.74 반짝돌 뽑기 — 하나만, 메인과 결과를 나누다 (2026-10-01)

- **문제**: 뽑기가 후보 셋 → 하나 고르기였고, 한 팝업 안에서 뒷면 셋 → 앞면 셋 → 고른 결과로 상태가 바뀌었다. 사용자 「1. 뽑기는 하나만 나온다. 2. 뽑기 메인 UI와 뽑기 결과 UI를 분리한다」, 리소스 · 연출은 아트방과 협업.
- **기술 포인트**: Core `Relics.TryDraw`가 후보 하나를 비중으로 골라 바로 별 +1 · 빈 칸이면 끼우고 사건에 그 유물을 싣는다. 남는 후보(`Offer` · `HasOffer` · `Choose` · `k_Choices`)와 사건 종류 `Chosen`을 지웠다. 화면은 뽑기 메인(`RelicCartView`: 카드 뒷면 한 장 · 뽑기)과 그 위에 뜨는 뽑기 결과(`RelicDrawResultView`: 뒤집기 → 새 별 → 결과 글 · 유물 보기 · 한 번 더 · 확인) 둘로 나눴고, 결과 프리팹은 메인 프리팹을 복사해 머리줄을 빼고 확인 줄을 더해 만들었다. Presenter는 둘을 함께 든다(행상이 떠나거나 편집 모드면 둘 다 닫음).
- **AI가 한 일**: 설계 페이지에서 결과를 띄우는 법 · 버튼 · 모양 잡기 세 결정을 권장안으로 확정받았다. 캡처에서 카드가 팝업 폭 전체로 늘어난 것을 찾아, 카드 안 세로 레이아웃이 「늘어나도 됨」을 보고하던 것을 카드의 `flexibleWidth` 0으로 막았다. 카드 뒷면 · 공개 연출 · 뽑기 소리는 아트방에 시안 셋씩 부탁했다(지금은 임시 그림 · 석상 소리). 같은 날 아트방 딸기 다 익음 원판(「한 알」)을 들이고, 빵집 입구 장식 넷(밀 통 · 웜뱃 제빵사 · 칠판 · 빵 식힘대)을 농장 입구 소품과 같은 방식으로 굽기에 넣었다(굽기 부산물 다섯은 되돌림).

### 4.75 어디서나 똥 · 거름 획득 연출 — 빵집 전용을 곳 공용으로 (2026-10-01)

### 4.79 별 평가 — 코인 말고 다른 열쇠, 끝없는 별과 가게 상한 (2026-10-02)

- **기술 포인트**: 별은 플레이어 상태(`ZooState.Stars`)이고 효과는 축복 · 유물과 같은 효과 배수 `Scale(effect)`에 곱한다(축복 × 유물 × 별). 조건은 별마다 행을 쓰지 않고 `StarConfigTable`의 공식(시간 · 만족 · 판매 · 실망 상한이 별 수로 커지고, 5의 배수는 큰 평가)으로 만들어 끝이 없다. 정해진 별에만 `StarMilestoneTable` 행을 두고 「앞 마일스톤 그대로」를 0으로 적어, 상한(`Cap`)과 「★n 필요」(`StarFor`)가 같은 표를 앞에서부터 읽는다. 편집 모드 구매(`IsCapped`)와 업그레이드 시트 줄(새 상태 `Locked`)이 이 상한을 본다. `Evaluation`은 사건만 센다: 평가가 시작된 뒤 들어온 손님(맛 평가단)의 계산 · 판 빵 · 포기. 만족 · 판매를 다 채우면 그 자리에서 통과, 실망이 넘치면 그 자리에서 실패라 결과를 기다리지 않는다. 손님 몰림은 광장 손님 간격을 나누는 한 줄이고, 가게 지키기는 곳의 `CanLeave` 하나를 통로 행동과 점원 외출 판정이 같이 본다. 평가단장은 `Visitor`를 이어 구멍에서 톡 나와 평가판 옆에 서고, 결과 한마디는 Core가 골라(`LastLine`) 말풍선과 소식지가 같은 줄을 쓴다. 팁은 별이 모자라 확률이 0이면 난수를 굴리지 않아 옛 시험의 난수 순서가 그대로다(감탄 ✨도 같다). 평가 팝업은 석상 팝업 프리팹을 복제해 스크립트 참조와 필드 이름만 바꿨고, 같은 틀에 「빵집 평가」와 「굴 소식」을 그린다. 상단에는 행상 알약을 복제한 평가 알약 하나와 조건 알약 넷을 쌓는다.
- **AI가 한 일**: 다섯 질문을 안 비교 · 권장 · 반영으로 설계 페이지 v2에 정리하고 새 결정 여섯을 뽑았다. 구현 전에 탐색 에이전트로 열두 곳(팝업이 열리는 길, 행상 NPC, 구매 · 업그레이드 상한, 계산, 간판, 점원 외출, 상단 알약, MainScene)을 찾았다. 시험 7개(★0 상한과 별로 풀림 · 조건 공식과 큰 평가 · 통과 보상 · 실망 초과 실패와 쉬는 시간 · 시간 끝 · 가게 지키기와 평가단장 자리 · 팁 확률)와 표 검증 하나를 더했다. 별과 무관한 옛 시험 4개는 상한을 걷어 내는 도우미(`LiftStarCaps`)로 맞췄다. 플레이에서 칠판 버튼 · 평가 팝업 · 평가 중 상단 알약과 평가단장 · 실패 · 통과 소식지 · 광장 간판 「빵집 ★1」 · 평가단장 한마디를 캡처로 확인했다. 그 과정에서 버그 둘을 고쳤다. 평가 전부터 있던 손님까지 실망으로 세던 것(→ 평가 중 들어온 손님만), 끝난 평가가 다음 평가 조건을 돌려줘 소식지의 「모자란 것」이 빠지던 것(→ 지난 조건 · 다음 조건을 나눔)이다. 아트방이 같은 날 낸 별 조각 C · 감탄 ✨ B를 바로 썼다. 테스트 272 → 282.

### 4.80 평가 화면 다듬기 — 글 목록을 아이콘 칸으로, 평가 표시는 한 장의 카드로 (2026-10-02)

- **문제**: 설계 40을 플레이한 사용자가 둘을 짚었다. 「평가 UI가 글씨로만 나열되어 있어서 읽기가 싫어짐」, 「왼쪽 위 타이머에 모든 정보가 다 나와서 헷갈림」. 평가판 팝업은 가운데 정렬 글 열두 줄이었고, 평가 중에는 코인 아래 왼쪽 줄에 평가 시간 · 조건 셋 · 행상 시간이 한 줄로 섞였다.

Resources 밖 그림(말풍선 칸 ♥ · !!, 진열대 · 오븐 · 계산대, 업그레이드 화살표)은 뷰가 이름 목록으로 들고, 그 밖은 표의 Resources 경로를 그대로 쓴다. 조건 아이콘을 평가단 머리 위에 뜨는 말풍선과 같은 그림으로 해 화면과 월드가 이어진다. 「2→3」은 별 n개일 때의 상한(`CapAt`)으로 지금 → 다음을 만든다. 칸이 몇 개든 그리드의 첫 자식을 본으로 복제한다. 평가 카드가 넓어져(큰 평가는 조건 넷) 왼쪽 행상 알약과 겹치자, 카드가 떠 있는 동안 왼쪽 알약을 카드 밑부터 쌓게 했다. 평가 중에 들어온 손님은 머리 위 수첩 표식(`Evaluation.IsJudge`)을 달고, 같은 자리의 말풍선 · 글자 말풍선 · 머리에 인 빵이 있으면 숨긴다.

### 4.81 곳 이름 팻말 — 곳을 옮길 때마다 1.2초, 들어오는 웜뱃 얼굴은 가리지 않게 (2026-10-02)

### 4.82 시작 배치 — 목업과 카메라가 다를 때, 그리고 배치가 드러낸 버그 둘 (2026-10-02)

- **AI가 한 일**: A를 넣고 플레이 캡처를 찍어 보니 카메라가 계산대의 웜뱃(x −1.4)을 따라가 화면이 밀리면서 진열대가 메뉴 버튼에 가리고 오븐이 잘렸다. 아트방 목업은 카메라를 가운데에 둔 그림이었다. 원인과 함께 B · C도 배치 검사를 돌려 객관식으로 물었고, 사용자가 계산대가 가운데인 C 「빵 굽는 구석」을 골랐다. ### 4.83 저장 · 오프라인 — 새 게임 위에 덮기, 점원 몫만 공식으로, 대조 시뮬이 찾은 버그 (2026-10-04)

- **문제**: 게임을 끄면 모든 진행이 사라졌다. 방치형의 바탕인 「자리를 비운 동안 번 돈」도 없었다. 저장할 상태는 빵집 · 광장 · 농장 층마다 흩어져 있고(칸 · 사물 · 업그레이드 · 점원 · 밭 · 유물 · 별 · 축복 · 행상 · 월급날), 시뮬은 매 프레임 행동 트리라 8시간을 그대로 돌리면 폰에서 수십 초가 걸린다.
- **기술 포인트**: 저장 파일 한 장(GameKit `DataManager`, 임시 파일 교체로 원자 쓰기 · 저장 시각 UTC). 불러오기는 새 게임을 평소처럼 만든 뒤 그 위에 덮는다(`GameSave.Apply`). 값을 치르거나 난수를 굴리는 공개 경로(사기 · 고용 · 뽑기)는 쓰지 않고, 상태 주인 클래스마다 `internal` 되살리기만 더했다. 표에서 사라진 id는 건너뛰고, 읽기나 덮기에 실패하면 `save.bad.json`으로 남겨 30초 뒤 자동 저장이 덮어쓰지 않게 했다(GameKit도 고침). 오프라인은 시뮬 대신 공식 근사다(`Offline.Settle`). 점원 한 바퀴 = 일 + 딴짓 몫이고, 빵집은 손님 · 계산 · 진열 공급 중 좁은 곳으로 판다. 재료는 바닥나는 때부터 농장이 거두는 만큼만 굽는다. 월급은 판 돈 안에서만 내고 상한은 8시간이다(사용자 결정 넷, 모두 권장안).
- **AI가 한 일**: 공식이 맞는지 실제 시뮬 20분과 대조하는 테스트를 두었는데, 일머리 60에서 게임이 예외로 멈췄다. 광장 문에서 「자리 확인 → 톡 뛰기」 사이에 손님이 한 명 넘칠 수 있는데(이미 받아들인 한계), 그러면 줄이 줄 자리 8칸을 넘어 범위 밖 예외가 났다. 실제 플레이라면 매 프레임 틱이 멈추는 버그라, 줄 자리를 고르는 공용 함수에서 끝자리에 겹쳐 서게 고치고 재현 테스트를 붙였다. 그 뒤 공식이 시뮬보다 18~20% 낮게 나왔다. 씨앗 하나로 재면 딴짓 난수 때문에 ±13% 흔들려 판정이 안 돼서, 씨앗 여섯의 평균을 냈다. 그래도 낮아 원인을 찾았다. 딴짓의 25%는 다른 점원과의 수다이고, 수다는 딴짓 시간이 아니라 대화가 끝나면 끝난다. 공식에 수다 몫을 넣으니 +1~2.5%로 맞았다(테스트도 평균 대조로). 불러온 점원은 「고용됨」 사건이 없어 그림이 안 생기고, 간판 별 · 축복 알약도 사건으로만 그려지던 것을 플레이 캡처로 찾아 처음 상태부터 그리게 했다. 시작 배치 그대로 일머리 50 안팎 점원 셋이면 월급이 판매를 다 먹어 오프라인 코인이 0이 되는 것도 숫자로 보고했다.

### 4.84 굴 파기 동작 — 기다리지 않는 끼워 넣기, 판 칸을 보고 서 있기, 흙덩이는 던지는 칸에 (2026-10-05)

- **문제**: 굴을 파면 칸이 밝아지고 흙덩이가 튀었지만 웜뱃은 숨쉬기 그대로 서 있었다. 아트방이 부위 조립 시안을 버리고 Codex로 새로 그린 「웅크려 퍼 던지기」(세 방향 × 12칸, 긁기 두 번 → 던지기)를 넘겨 왔다.
- **기술 포인트**: 딴짓에 쓰던 끼워 넣기(`SpriteAnimator.Interject`)는 숨쉬기 한 바퀴(최대 1.3초)가 끝나기를 기다렸다가 시작한다. 버튼에 바로 답해야 하는 파기에는 맞지 않아 `now` 하나를 더해, 지금 칸에서 끊고 바로 첫 칸부터 보인 뒤 돌던 프레임의 처음으로 돌아가게 했다. 파기 사건은 빵집 · 농장 화면이 이미 「내 굴인가」를 걸러 받고 있어, 거기서 웜뱃 뷰의 `Dig()`를 부르고 그 반환값(던지기까지 남은 초 = 던지는 칸 8 × 한 칸 시간)만큼 흙덩이를 늦춘다. 사용자가 써 보고 「파는 도중에 움직여짐」 · 「좀 느리다」고 해서, 웜뱃이 서 있는 시간을 표 하나(`ConfigTable` wombatDigSeconds 0.72)로 두고 Core 웜뱃이 그동안 조이스틱 · 시스템 이동을 모두 멈추게 했다(시트에서 파기를 고른 웜뱃 경로에서만 — 저장 불러오기 · 치트의 파기는 묶지 않는다). 그림은 이 값을 칸 수로 나눠 돌아(0.96 → 0.72초) 동작 길이와 서 있는 시간이 늘 같다. 이어 「파는 땅쪽을 바라보게」에 따라 웜뱃이 판 칸 사각형에서 가장 가까운 점 쪽으로 돌아선다. 이 돌아서기 · 묶기는 파기 행동 안에서 칸을 파기 직전에 한다. 판 사건을 받는 그림이 그 순간의 방향 · 「파는 중」을 읽기 때문이다.
- **AI가 한 일**: 0.05배속으로 세 방향을 찍고, 흙덩이 수를 게임 시각과 함께 읽어 던지기 칸에 0 → 24로 바뀌는 것을 확인했다. 고친 뒤에는 시트 경로로 파고 조이스틱을 민 채 0.1배속으로 위치를 읽어, 0.72초 동안 그 자리에 있다가 걷는 것을 확인하고 같은 내용을 EditMode 테스트로 남겼다(298 → 299). 돌아서기를 넣자 플레이에서 파기 그림 대신 숨쉬기가 나왔다. 방향이 바뀌면 그림 쪽이 「새 방향 숨쉬기」를 다시 틀면서 끼워 넣은 동작을 지운 것이다. 파기를 시작할 때 새 방향 숨쉬기를 먼저 깔아 두어 고쳤고, 아래 · 오른쪽 칸을 파 보아 그 방향 그림이 나오고 끝나면 같은 방향 숨쉬기로 돌아가는 것을 상태 값으로 확인했다. 파는 동안에는 계산대 손님 쪽으로 돌아보지 않게 했다. 처음 옆모습 시험에서 동작이 안 나왔는데, 방향을 바꾼 바로 그 프레임에 파서 새 방향의 숨쉬기가 끼워 넣기를 지운 것이라(실제 플레이에서는 서서 파므로 생기지 않음) 시험을 나눠 다시 쟀다. 저장 불러오기도 칸마다 파기 사건을 내지만 화면이 붙기 전이라 시작할 때 동작이 튀지 않는 것을 순서로 확인했다. 아트방이 물은 「웅크리면 머리 위 말풍선이 내려가나」는 말풍선이 몸 그림이 아니라 고정 높이에 붙어 있어 그대로라고 답했다. 재굽기가 만든 광장 프리팹 · 시트 메타의 번호만 바뀐 변경은 되돌려 프리팹 diff를 굴 파기 배열만 남겼다.

### 4.85 굴 벽 띠의 드러난 끝 — 그림 규칙을 파이썬으로 흉내 내 마감안 고르기 (2026-10-05)

- **문제**: 사용자가 플레이 화면에서 「웜뱃이 바라보는 곳 벽 모서리가 다듬어지지 않아 이상하다」고 했다. 안 판 흙 덩어리의 앞면 띠가 옆 칸이 파인 쪽에서 외곽선 없이 칼로 자른 듯 끝나고, 덩어리 아래 모서리만 둥글게 깎여 있었다.
- **기술 포인트**: 굴 그림은 마스크 한 장에서 나온다. 테두리(선 · 턱 6칸)는 마스크 밖에만 그리는데, 띠는 「방 안」(걷지는 못하는 마스크)이라 띠 끝이 바닥과 맞닿는 곳에는 경계가 생기지 않았다. 띠 끝이 방으로 드러난 열(위 칸은 안 팠고 옆 위 칸은 판 곳)을 한 칸 폭만 마스크 밖으로 빼면 그 열이 바깥 선이 된다. 둥글리기 전에 빼서 덩어리 아래 모서리가 「안쪽 모서리」로 메워지지 않게 하고, 둥글리기 뒤에 한 번 더 빼서 띠 밑 끝을 메운 것을 지운다. 걷는 땅은 그대로다(띠는 원래 걷지 못하는 곳).
- **AI가 한 일**: 마스크 · 둥글리기 · 칠하기를 파이썬으로 그대로 옮겨 지금 모습이 게임 캡처와 같게 나오는 것부터 맞춘 뒤 마감안 여섯(턱 띠를 내리기 · 둥글리기 뒤 내리기 · 선 한 줄 · 모서리를 살린 선 · 곧은 선 · 곧은 턱 띠)을 그려 비교했다. 덩어리 위 테두리의 턱(땅 가장자리)이 앞면 끝으로 내려오면 T자 이음이 생겨 무거워서, 덩어리 옆 바깥 선만 곧게 내리는 안을 골랐다. 옛 동작(아래 모서리를 메움)을 기대하던 마스크 테스트를 새 모양(끝 열은 방 밖 · 바로 옆은 띠 전체 높이 · 덩어리 모서리는 그대로)으로 바꾸고, 플레이에서 사용자가 본 덩어리 앞에 웜뱃을 세워 전후를 캡처로 비교했다.

### 4.86 낚시 디펜스 수직 슬라이스 — 세 번째 곳을 넣기 전에 두 갈래 분기부터, 오프라인은 같은 판을 한 번 더 돌려서 (2026-10-05)

- **문제**: 낚시 기획 2회차에서 사용자가 「낚싯대 부두 편성」을 고른 뒤 「낚시와 디펜스 배치를 섞은 아이디어가 좋다, 더 디벨롭」이라 해서, 낚시터를 랜덤 디펜스 판으로 다시 짰다(S자 물길 = 길, 둑 말뚝 = 탑 자리, 낚싯대 = 유닛, 물때 = 웨이브, 대물 = 보스, 소환 · 셋 합성 · 계열 문턱). 기획 회차 상한(같은 주제 2회)에 따라 바로 수직 슬라이스(설계 44)로 만들어 플레이로 판정하기로 했다. 그런데 코드는 곳이 빵집 · 광장 · 농장 셋뿐이라는 가정으로 짜여 있었다.
- **기술 포인트**: 조사 에이전트로 곳을 붙이는 자리를 훑었더니, 광장 문 · 점원 일 · 저장 · 치트에 「농장 아니면 빵집」 두 갈래 분기가 박혀 있어 세 번째 곳이 조용히 빵집 쪽으로 빠지거나 예외를 냈다. 낚시터보다 먼저 이것을 주인 객체로 옮겼다. 광장 문은 표(PlazaConfigTable doors: 갈 곳 · 칸)의 목록이 되고, 곳마다 「광장에서 나를 잇는 문」(PlazaGate, 농장 아래층은 맨 위층 문)을 답한다. 점원 생성자의 `default`(계산대 일)는 모르는 자리면 예외로, 저장의 고정 점원 자리는 `FixedClerkSlot`으로 바꿨다. 낚시 판은 `FishingSim` 하나에 모았다(물고기는 꺾은선의 길이 s를 따라가고, 대는 사거리 안 맨 앞 물고기를 감고, 무게만큼 감기면 낚인다). 실제 낚시터와 오프라인 정산이 같은 코드를 쓴다: 오프라인은 지금 판으로 물때 하나를 씨앗 고정 난수로 한 번 돌려 잰 뒤 비운 시간의 물때 수를 곱한다. 월척을 붙잡는 상태도 시뮬 쪽에 두어 오프라인 판정이 실제 말뚝을 건드리지 않는다. Mall은 낚시터를 선택 인자로 받고, 없으면 씨앗 고정 난수의 낚시터를 만들어 기존 테스트의 난수 순서가 바뀌지 않게 했다. 대물 3택 1은 새 UI 프리팹 대신 낚은 대물을 둑에 눕혀 기존 사물 시트로 고르게 했다(게임의 「가서 버튼」 결 그대로).
- **AI가 한 일**: 발상 에이전트 셋(손맛 · 편성 깊이 · 엉뚱한 전제)이 낸 열여덟 안을 심사해 묶음을 만들고, 고를 것 넷을 객관식으로 물어 확정했다. 테스트 어셈블리가 Core의 internal을 못 보는 것을 살려, 낚시 테스트 16개는 웜뱃을 말뚝 앞에 세우고 버튼을 누르는 실제 길로 짰다(소환 · 합치기 · 옮기기 · 쿵 · 월척 · 대물 · 점원 · 저장 · 오프라인 대조). 처음 실패 셋은 모두 테스트 쪽 가정이었다(테스트 표가 재료를 처음부터 넉넉히 줌, 표 인스턴스가 달라 대 객체 비교가 틀림, 월척을 100%로 두니 대가 붙잡고 있어 합치기가 막힘). 오프라인 공식은 실제 20분 시뮬과 ±25% 안에 들었다. 플레이에서는 광장 → 낚시터 이동 · 소환 · 털썩 · 맞바꾸기 · 대물 → 단계 · 시트 3택 1 · 오프라인 팝업의 물고기를 캡처와 상태 값으로 확인했다. 같은 날 아트방이 넘긴 물길 「흙 도랑」은 그쪽 스크립트 머리말의 칠하기 규칙을 그대로 옮겨 굴 그림처럼 칸마다 칠했고(StreamPainter), 말뚝 그림도 붙였다. 테스트 299 → 324.

### 4.87 낚시 폴리싱 — 로직은 있는데 화면이 말하지 않는 사건부터, 사건 넷과 조회 하나로 (2026-10-05)

- **문제**: 낚시 디펜스 슬라이스는 규칙이 다 돌았지만, 대가 무엇을 감고 있는지 · 물고기가 언제 낚였는지 · 몇 단계인지 · 소환이 드문 것인지가 화면에 없었다. 물고기는 그림자 타원이 미끄러질 뿐이고, 낚이면 그 자리에서 사라졌다. 대물이 와도 팻말 글자만 바뀌었다.
- **기술 포인트**: polish-review 절차대로 Core 사건과 그것을 받는 화면을 맞대어 「사건은 있는데 표현이 약한 곳」을 뽑았다. 표현에 필요한 사실만 Core에 더했다: 사건 넷(FishEscaped · WaveStarted · RodSummoned · RodsMerged)과 「이 말뚝이 지금 감는 물고기」 조회(시뮬이 틱마다 기억하는 대상, 붙잡은 월척 우선). 화면 쪽은 그림이 올 때까지 쓰는 코드 그림 위에 얹었다: 낚싯줄은 대 끝과 물고기를 잇는 늘인 네모, 대는 물고기 쪽으로 기울어 낭창거리고, 물고기는 물길 방향으로 90도 단위로만 돌아(칸 격자 유지) 옆으로 두 칸 살랑인다. 낚이면 물고기 그림을 목록에서 떼어 대 끝으로 포물선을 그리게 하고, 닿은 뒤에 재료 팝업을 띄워 원인 → 결과 순서를 맞췄다. 같은 날아가기 코루틴이 놓친 물고기(구멍으로), 대물(둑으로), 합치기(짝 대가 합친 말뚝으로)를 함께 맡는다. 큰 사건 알림은 새 UI 대신 곳 이름 팻말(설계 42)에 「대물이 온다!」 · 「n단계!」 · 「대물을 놓쳤다」를 실었다. 값 표식 알약은 글이 길면 옆으로 늘어나게 해 「5단계 대물!」 같은 팻말이 넘치지 않는다.
- **AI가 한 일**: 체감이 큰 순서로 고쳤고, 기존 테스트 셋에 새 사건 검사를 얹어(물때 · 놓침 · 소환 · 합치기 · 감기 조회) 324개가 그대로 통과했다. 플레이에서는 시간을 0.05~0.1배로 늦추고 「날아가는 물고기가 있으면 멈춤」 스크립트로 0.35초짜리 낚아 올림과 합치기를 캡처했고, 팻말은 화면 상태 값(글 · 투명도)으로 확인했다. 가장자리 팻말이 화면 밖으로 나가는 문제는 HUD로 옮길지 고를 것으로 남겼다. 같은 날 아트방 낚싯대 「통통한 대」 13장이 와서 코드 막대를 바꿨다. 픽셀 그림이라 돌리지 않고, 피벗을 꽂는 자리에 두어 말뚝 뒤로 저절로 정렬되게 했으며, 물고기 쪽으로는 좌우만 뒤집고 월척은 휜 대 그림으로 바꿔 한 칸씩 떨게 했다. 줄은 아트방이 넘긴 대 끝 칸 좌표에서 나온다(꽂는 자리 칸은 굽기 스크립트가 PNG 머리에서 폭을 읽어 피벗으로).

### 4.88 물길 파기(설계 45) — 표의 꺾은선을 「끝까지 판 길」로 바꾸고, 판 길이 하나로 물 · 길찾기 · 그림을 다시 만든다 (2026-10-05)

- **문제**: 사용자가 「낚시 다시 폴리싱」에서 셋을 짚었다. 낚싯대가 부자연스럽다, 물길 끝 구멍 그림이 어색하니 빼고 막은 뒤 땅을 파서 물을 늘리게 하자, UI 글자가 이상하다. 낚싯대는 무엇이 어색한지 객관식으로 물었고, 사용자는 넷 다에 「대가 말뚝과 안 맞는다」를 더했다. 그중 「아래 물길로 줄이 땅을 가로지른다」는 그림이 아니라 규칙 문제였다(말뚝이 위아래 물길을 다 감는데 대는 늘 위를 향함).
- **기술 포인트**: 물길을 새 자료로 만들지 않고, 표의 꺾은선을 끝까지 팠을 때의 길(Plan)로 읽고 판 길이(Length)만 상태로 뒀다. `FishingLayout.SetDug`가 판 길이까지 꺾은선을 자르고, 그 꺾은선에서 막힌 사각형과 길찾기 격자를 다시 만든다. 물고기 · 그림 · 쿵 · 오프라인 시뮬은 원래부터 `Layout.Length` · `Stream`만 읽었으므로 고칠 곳이 없었다. 막다른 끝의 둑은 물 칠하기가 「물 밖 둘레에 둑」 규칙이라 그대로 그려졌다. 파기 버튼은 다음에 팔 한 칸의 가운데에 두는 사물이고, 새 물에 서 있던 웜뱃은 길찾기의 「가까운 빈 점」으로 비킨다. 대가 위쪽 반원만 보는 규칙은 `FishingArea.InReach` 하나에 두어 감기 · 미끼 둔화 · 대물 곁 앉기가 같이 따른다. 그래서 셋째 물길 아래 말뚝 자리가 필요해 방을 한 줄 늘렸다. 월드 글자가 깨진 까닭은 값 표식 알약을 0.45 · 0.7배로 줄여 쓴 것(UI 규칙 8 「정수 배」 위반)이라 모두 1배로 돌렸고, 「!!」 알약은 손님이 쓰던 「!」 이모지 말풍선으로 바꿨다. 같은 날 아트방이 넘긴 물고기(물속 모습 · 옆모습)와 말뚝에 맞춘 낚싯대(당김 판 포함)를 붙였다. 물고기는 오른쪽을 보는 그림을 가로는 뒤집고 세로는 90도로만 돌리며, 월척은 2배(정수 배)로 키웠다. 광장 낚시터 문에는 아트방 「물고기 간판」(아치 위 나무 물고기, 이름 판에 진갈색 글)을 얹었다.
- **AI가 한 일**: 객관식 두 번(무엇이 어색한가 · 물길을 어떻게 늘릴까)으로 설계를 정하고 배치 그림이 든 설계 페이지로 확인받았다. 테스트 둘을 더했다(파기 열두 번으로 끝까지 · 값 · 웜뱃 비킴 · 끝에서 대상 없음, 말뚝 아래 물고기는 90초 동안 한 번도 감지 않음). 플레이 중에 스크립트를 고쳐 도메인이 다시 읽히며 생긴 예외를 게임 오류로 잘못 볼 뻔했다. 깨끗이 다시 켜서 콘솔 0을 확인했다. 에디터를 강제로 끈 뒤 다시 켜자 장면 백업 복구 창에서 멈춰 있어서, 화면을 찍어 보고 「아니오」를 눌렀다(장면은 고치지 않았다). 테스트 324 → 326.

### 4.89 아트방 UI 다듬기 넷 · 흙 계단 · 오두막 — 모형 스크립트를 프리팹 편집으로 옮기고, 팝업이 HUD 아래로 숨던 것을 한 곳에서 (2026-10-05)

- **문제**: 아트방이 사용자에게 고르게 한 UI 시안 넷(편집 패널 D · 돌아왔을 때 팝업 A · 유물 화면 B · 석상 팝업 A)과 흙 계단 · 낚시 오두막이 넘어왔다. 시안은 플레이 중 진짜 팝업을 복제해 고친 모형 스크립트로 찍은 것이라, 수치의 원본이 화면 px 숫자와 코드 한 벌이었다. 따로 지적된 버그도 있었다: 유물 · 석상 · 돌아왔을 때 팝업을 열면 오른쪽 HUD 버튼 줄이 팝업의 닫기(×) 위에 그려졌다.
- **기술 포인트**: 모형 스크립트를 읽어 같은 조작을 `PrefabUtility.LoadPrefabContents`로 프리팹에 한 번 적용하는 편집 스크립트로 옮겼다(새 조각을 만들고 직렬화 필드를 `SerializedObject`로 잇는다). 줄 수가 표에서 오는 것(석상 메달 = 축복 수)은 프리팹에 칸 틀 하나만 두고 화면이 복제한다. 글과 값을 한 줄에 섞던 문구(「판매 +{0}」 · 「모은 유물 {0}/{1}」)는 이름과 값을 나누어 칩 · 소제목 줄에 따로 놓았다. HUD 겹침의 원인은 GameKit `UIManager.Open`이 화면을 연 순서대로 형제 순서를 정하는데, 유물 화면이 편집 · 점원 · 창고 화면보다 먼저 열려 그 버튼들이 위에 그려진 것이었다. 팝업 열기는 모두 `UiFx.Appear` 한 곳을 지나므로, 팝업 몸통이 있을 때 그 화면을 맨 앞 형제로 올리는 한 줄로 모든 팝업이 고쳐졌다(목록 줄이 나타날 때는 건드리지 않는다).
- **AI가 한 일**: 다섯 넘김의 수치를 대화 기록에서 다시 찾아 모았고(요약으로 잘려 있었다), 아트방이 에디터를 쓰는 동안에는 코드만 쓰고 비면 프리팹 편집 · 굽기 · 플레이 확인을 했다. 플레이에서 다섯 화면과 석상을 빈 뒤 메달 상태를 캡처했다. 같은 날 웜뱃 엉덩이 쿵 · 털썩 앉기 시트(굴 파기 시트를 빌리던 것을 칸 순서 표로: 쿵 [0,0,1,1,1,2,2,2], 털썩 [0,0,1] 뒤 앉음 유지, 대물 곁에 앉기 시작할 때 한 번)를 붙였고, 아트방이 그림 규칙을 「원본 그대로」로 바꿔 낚시 그림을 같은 이름으로 다시 옮겼을 때는 좌표가 그대로라 다시 불러오기만으로 끝났다(물고기 크기는 그림에서 읽는다). 낚시 행동 아이콘 다섯(원본 그대로라 18×18이 아님)은 상호작용 버튼 아이콘을 고정 72px 대신 그림 크기 × 4(`SetNativeSize`, PPU 25)로 바꿔 받았다. Unity가 꺼졌다 켜지며 남긴 복구 씬은 지금 씬과 바이트까지 같은 것을 확인하고 지웠다. 그 사이 상대 방이 플레이 중일 때 스크립트를 고쳐 다시 컴파일될 수 있었던 것은 알리고 사과했다(그 뒤로는 상대 플레이 중에 파일을 건드리지 않음).

### 4.90 두 방 폴리싱 루프 — 플레이어의 「왜?」를 번호로 쌓고, 원인은 판독이 아니라 상태 값으로 (2026-10-05)

- **문제**: 사용자가 자리를 비우며 아트방에 「프로그래밍방과 협업해 라이브게임 급으로, 콘텐츠 추가 없이 플레이하며 어색한 곳을 고치라」고 했다. 낚싯대가 말뚝 구멍 뒤에 떠 있었고(대를 말뚝 뒤에 그림 + 피벗 한 칸 어긋남), 오븐 점원 얼굴이 굴뚝에 가렸고, 오른쪽 버튼 줄이 맨 끝 사물을 덮었고, 물때 팻말이 화면 밖으로 잘렸고, 밀이 없어 멈춘 빵집이 「…」 말풍선 하나로만 보였다.
- **기술 포인트**: 판독이 짚은 원인을 그대로 믿지 않고 상태 값으로 확인했다. 「낚싯줄이 값 알약을 가린다」는 확대해 보니 같은 정렬 순서(1000)의 「!」 말풍선이었고, 「버튼이 사물을 가린다」는 카메라 경계가 아니라 따라가기 중심 문제라(빵집 경계가 화면보다 훨씬 넓다) 웜뱃을 버튼 줄을 뺀 폭의 가운데에 두는 한 줄(`Frame`)로 고쳤다. 대 피벗은 짝수 폭 가운데를 왼쪽 칸으로 잡던 계산을 원본 스크립트에서 고쳐 그림 픽셀은 바이트까지 같게 두었다. 멈춘 빵집은 Core 점원에 「기다리는 재료」 하나만 더하고, 있는 대사 말풍선을 상태형으로 쓰는 `SayWhile`로 「밀 모자라요」를 띄웠다. 아트방이 그린 말뚝 등급 별은 등급 수만큼 가운데 맞춤으로, 물결 타일 넷은 물길 그림을 네 장 칠해 0.35초마다 바꾸는 것으로 받았다(프리팹은 다시 굽지 않고 필드만 잇기).
- **AI가 한 일**: 아트방 판독 목록(13개)과 내 사건 훑기(사건마다 받는 화면 · 소리 대조 → 물길 파기만 소리가 없었다)를 리뷰 페이지 한 장에 번호로 쌓았다. 에디터 하나를 「쓴다 → 비었음」 메시지로 나눠 쓰고, 고치기 전에 파일 이름을 먼저 보냈다. 오븐 점원 자리를 옮기자 오프라인 공식 대조 테스트가 깨져 임시 진단 테스트로 자리 다섯을 시뮬했는데, 자리를 0.03만 바꿔도 판매가 780~893으로 출렁여 이 대조 테스트(씨앗 6개)가 시뮬 소음에 민감하다는 것을 보고에 남겼다. 커밋 · 푸시는 전달받은 지시로는 하지 않고 사용자를 기다렸다.

### 4.91 낚시 다시 보기 — 쿵은 「범위 고리 + 머리 위 별」, 든 대는 세운 그대로 손에 (2026-10-05)

- **문제**: 사용자가 낚시터에서 일곱 가지를 물었다. 셋은 질문이었고(대 사거리 반원 · 앉기 · 특별한 대의 효과) 넷은 고칠 것이었다. 쿵은 물고기를 멈추는데 화면에는 웜뱃 동작과 작은 물보라뿐이었다(멈춘 물고기 깜빡임은 어두운 그림자에 색을 곱해 거의 안 보였다). 파기 값이 늘 떠 있었고, 놓침 팻말은 빼기로 했고, 머리 위에 90도로 눕혀 든 대는 「머리에 막대가 꽂힌」 모양이었다.
- **기술 포인트**: 새 그림 없이 있는 조각으로 풀었다. 쿵은 웜뱃 쿵 칸에 맞춰(동작이 그 초를 돌려준다, 파기와 같은 방식) 쿵 반지름까지 퍼지는 고리 + 물보라, 멈춘 물고기마다 말뚝 별 하나가 머리 위를 돈다. 든 대는 돌리지 않고 웜뱃의 손 자리(든 빵과 같은 자리 · 같은 앞뒤 순서)에 세우고, 원본에서 같이 옮겨진 밑동의 말뚝 테 다섯 칸은 잘라 낸 그림을 `Sprite.Create`로 한 번 만들어 쓴다. 파기 값은 빵집 · 농장처럼 대상일 때만, 놓친 수는 Core에서까지 지웠다(테스트는 사건 수로).
- **AI가 한 일**: 질문은 표 · 코드에서 값을 읽어 답했다(사거리 2.0~2.4 위쪽 반원, 쿵 반지름 1.8 · 2초 · 쉬는 15초, 앉으면 대물 감기 ×2, 도르래 대물 ×3 · 등대 다른 대 사거리 +20% · 통발 4초마다 맨 앞 물고기 되돌림). 플레이에서 시간을 0.25배로 늦춰 쿵 고리와 별을 찍었고, 웜뱃을 앞 · 옆 · 반대 옆으로 돌려 든 대를 확인했다.
