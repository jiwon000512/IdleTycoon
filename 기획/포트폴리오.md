# 동물원 타이쿤 — 포트폴리오 (AI 활용 · 기술 중심)

목적: 매출과 무관하게 "AI 에이전트와 1인 개발로 모바일 게임을 어떻게 만들었나"를 보여 주는 문서. **기능 하나를 완성할 때마다 4장에 한 절을 추가**한다. 기획 내용은 `동물원-타이쿤-기획서.md`, 절차·규칙은 `코드-규칙.md`가 원본이고 여기는 요약·성과만 둔다.

---

## 1. 한 줄 요약

Unity 6 · URP · 세로 모바일 방치형 타이쿤. 기획서 작성부터 코드·씬·프리팹·더미 리소스·테스트까지 **Claude Code 에이전트가 Unity 에디터를 CLI로 직접 조작**해 구현하고, 사람은 결정과 확인만 한다.

## 2. 기술 스택과 구조 결정

## 3. AI 활용 방식

### 3.1 작업 절차 (기능 하나 = 세션 하나)

1. **설계**: 에이전트가 `기획/설계/NN-*.md`에 클래스·책임·의존·검증 항목을 쓰고, 결정이 필요한 것은 객관식으로 묻는다. 사람이 확정.
2. **구현**: 에이전트가 한 번에 전부 구현. 스크립트뿐 아니라 **씬·프리팹·게임오브젝트·더미 스프라이트까지 Unity CLI(`run_script`, `recompile`, `capture_game_view`)로 에디터 안에서 생성**한다.
3. **검증**: 에이전트가 1회 실행 — 컴파일 0·콘솔 0·EditMode 테스트·플레이 모드 캡처.
4. **보고**: 만든 것·검증 결과·달라진 점을 짧게. 진행상황·포트폴리오 갱신.

### 3.2 에이전트가 맡은 것 / 사람이 맡은 것

| 에이전트 | 사람 |
|---|---|
| 기획서 초안·버전 관리, 레퍼런스 조사, 수치 초안(비용 곡선·확률·레벨 표) | 장르·루프·시점 같은 방향 결정, 객관식 답변 |
| 설계 문서, 전 코드, 테스트, JSON, 씬·프리팹 조립, 더미 리소스 생성 | 플레이 감각 확인("작동은 잘돼", "원근감이 안 나타나"), 스크린샷으로 문제 제보 |
| 규칙 문서 유지(코드 규칙·데이터 규칙·규약), 세션 인수인계 문서 | 절차 자체를 바꾸는 결정 |
| 커밋 메시지 | 커밋 시점 결정 |

### 3.3 재현 가능하게 만든 장치

- **규칙 문서가 코드보다 먼저**: 표기·계층·오류 처리·이벤트·테스트 규칙을 문서로 두고 에이전트가 grep으로 스스로 검사(`UnityEngine` in Core, `Find`, 한국어 리터럴 0건).
- **UI 문구 전부 `strings.json`**: 코드·프리팹에 한국어 리터럴 금지 → 다국어 대비.
- **더미 리소스 우선**: 에이전트가 단색 스프라이트·프리팹을 먼저 만들고, 사람이 같은 경로에 실제 아트를 덮어쓰면 코드 수정 없이 교체.
- **세션 인수인계 문서(`진행상황.md`)**: 다음 세션이 알아야 할 것만 — Unity CLI에서 겪은 함정(플레이 모드 중 `run_tests` 금지 등)을 포함.

## 4. 기능별 기록

### 4.1 기반 세팅 + GameKit (2026-09-13)

- 기술: asmdef 계층, `.editorconfig`, JSON 테이블 규칙, 세로 고정, 불필요 패키지 제거. 공통 기반을 별도 UPM 패키지(GameKit v0.1)로 분리해 `file:` 참조.
- AI: 초기 세팅 절차를 Claude 스킬(`unity-project-setup`)로 만들어 다음 프로젝트에서 재사용. 규칙 문서 3종을 에이전트가 초안 → 사람이 다듬음.

### 4.2 기능 01 — 부트스트랩과 상단 바 (2026-09-14)

- 기술: 테이블 로드 → 검증 → 상태 생성 → Presenter 조립의 컴포지션 루트. `TableValidator`가 데이터 규칙 7장을 코드로. EditMode 테스트 47개.
- AI: 한글 TMP 폰트가 없어 `초당`이 □로 나오는 것을 캡처로 발견하고 SDF 폰트 에셋까지 스스로 생성. 의존 방향(`UI → Game`)을 구현 중 `Game → UI`로 뒤집고 규칙 문서에 이유를 남김.

### 4.3 기능 02·03 — 가차와 월드 슬라이스 (2026-09-14)

- 기술:
  - 가차: 등급 가중치 × 종 가중치를 누적 표 하나로 만들어 난수 1회(`GachaTable`), 비용 `100 × 1.12^n` 반올림, `IRandom` 경계로 결정적 테스트(`SequenceRandom`). 테스트 케이스 78개.
  - 월드: 처음엔 uGUI 3×3 격자 → 기획 전환으로 **2D 월드 맵**. 동물은 우리 안을 랜덤 목적지로 걷는 개체, 중복 뽑기 = 마리 수 증가(`Level` = 마리 수, 수식 유지).
  - 시점: 쿼터뷰(방향별 스프라이트 부담) 기각 → "우리 단위 원근"(사다리꼴·축소) 구현 → **세로로 쌓으면 소실점이 모순**되는 것을 사용자 스크린샷으로 확인 → **원근 카메라 + 빌보드 카드**로 전환. 깊이 정렬·축소 코드가 사라지고 World가 더 단순해짐.
- AI:
  - 프리팹 4개·씬 오브젝트·더미 스프라이트 15개를 전부 `run_script`(에디터 C#)로 생성. 플레이 모드 없이 `capture_game_view --source camera`로 카메라 프레이밍을 세 번 반복 조정.
  - 기획 방향이 세션 중간에 바뀌었을 때(격자 → 월드), 살릴 코드(Core·버튼·카드)와 버릴 코드(격자 View·대기실)를 분리해 기획서 v0.9·로드맵을 다시 씀.
  - 문제 특정: 스크린샷 한 장에서 "우리마다 소실점이 따로라 인접 원근이 모순"이라는 구조적 원인을 짚고 선택지 3개(원근 카메라 / 원근 포기 / 소실점 공유)와 비용을 제시.

### 4.4 기능 04 — 수입 틱과 GameManager (2026-09-14)

- 기술:
  - `IncomeService.Tick(dt)` 5줄: 초당 수입 × 경과 초 적립 후 레벨 판정. `GameManager.Update`가 `game_config.income.tickSeconds`(1초)마다 호출. 표시 보간 없음.
  - 버튼 남은 시간 = ⌈(비용 − 코인) ÷ 초당 수입⌉, 수식은 `GachaService`에, 문구는 `strings.json`. 갱신은 기존 `CoinsChanged` 구독으로 끝(틱마다 발생).
  - 구조 변경: 컴포지션 루트 `GameBootstrap` → **`GameManager`(MonoSingleton) + 씬 스크립트 `MainScene`**. 씬이 늘어도 상태는 한 곳. `.meta`만 이름을 바꿔 씬 참조를 살렸다.
- AI:
  - 구현 직전 전 스크립트를 과잉 설계 관점으로 리뷰해 12건 -105줄 정리(미사용 API·수동 코루틴 핸들·설정 아닌 설정값 `costBasis` 삭제) 후 기능을 얹음.
  - 설계 단계에서 "매 프레임 틱, 보간 없음"을 제안 → 사용자가 "1초 틱"으로 확정. 틱 간격은 기획 숫자로 보고 JSON(version 4)에 둠.
  - 검증 중 에디터 창이 뒤에 있으면 프레임이 멈추는 것을 `Time.frameCount` 조회로 잡아 `editor_focus`로 해결, 인수인계 문서에 기록.

### 4.5 기능 05 — 동물 데이터와 상태, 웜뱃 (2026-09-14)

- 기술:
  - 동물의 스탯·연출값 7개(시트 경로·프레임 속도·크기·이동 속도·대기 시간)를 `animals.json` version 2로. 프리팹·코드에 종별 숫자 0개.
  - `AnimalActor`는 `AnimalState { Idle, Move }` + `switch`의 명시적 FSM. `SpriteAnimator`(20줄)가 프레임 배열을 순환. Unity Animator 에셋 없이 JSON만으로 새 종이 붙는다.
  - 등급 확률을 "동물이 있는 등급만 정규화"로 바꿔 종이 1개일 때도 표시·수식이 거짓이 아니다.
- AI:
  - 실제 아트 3장(정지·idle 시트·move 시트)을 받아 Unity 자동 슬라이스가 맞닿은 프레임을 합쳐 놓은 것을 meta에서 발견, `ISpriteEditorDataProvider`로 6×1 격자 슬라이스·피벗·PPU를 CLI 스크립트로 설정. 다운스케일된 크기로 자른 첫 시도의 오차(341 vs 362)를 원본 크기 조회로 바로잡음.
  - 더미 8종 삭제로 깨지는 테스트 6개 파일을 웜뱃 숫자로 다시 씀. 프레임 경계 비침은 아트 문제로 분리해 기록.

### 4.6 기능 06 — 관광객 (2026-09-14)

- 기술:
  - 관광객 수를 홍보 단계가 아니라 **초당 수입의 로그**(`min(12, 1 + ⌊log₂(1 + 수입)⌋)`)로 계산하는 순수 함수 `VisitorCalculator`(Core, 테스트 6케이스). 어떤 성장 축이든 수입을 올리면 길에 사람이 늘어 세 축 공통의 시각 피드백이 된다.
  - 길은 우리마다 앞에 깔린 **길 타일의 경계**(`CageView.PathBounds`)가 곧 걷는 영역. 웨이포인트·길찾기 없이 X 방향 직진 + Enter·View·Leave 3상태 FSM. 우리가 늘어도 데이터가 늘지 않는다.
  - 관광객 종류는 `visitors.json`(가중치 선택), 연출 숫자는 프리팹 인스펙터, 게임 규칙 숫자는 `game_config.visitors`. 세 종류의 숫자가 각각 제자리에 있다.
- AI:
  - 인터넷 레퍼런스 14건(Idle Miner Tycoon GDC, 고양이와 스프, Merge Town, AdVenture Capitalist 수학 등)을 조사해 "환생 없음 + 성장 축 3개 + 지점 유지형 2호점"을 근거와 함께 제안, 사용자가 확정(기획서 v0.13).
  - 설계 06의 관광객 수 제안(기본 3 + 단계)이 사용자 답변("수는 획득 가능한 코인에 따라")과 달라 로그 수식으로 다시 설계하고 구현. 더미 실루엣·길·코인 PNG 4장, 프리팹 2개, 씬 연결을 CLI 에디터 스크립트 2개로 생성. Unity 가짜 null(`?? AddComponent`) 실패를 `TryGetComponent`로 수정.
  - 플레이 검증은 리플렉션으로 FSM 상태를 14회 폴링해 View 상태와 0.7초짜리 코인 팝업을 실제로 잡았다(캡처만으로는 놓친다).
- 문제와 해결: 사용자가 "난간이 관광객을 가린다"고 지적. 플레이를 일시정지해 관광객 좌표를 읽고 그 지점을 4배 확대 크롭해 비교하는 방법으로 원인을 특정했다. 카메라 거리 정렬은 9.6유닛짜리 난간의 정렬점이 가운데 하나뿐이라 옆으로 간 관광객을 뒤로 보낸다. 정렬점 Pivot만으로는 가운데만 해결돼, URP 2D 렌더러를 Custom Axis(Z) 정렬로 바꿔 해결. 렌더러 에셋을 텍스트로 고친 뒤 강제 재임포트가 필요하다는 것도 이때 알았다.

### 4.7 구조 정리 06-1 — 리뷰 8건 (2026-09-14)

- 기술:
  - 월드 개체를 `Unit`(공통 몸체) → `Animal`·`Visitor`로 재구성하고, `switch` FSM을 **상태 객체**(`UnitState` → `WalkState`·`WaitState`)로 바꿨다. 두 개체가 "걷기"와 "기다리기" 두 상태를 공유하므로 상태 클래스는 2개뿐이고, 개체는 전이 순서만 적는다. 상태 인스턴스는 초기화 때 한 번 만들어 재사용.
  - 초당 수입의 소유자를 `IncomeService` 하나로(`IncomePerSecond` + `IncomeChanged`). 세 곳이 각자 재계산하던 것을 없애 다음 기능(홍보)의 구독 지점이 한 곳이 됐다.
  - "레벨"이라 부르던 마리 수를 코드·JSON·문구 키까지 `Count`로 통일해 다음 성장 축(별)과의 이름 충돌을 미리 제거. 데이터 변경 절차(기획서 → JSON version 6 → 검증 테스트)를 그대로 밟았다.
  - `FrameCache`(경로당 1회 로드, 번호 접미사 정렬)로 관광객이 1.5초마다 `Resources.LoadAll`을 부르던 비용과 11프레임 이상 시트의 정렬 버그를 함께 제거.
- AI:
  - 코드 3,000줄 전체를 읽고 규칙 문서와 대조해 8건을 순위와 근거로 보고 → 사용자가 "전부 + Unit 상속·State 패턴" 지시 → 코드 20파일·테스트 4파일·JSON 2개·기획 문서 4개를 한 번에 수정. 스크립트·프리팹 이름 변경은 `.meta`를 같이 옮겨 GUID를 유지(씬·프리팹 참조 무손실).
  - 검증은 플레이 모드에서 버튼 3회 호출 후 상태 조회(마리 수·스프라이트 프레임·관광객 수·결과 카드 활성)로 확인. 캡처만으로는 프레임 전환을 못 본다.
- 문제와 해결: 팝업 View를 Presenter에 주입하려면 GameKit `UIManager`에 "열지 않고 얻기"가 없었다. `GetView<T>`를 public으로 여는 한 줄 변경(패키지 저장소).

### 4.8 기능 07 — 우리 꾸미기, 시설 (2026-09-15)

- 기획 전환: 설계 시작 시점에 "우리 해금·맵 확장"이던 07을 사용자가 **"우리는 지점당 하나, 그 우리를 꾸미는 구조"**로 바꿨다. 에이전트가 객관식 5문(꾸미기의 본체·배치 방식·수입 효과·해금 조건·첫 범위)으로 결정을 받아 기획서 v0.16·데이터-테이블-규칙 v1.10·설계 07을 같은 세션에 반영하고 구현했다.

  - 시설 = 테이블 행(`facilities.json`: 자리·해금 레벨·최대 단계·단계당 배수·비용 곡선). 홍보는 첫 행일 뿐이라 `game_config.promotion`과 `ZooState.PromotionStage`를 지우고 **시설별 단계 사전 + `FacilityService`** 하나로 통일. 총 배수는 시설 배수의 곱.

- 문제와 해결: 캡처에서 **산 시설이 화면에 없었다.** 자리를 우리 바깥(x ±6.2)에 잡았는데 세로 화면은 길 깊이에서 ±5유닛만 보인다 → 우리 안 네 모서리로 옮기고 기획서·규칙 문서를 함께 고쳤다. 고친 JSON이 플레이에서 옛 값으로 읽혀(에디터 비포커스 상태에서 자동 임포트 안 됨) `AssetDatabase.ImportAsset(ForceUpdate)`를 eval로 돌려 해결.

### 4.9 기능 07-1 — 시점 전환, 원근에서 직교 쿼터뷰로 (2026-09-16)

### 4.10 기능 07-2 — 순수 2D 쿼터뷰로 전환 (2026-09-16)

- **기술 포인트**: 07-1의 "3D 카메라 + 빌보드"를 같은 날 버리고 장르 표준인 순수 2D로. 논리 좌표(XZ)는 그대로 두고 `Iso.ToScreen` 한 함수가 화면 XY(2:1)를 만들며, 깊이는 화면 y 정렬. 바닥·길은 평행사변형 스프라이트, 울타리는 칸 단위 스프라이트를 네 변에 늘어놓는 방식(긴 한 장은 y 정렬이 깨진다). World 계층 10개 파일 수정, Core·테스트 변경 0, 98/98 통과.
- **AI가 한 일**: "왜 그냥 2D에 안 뿌렸나"라는 질문에 두 방식의 등가성과 차이(변환 코드 vs 방향별 아트, 픽셀 리샘플링, 장르 관행)를 표로 답하고, 레퍼런스 게임들이 순수 2D임을 근거로 추천을 바꿨다. 더미 바닥·길·울타리 PNG를 외부 라이브러리 없이 순수 python(zlib)으로 생성하고, 실제 아트용 프롬프트(눕는 텍스처는 top-down seamless → 에이전트가 평행사변형 변환, 서 있는 물체만 쿼터뷰 각도)를 `아트-프롬프트.md`에 적었다.
- **문제와 해결**: 07-1 검증 중 Unity CLI 파이프라인이 `run_tests` 뒤 멈춰 프로세스를 강제 종료·재실행. 재실행 직후 스크립트를 쓰는 중에 컴파일이 돌아 옛 오류가 콘솔에 남았고, `console_status`의 groundTruth(오류 0)로 구분했다.

### 4.11 기능 07-3 — 타일맵과 1호점 맵 (2026-09-16)

- **기술 포인트**: 눕는 바닥(잔디·흙·길)을 Unity Tilemap(Isometric Grid, 셀 1×0.5)으로 옮기고 타일 64×32 px = 논리 1유닛이 되도록 `Iso` 상수만 0.5/0.25로 바꿨다. Unity의 `CellToWorld`와 `Iso.ToScreen`이 같은 식이라 셀 (x, z) = 논리 (x, z)로 두 좌표계가 하나가 됐다(`GetCellCenterWorld(0,0) == Iso.ToScreen(0.5,0.5)`로 검증). 존은 6×8 타일 프리팹(`ZoneView`), 1호점은 존 10개 + 길 2칸을 타일맵에 미리 칠해 둔 프리팹(`BranchView`)이고 씬에는 인스턴스 하나. 서 있는 것(울타리·시설·동물)은 스프라이트 + 화면 y 정렬을 유지해 타일맵 청크와 정렬 충돌을 피했다. 코드 변경은 World 7파일, Core·테스트 0.
- **AI가 한 일**: 타일맵 채택 여부와 1호점 배치를 아티팩트 두 장(현행 vs 안 B·C 비교, 위에서 본 배치 + 쿼터뷰 렌더링 SVG)으로 그려 논의를 이끌었고, "왜 Unity Tilemap을 안 쓰나"는 오해에 바닥층은 쓰고 서 있는 것만 안 쓰는 이유(청크 정렬·런타임 생성)를 답했다. 타일 더미·울타리 더미는 Pillow로 생성(첫 시도의 폴리곤 가장자리 틈을 행 단위 스팬으로 고쳐 이음새 제거), 에디터 스크립트 한 번으로 임포트 설정·Tile 에셋·프리팹 2개·타일 칠하기·씬 교체를 끝냈다. 캡처에서 발견한 세 가지(타일 틈, 개체가 타일 대비 큼, 울타리 뒤 모서리 X자 교차)를 그 자리에서 고쳤다(정수 좌표 기둥 + 뒤 모서리 기둥 스프라이트).
- **문제와 해결**: PATH의 python이 MSYS2용이라 pip이 없고 pacman은 gcc 의존 충돌. winget으로 Windows Python 3.12를 따로 설치해 Pillow를 쓴다. 아트 생성은 사용자의 ChatGPT 구독으로 로그인된 Codex CLI의 내장 이미지 생성을 명령줄에서 호출할 수 있음을 확인(자물쇠 1장 테스트)해, 이후 리소스는 에이전트가 직접 뽑는다.

### 4.12 기능 08 — 빵집 코어 루프, 손님이 걸어서 사 가는 가게 (2026-09-18)

- **기술 포인트**: 굴(존)을 누르면 가게 화면으로 넘어가고, 손님 동물이 입구 → 좌우 진열대(원하는 빵) → 가운데 줄 → 계산대 웜뱃 → 퇴장한다. 재고가 없으면 참다가 화내며 나간다. 규칙은 Core `ShopSim` 하나가 전부 갖고 **걷는 시간까지 Core가 센다**(진열대까지 = 1.5 + 층 × 0.8초). World는 이벤트를 받아 "경로 길이 ÷ 받은 시간"으로 속도를 맞춰 걷기만 하므로, 화면과 규칙이 어긋나지 않고 오프라인 계산(11)도 같은 시뮬을 화면 없이 돌릴 수 있다. 가게는 **구역 프리팹을 위에서 아래로 쌓은 것**(입구 · 진열 층 × n · 계산대 · 오븐 줄 × m)이라, 빵을 해금해 층이 늘면 한 층을 끼우고 아래를 내린다(굴 확장 연출 + 카메라 이동). 빵 종류 추가 = `breads.json` 한 행. 카메라는 가게에 들어가면 경계만 가게 사각형으로 바꿔 기존 드래그 코드 그대로 세로 스크롤이 된다. 다 구운 빵은 오븐에서 기다리다 진열대에 자리가 나면 옮겨진다.
- **AI가 한 일**: 첫 설계(v0.2)가 줄 게이지·러시·쿵 버튼으로 돌아가는 "HUD 게임"이라는 사용자 지적을 받고, 객관식 네 문항(손님 흐름·플레이어 역할·원하는 빵·업그레이드)으로 의도를 좁혀 v0.3 → 배치 지시 반영 v0.4 → 결정 3개 확정 v0.5로 설계 아티팩트를 갱신했다. 구현은 한 번에: Core 4파일 + 테스트 12개, World 10파일, UI 팝업 공용 베이스(`ListPopupView`) + 굽기·업그레이드 팝업, 더미 스프라이트 14장(Pillow), 구역 4종·가게·손님·HUD·팝업 프리팹을 굽는 `ShopBaker` 메뉴. 플레이 모드에서 도착·줄·계산·화난 퇴장·굴 확장·스크롤 경계·오븐 탭 → 팝업 → 굽기를 상태 조회와 캡처로 확인했다.
- **문제와 해결**: 캡처에서 바닥 점·구역 경계로 초록 배경이 비쳐 보여(반투명 픽셀) 불투명 어두운 색으로 다시 그렸다. 문자열 리터럴을 상수로 바꾸는 일괄 치환이 상수 선언 자체까지 바꿔 순환 정의 컴파일 오류가 났고 선언만 되돌렸다. 도착 4초·계산 1.5초에서는 줄이 1명 넘게 쌓이지 않아, 검증할 때만 실행 중 값을 바꿔 줄 모양을 확인했다(데이터는 그대로).

### 4.13 아트 — 첫 손님 토끼, 시안부터 인게임까지 (2026-09-21)

- **기술 포인트**: 손님 외형이 이제 앞·뒷모습 × 숨쉬기·걷기 4시트다. `Unit.Face`가 화면에서 위로 걸으면 뒷모습, 아래로 걸으면 앞모습을 고르고, 옆으로만 걸을 때는 직전 방향을 유지한다. 대기와 걷기 프레임 속도를 나눠 웜뱃과 같은 2.5·8fps로 맞췄다(`visitors` version 2). 말풍선은 외형 키(스프라이트 높이)에 맞춰 머리 위에 뜬다. 숨쉬기·걷기 프레임은 AI 없이 칸 편집 스크립트가 만들고, 웜뱃 스크립트에 토끼 설정 줄만 더해 공용으로 쓴다(다시 돌려도 웜뱃 결과는 그대로).
- **AI가 한 일**: 후보 4종을 실루엣 기준으로 제안하고, Codex CLI로 시안 3장을 뽑아 격자를 강제한 뒤 실제 가게 캡처 위에 합성한 비교 아티팩트 한 장으로 논의했다. 버전 6까지 같은 URL에서 갱신하며 선택을 좁혔다(앞모습 3장 → "A에 B의 손" 칸 편집 → 손가락 선 제거 → 뒷모습 3장 → 숨쉬기 → 걷기). 숨쉬기·걷기는 페이지 안에서 게임 속도로 재생해 보여 줬다. 적용은 한 번에: 시트 묶기 스크립트, 슬라이스 메뉴(`ZooTycoon/Bake/Import Visitor Sheets`), 레코드·검증·테스트, 방향 전환, 말풍선 높이. 플레이 모드에서 진열대 앞 앞모습, 줄 서기, 계산 뒤 뒷모습 퇴장, 화난 퇴장을 캡처로 확인했다.
- **문제와 해결**: 웜뱃 걷기처럼 귀 전체를 옆으로 밀면 긴 귀가 머리와 만나는 곳에서 외곽선이 끊겨, 귀 윗부분만 미는 `tip` 값을 추가했다. 격자 자동 측정이 시안 C에서 반 주기를 잡아 얼굴이 뭉개졌고, 칸 수를 직접 줘서 다시 맞췄다. 크림색 털이 가게 바닥과 비슷해 묻힌다는 점은 비교 페이지에 적었고, 사용자는 그 점을 알고 A를 골랐다.

### 4.14 아트 — 손님 3종 추가(펭귄·여우·고슴도치), 파이프라인 재사용 (2026-09-23)

- **기술 포인트**: 토끼 때 만든 파이프라인(격자 강제 → 칸 편집으로 숨쉬기·걷기 → 시트 → 슬라이스 메뉴 → `visitors` 행)에 스크립트 설정 줄과 JSON 행만 더해 새 손님을 넣었다. 세 종을 넣는 동안 코드 변경은 시트 칸 폭 상수 하나(60 → 88, 여우 걷기 프레임이 86px)와 테이블 버전 테스트뿐이다. 귀가 없는 종(펭귄·고슴도치)은 숨쉬기 스크립트의 귀 목록을 비우면 그대로 돌고, 뾰족귀(여우)는 토끼처럼 귀 끝만 갸웃한다.
- **AI가 한 일**: 앞모습을 참조로 뒷모습 3장을 뽑아 실루엣을 앞모습과 같게 맞추고, 앞모습 팔레트로 색을 통일했다. 격자 자동 측정이 한 장에서 48줄을 잡아 36줄로 강제했고, 팔레트 문턱에 하이라이트가 잘려 주황으로 바뀐 것을 문턱을 낮춰 살렸다. 여우·고슴도치는 사용자가 앞모습(여우 A·고슴도치 B)만 고르고, 뒷모습 3장씩은 그때까지의 선택 기준(앞모습과 같은 실루엣·같은 자리 하이라이트·앞뒤가 이어지는 특징·7색 이하)으로 에이전트가 골라 인게임까지 한 번에 적용했다. 뒷모습 실루엣이 앞과 칸 단위로 같아 숨쉬기·걷기 설정을 앞뒤가 공유한다.
- **검증**: EditMode 56/56, 콘솔 0, 플레이 캡처로 네 종의 진열대 앞 앞모습·계산 뒤 뒷모습 퇴장·화난 퇴장 확인.
