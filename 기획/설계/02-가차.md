# 설계 02 — 가차

상태: 구현 완료 · 2026-09-14. **설계 03(기획서 v0.9)에서 우리 격자·대기실 부분은 폐기**(Core 가차·버튼·결과 카드는 유지). QA는 03과 함께 한다
기능: 하단의 큰 가차 버튼으로 코인을 내고 동물 1마리를 뽑는다. 새 종이면 빈 우리에 들어가거나(없으면 대기실), 이미 있는 종이면 레벨업한다. 결과는 약 1초 동안 카드로 보여 준다. 우리 격자 3×3에 열린·빈·잠긴 우리를 표시한다.
기획서 대응: 3장 핵심 루프 1~2, 4장 우리 격자·큰 가차 버튼, 6.1 확률, 6.2 레벨, 6.3 비용, 6.4 시작 상태, 8장 확률·결과 연출
다음 기능: 03 수입 틱(초당 수입 적립, 관광객 연출, 버튼의 남은 시간)

## 0. 결정

### 0.1 사용자 확정 (2026-09-14)

| # | 결정 | 이유 |
|---|---|---|
| D1 | 결과 연출은 **자동으로 사라지는 카드**(약 1초). 떠 있는 동안 반투명 전체 화면 차단막이 입력을 막는다 | 연타 리듬을 해치지 않으면서 새 종/레벨업이 눈에 들어온다 |
| D2 | 확률은 **버튼 아래 등급 한 줄** 상시 표시: `일반 70% · 희귀 27% · 전설 3%` | 기획서 4장 "확률 상시 표시"를 가장 적은 UI로 충족 |
| D3 | **우리 탭 정보 팝업은 02에서 제외** | 칸에 이름·Lv·초당 수입이 이미 보인다. 로드맵에 따로 올린다 |
| D4 | **시작 코인 300 → 350** (기획서 v0.8) | 비용 100·112·125로 첫 3회에 337이 든다. 300으로는 2회뿐이라 "첫 3회가 튜토리얼"(6.4)이 성립하지 않았다 |

### 0.2 설계 제안 (검토 필요)

| # | 제안 | 이유 |
|---|---|---|
| P1 | 비용은 **반올림한 정수**: `Math.Round(100 × 1.12^n, AwayFromZero)` | 기획서 6.3 표(176·311·965)가 반올림 값이다. 표시한 값과 차감하는 값이 같아야 한다 |
| P2 | 추첨은 **난수 1회**: 동물별 확률 = 등급 가중치 비율 × 등급 안 동물 가중치 비율. `sortOrder` 순 누적 구간에서 고른다 | 기획서 8장 "난수 1회". 확률을 한 표로 만들면 테스트가 6.1 표와 1:1로 맞는다 |
| P3 | `PlacedAnimal` → **`OwnedAnimal`로 이름 변경**, 레벨은 종마다 하나. `ZooState.WaitingRoom`도 `string` 목록에서 `OwnedAnimal` 목록으로 | 대기실 동물도 중복이 나오면 레벨업해야 하므로 레벨을 들고 있어야 한다 |
| P4 | 코인 부족 시 버튼 **비활성만**. "남은 시간" 표시는 **03으로** | 02에는 수입이 없어(초당 0) 남은 시간을 계산할 수 없고, 갱신 주기도 03의 틱이 만든다 |
| P5 | 레벨업으로 우리가 열릴 때 대기실 동물이 들어가는 처리는 **04**. 02는 `ZooLevelService.Refresh()`를 부르지 않는다 | 02에서는 누적 코인이 늘지 않아 레벨이 오르지 않는다 |
| P6 | 결과 카드는 **View가 표시 시간이 끝나면 스스로 닫는다**(`UIManager.Close(this)`). 시간은 프리팹 인스펙터 값 `m_displaySeconds = 1` | 닫기는 연출의 일부라 Presenter가 타이머를 들 이유가 없다. 연출 시간은 기획서 숫자가 아니어서 JSON 스키마(`version`)를 올리지 않는다 |
| P7 | 입력 잠금은 **결과 카드의 차단막 하나로만** 한다. 버튼 Presenter가 카드 상태를 알지 못한다 | Presenter끼리 참조 금지(코드-규칙 4장). 레이캐스트 차단으로 충분하다 |
| P8 | 잠긴 우리의 해금 레벨은 `ZooLevelService.UnlockLevelOfCage(index)`. 어떤 레벨에서도 열리지 않는 칸은 **버그로 보고 예외**. 대신 검증기 규칙을 `마지막 cageCount == 격자 칸 수`로 강화한다(현재 `<=`) | 격자에 영원히 잠긴 칸이 있으면 표시할 문구가 없다. 지금 데이터(Lv.7 우리 9 = 3×3)는 이미 만족한다 |
| P9 | 스프라이트는 Presenter가 `Resources.Load<Sprite>(record.Sprite)`로 직접 읽는다. 캐시 클래스를 만들지 않는다 | Unity가 이미 로드된 에셋을 같은 인스턴스로 돌려준다. 호출 지점은 격자·결과 카드 둘뿐 |
| P10 | 난수 어댑터 이름은 `SystemRandom`(코드-규칙 8장 지도의 `SeededRandom` 대신) | 시드를 받지 않는다. 결정성은 테스트 대역 `SequenceRandom`이 맡는다 |

`TryPull` 흐름(순서가 곧 이벤트 순서):

```
cost = CurrentCost
TrySpendCoins(cost) 실패 → false (상태 불변)       → CoinsChanged
RecordPull()
animal = Table.Pick(random.NextDouble())
Owns(id) ? LevelUpAnimal(id) → LevelUp
         : AddAnimal(id, zooLevel.CageCount) → Placed / Waiting   → AnimalsChanged
OnAnimalPulled(result)                                            → AnimalPulled
```

`CoinsChanged` 시점에는 `PullCount`가 아직 이전 값이라 버튼 비용이 한순간 옛 값으로 계산되지만, 곧이어 `AnimalPulled`에서 다시 갱신하므로 최종 표시는 맞다.

### 1.3 조립 순서 (`GameBootstrap.Awake`)

테이블 로드·검증 → `ZooState.CreateNew` → `ZooLevelService` → `SystemRandom` → `GachaService` → `Open<TopBarView>` → `Open<CageGridView>` → `Open<GachaButtonView>` → 프레젠터 4개 생성. 결과 카드는 뽑을 때 `Open`되므로 항상 맨 위(마지막 형제)에 온다.

### 1.7 규칙 적용과 예외

- 이벤트 핸들러 이름 `State_AnimalsChanged`, `GachaService_AnimalPulled`, `View_Clicked`. 프레젠터는 전부 `Dispose`에서 해제.
